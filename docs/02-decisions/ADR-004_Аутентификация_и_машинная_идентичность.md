# ADR-004 — Аутентификация и машинная идентичность

**Статус:** Принято  
**Дата:** 6 сентября 2026 года  
**Владелец решения:** владелец продукта и технический владелец  
**Затрагивает:** сотрудники, инвесторы, Server, Agent, аудит и поддержка

## 1. Решение

Разделить человеческую и машинную идентичность:

- сотрудники и инвесторы входят через ASP.NET Core Identity с cookie-сессией;
- регистрация выполняется только приглашением администратора;
- для владельца и администраторов обязательна MFA;
- Agent регистрируется отдельным одноразовым кодом, после чего получает
  уникальное отзываемое машинное удостоверение;
- права Agent ограничены версией контракта и API сбора; человеческая роль ему не
  назначается;
- сервер авторизует каждую операцию и не доверяет скрытому UI.

Внешний корпоративный OIDC и mTLS не требуются для первого пилота, но интерфейсы
аутентификации не должны делать их будущую замену миграцией бизнес-данных.

## 2. Контекст

Система содержит внутренние решения, персональные данные, финансовые сведения и
кабинет внешнего инвестора. Одновременно к ней подключаются 3–5 локальных машин,
которые нельзя считать доверенными только по IP или имени компьютера.

## 3. Пользовательская идентичность

Минимальный поток:

1. администратор создаёт приглашение с ролью и сроком действия;
2. пользователь подтверждает адрес и задаёт пароль либо проходит выбранный
   passwordless-поток;
3. сервер создаёт сессию с ограниченным временем жизни;
4. изменение роли/проектного доступа немедленно влияет на новые запросы;
5. отзыв сессий доступен администратору и самому пользователю.

Пароли, recovery codes и токены не попадают в аудит или прикладные логи.
Требования сложности не заменяют rate limit, блокировку перебора и MFA.

## 4. Авторизация

Роль задаёт общий класс действий, permission — конкретную операцию, scope —
допустимые данные. Для инвестора обязательна проверка `ProjectId` на сервере в
каждом запросе и при выдаче файла. Факт знания URL или идентификатора не даёт
доступа.

Отрицательные тесты должны доказывать, что инвестор A не получает проекты,
файлы, события и агрегаты инвестора B. Owner/Admin не обходят аудит критичных
операций.

## 5. Машинная идентичность Agent

Предлагаемый стартовый поток:

1. администратор создаёт одноразовый registration code с коротким сроком;
2. код вводится на конкретном Agent;
3. сервер создаёт `AgentId`, привязывает устройство и выдаёт секрет;
4. локальное приложение хранит секрет в защищённом хранилище ОС;
5. каждый запрос содержит проверяемое удостоверение и защищён TLS;
6. секрет можно ротировать и отозвать без удаления истории Agent;
7. при компрометации устройство получает `Revoked` и больше не берёт задания.

Секрет хранится сервером только как безопасный verifier/hash, когда выбранный
протокол это допускает. Cookie браузерной сессии источника остаются локальными и
не смешиваются с credential Land ERP.

## 6. Рассмотренные варианты

### Человеческий вход

| Вариант | Оценка |
|---|---|
| ASP.NET Core Identity | Рекомендуется для ранней закрытой ERP и кабинета по приглашениям |
| Внешний OIDC/SaaS IdP | Полезен при корпоративном SSO или росте требований; добавляет зависимость и стоимость |
| Собственная криптография/сессии | Запрещено без исключительной причины |

### Agent

| Вариант | Оценка |
|---|---|
| Уникальный ротируемый credential на устройство | Рекомендуется для 3–5 машин |
| mTLS | Сильнее идентифицирует устройство, но требует жизненного цикла сертификатов |
| Общий API key | Запрещён: нельзя точечно отозвать или атрибутировать машину |
| Доверие IP/VPN | Может дополнять защиту, но не заменяет identity |

## 7. Сроки и защитные меры

Точные значения выносятся в конфигурацию, но должны существовать политики:

- короткое приглашение/registration code;
- ограниченная пользовательская сессия и re-auth для критичных действий;
- rate limit входа и регистрации Agent;
- rotation Agent credential;
- немедленный revoke;
- журнал входов, отказов, изменений роли, scope, регистрации и отзыва Agent;
- уведомление администратора о подозрительных событиях без раскрытия секрета.

## 8. Восстановление доступа

Восстановление пользователя подтверждает владение выбранным каналом и завершает
старые сессии по политике. Восстановление Agent — только новая регистрация или
административная ротация; старый секрет не показывается повторно.

## 9. Что не решает этот ADR

- конкретный почтовый/SMS-провайдер;
- юридическую модель инвестора;
- доступ к аккаунту Авито и хранение его локальной сессии;
- облачного провайдера;
- окончательную реализацию mTLS.

## 10. Проверки реализации

- invite, expire, revoke и повторное использование;
- MFA владельца/администратора;
- горизонтальный доступ инвестора к чужому ProjectId;
- отзыв роли при активной сессии;
- регистрация, rotation и revoke Agent;
- отсутствие секретов в логах и аудите;
- работа за reverse proxy и корректные secure-cookie/CSRF-настройки.

## 11. Зафиксированное решение и открытая настройка

6 сентября 2026 года приняты закрытая регистрация по приглашениям, MFA для
владельца/администраторов и отдельный отзываемый credential каждого Agent.
Провайдер и канал доставки приглашений/MFA остаются операционным выбором. До его
утверждения локальный тестовый канал разрешён только в Development.
