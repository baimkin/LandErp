- Цвет не единственный носитель смысла. Сохранить keyboard/focus, подписи контролов, понятные loading/error/empty/disabled состояния. Основные действия не доступны только при наведении.

## R1. Надёжное сохранение

Исправить зависания общения и заметок с файлами, обрыв соединения, отсутствие ошибки и браузерный вопрос «Закрыть сайт?» при сохранении.

Приёмка: текст без файла; текст + файл; текст + Ctrl+V-картинка; общение + задача; общение + задача + файл. Успех подтверждается повторным открытием. При ошибке сохраняется черновик, loading завершается, причина и повтор доступны. Защита от потери текста при реальном уходе остаётся. Повтор/двойное нажатие не создаёт дубликаты.

Известная диагностика для проверки: JS-адаптер возвращал DotNet.createJSObjectReference в typed InvokeAsync<IJSObjectReference> и stream descriptor вместо Blob для typed stream result; повторная обёртка приводила к `text is not a function`, необработанное исключение обрывало circuit. Hotfix изменяет эти возвраты и обработку ошибок. Не удалять все stream references: передача файла аргументом имеет другой контракт. Точечный Node-тест ранее прошёл; .NET-проверка остановлена, полный сценарий не подтверждён.

Не обещать общую транзакцию БД и внешнего хранилища. Если запись создана, загрузка не удалась — явно сообщить частичный результат и повторить только загрузку, без дублирования общения/задачи.

## R2. Общение, задача и файлы связаны в интерфейсе

В переговорах, ходе работы и просмотре общения видны материалы и созданная задача. Имя файла открывает/скачивает файл штатным разрешённым способом, название задачи открывает задачу. Из задачи доступно исходное общение. Не заставлять искать файл среди всех документов объекта. Связи по идентификаторам, не по совпадению текста/времени.

Известные точки проверки: CaseAttachment имеет NegotiationId. CaseFeedFormat.From(NegotiationView) ранее не передавал Attachments, хотя overload истории передавал, а CaseActivityFeed умеет их показывать. Полная карточка строила строки из card.Negotiations. Идентификаторы общения/задачи встречались в аудите создания, но не выведены в навигацию. Проверить достаточность существующих данных; не вводить новую модель без необходимости.

Приёмка: сохранить общение с задачей и файлом, снова открыть объект; из записи открыть обе сущности. После выполнения задачи ссылка продолжает работать. Права доступа сохраняются сервером.

## R3. Задачи: прочитать → выполнить → записать результат → найти выполненную

- Компактный список: понятный контроль выполнения, название, срок/ответственный; вторичные действия в меню. Убрать ряд одинаково заметных «Изменить / Удалить» у каждой строки.
- Название открывает небольшое окно просмотра описания, срока, ответственного, исходного общения и файлов. Для чтения не нужно включать редактирование. Наличие описания/файлов видно компактной отметкой.
- «Выполнить» позволяет указать результат текстом и приложить файл/картинку. Результат необязателен для простой задачи; доступно завершение без отчёта. Описание и результат раздельны.
- В блоке переключение «Активные / Выполненные» с количеством. У выполненной доступны описание, результат, файлы, кто/когда завершил и исходные связи.
- В ходе работы появляется понятная запись о выполнении с результатом/переходом, без повторов одного текста.
- Форма: что сделать, тип, срок, ответственный, дополнительные сведения, действия. Типы не рассыпаются случайными переносами. Дата/время рядом; «Сегодня / Завтра / Без срока» вместе. Дополнительное описание допустимо раскрывать, но его наличие видно. Цены в общении не прятать обратно в аккордеоны.
- Просрочено: текстовая красная отметка; сегодня: «Сегодня, 22:00» с умеренным акцентом; будущие: спокойная дата/«Завтра»; без срока: нейтрально. Порядок — просроченные, ближайшие, без срока. Без новых приоритетов.
- Срок со временем просрочен после момента; дата без времени — после окончания дня по Москве. Правило одинаково в списке/сводке/панели.

Сначала проверить существующие поля результата, завершения, описания и вложений. Если нужна миграция — сообщить до реализации. Приёмка: обе формы завершения, повторное открытие результата, доступ к выполненным, длинное описание, несколько файлов, date-only и точный срок.

## R4. Время одинаково во всём проекте

Во всех полях ввода времени `1200` → `12:00`, `0930` → `09:30`, поддерживается форматированная вставка. Частичный ввод, удаление, выделение и правка середины не ломаются и не сбрасывают курсор. Невозможное время не заменяется молча другим — ошибка рядом с полем. Пустое время допустимо при сроке только датой.

Адресным поиском найти реальные time inputs проекта и использовать общий подход. Предварительный TimeEntry не является доказательством полного покрытия.

## R5. Числовые поля и отображение во всём проекте

- Разделение тысяч пробелами при вводе и просмотре: `14589653` → `14 589 653`.
- Все денежные значения без копеек: `14 589 653 ₽`, включая медиану, среднюю, цену за сотку, торг, тест спроса, денежные расчёты и фильтры.
- Валюта рядом с полем, вводить её не требуется. Вставка с обычными/неразрывными пробелами и знаком валюты работает, курсор не прыгает, пустое поле не превращается в ноль.
- Единое округление денег до рубля при отображении, не усечение; обычная половина вверх для неотрицательных сумм. Точность БД/расчётов сохранить. Открытие формы и сохранение другого поля не затирает копейки исходной суммы.
- Значимые дроби измерений сохранить: `13,1 сот.` не превращать в `13 сот.`. Требование без копеек относится к деньгам.
- Не применять числовую маску к ID, кадастровым номерам, телефонам, кодам, датам/времени. Общие input/formatter вместо отдельных реализаций на каждой странице.

Приёмка: большие значения, вставка, редактирование середины, очистка, дробная площадь, показ округлённой цены без изменения исходной при сохранении других полей.

## R6. Проверки объекта

Вернуть понятный видимый выбор типового пункта и своё название. Скрытого datalist с обещанием «выберите» недостаточно. Два простых сценария: назначить проверку (пункт, необязательный ответственный/срок) либо сразу записать результат. Результат — обычный текст и вложения.

Сохранить базовые/глубокие проверки, состояния, права, блокирующие вопросы и ограничения переходов. Не превращать всё в несвязанные заметки. В CaseChecks проверить templates и legacy поля назначения: данные могли остаться, а создание/редактирование назначения пропало из формы. «Есть вопросы» и блокер не объединять автоматически, глубокую проверку не открывать в обход допуска. Пустые редакторы общих заметок не должны заслонять список.

Приёмка: выбрать типовой пункт, создать свой, назначить, записать результат без предварительного назначения, просмотреть сохранённое; сохранить прежние права и блокировки.

Единая сетка: дата действия слева, бизнес-смысл в широкой средней колонке, короткий тип/автор справа. Колонки выровнены; перенос текста остаётся в своей колонке. Метаданные не разрывают смысл и не добавляют строку без необходимости.

Не повторять результат общения в заголовке и теле. Отличать время события от срока задачи. Показывать файлы/задачи; для изменений — «Подробнее» с реальным «было → стало», если данные сохранены. Не выдумывать отсутствующую историю.

Историю входящего тоже очистить от внутренних названий: изменение участия в медиане не должно выглядеть как «PropertyCase возобновлён». Проверить соответствие подписи фактическому событию, не менять аудит ради оформления.

## R8. Просмотр осмотра

true/false → «Да/Нет» или «Есть/Нет» по смыслу; отсутствующий ответ → «Не указано». Отступы от рамок и цветных линий обязательны.

На широком экране — компактные смысловые группы (подъезд, окружение, коммуникации, участок) в двух колонках, выровненные названия/ответы; на узком — одна. Заключение сверху, длинным комментариям/фото хватает ширины. Не растягивать каждый короткий ответ на всю страницу.

Проблему выделять локально и понятной подписью. false не универсальный признак проблемы: проверить источник существующей оценки, сохранить смысл чек-листа. Данные и процесс осмотра не переписывать.

## R9. Цена, торг и рынок

Панель имеет две смысловые части: слева заметная рабочая цена, выровненные «Продавец / Наше предложение / Согласовано» и переход в переговоры; справа группа, ₽/сот., медиана/средняя/тест спроса и число участников. Без группы явно сообщить об отсутствии сравнения; при нескольких показать одну и дать видимый доступ к другим. Не менять расчёт и не выдавать цену проданного объявления за подтверждённую цену сделки.

## R10. Входящие: фильтры, медиана, выбор и уведомления

- Таблица — основная область. Фильтры компактной сеткой: пары «Цена от–до», «Цена за сотку от–до», «Площадь от–до» вместе.
- Условие «В медиане: Все / Учитываются / Не учитываются». Не путать с автоматическим включением новых объявлений.
- «Применить / Сбросить / Сохранить фильтр» рядом. Название, группа и автоматическое включение новых — в небольшом окне сохранения/редактирования, не постоянная анкета посреди отбора. Если группа требуется, понятно предложить её выбрать.
- Короткие пояснения вместо абзацев; дополнительные — в подсказках. Применение временных условий не меняет незаметно общий сохранённый фильтр.
- Массовое включение убрать из формы фильтров. Действия появляются при явном выборе строк и показывают количество. Выбор страницы и всех результатов различим; после «все» можно снять отдельные строки, счётчик и сервер учитывают исключения. Не сломать ExcludedIds.
- Сортировка в заголовках, без дублирующих кнопок. Удобные чекбоксы, узкая колонка выбора, достаточная ширина объявления, без гигантских пустых строк.
- Одиночная смена медианы: успех виден по переключателю; ошибка возвращает достоверное состояние с понятной причиной. Никаких «Всего:1, Изменено:1, Уже имели:0». Массовая операция — короткий итог и только реальные исключения.

Сохранить бизнес-правила: единая отметка для объявления и всех групп; ручные исключения не возвращать неявно; проданное допустимо, дубль/фейк/снятое исключены; старые период/тип/цена не ограничивают скрыто отмеченную выборку. Не сбрасывать текущие отметки: «изначально выключены» относилось к первоначальному внедрению.

## R11. Взять в работу за одно нажатие

«Взять в работу» создаёт объект на текущего сотрудника, после успеха закрывает панель, обновляет список, показывает «Объект взят в работу» со ссылкой «Открыть». Не переходить в карточку автоматически. Убрать окно выбора «Создать PropertyCase»/существующего объекта и подтверждение.

Последнее прямое уточнение владельца: в нижнем блоке панели объявления только одна кнопка «Взять в работу». Убрать из этого блока передачу сотруднику, оба связывания и классификационные действия. Для уже связанного объявления — текст состояния без повторного создания. Предыдущая формулировка об отдельных действиях в этом блоке отменена.

На ошибке панель остаётся и показывает причину. Повтор не создаёт дубль. Уже связанный объект не пересоздаётся и ответственный не меняется молча. Сохранить работу с подтверждённой группой источников.

Для «Взять в работу» действует последнее прямое требование владельца: закрыть панель и остаться в списке, без автоматического открытия следующего объявления. Существующую настройку «После решения открыть следующее объявление» для других решений не удалять и не менять молча; её подпись/область действия не должны обещать переход после взятия в работу.

## R12. Сравнение дублей и фотографии

Закрепить заголовок/закрытие и нижний блок причин/действий внутри окна. Прокручивается содержимое, последняя строка не перекрыта footer. Причины компактны, не занимают половину небольшого окна.

У обоих объявлений независимые галереи: стрелки, счётчик, крупное открытие. Для одного фото не показывать бессмысленные стрелки, для отсутствующего — понятную заглушку.

«Совпала фотография» подкрепляется конкретной парой миниатюр с крупным сравнением. Несколько пар можно листать. Если пара достоверно известна, первоначально показывать её в галереях. Для сходства писать «Похожие фотографии», для точного совпадения — соответствующий точный текст. Не подставлять первые фото вместо доказательств.

Если конкретная пара сейчас не сохраняется, сообщить о нужной технической доработке до изменения хранения. Старые записи без доказательств показывать честно, не обещать неизвестную пару. Приёмка: длинные описания, разные количества фото, отсутствие фото, одна/несколько доказательных пар, доступность действий без прокрутки до конца.

## Порядок работы и расход ресурсов

1. Узкий аудит hotfix и R1–R12: что уже есть, что скрыто, где нужна функциональная правка. Сразу обозначить возможные модельные вопросы R2/R3/R12 и минимальное решение.
2. Общие примитивы ввода/форматирования и сохранение.
3. Общение → задача → результат/файлы.
4. Проверки, ленты, осмотр, цены.
5. Входящие, фильтры, взятие, дубли.
6. Адресная проверка и итоговый отчёт.

Одна задача, без новых агентов и широких архитектурных переделок. Не гонять полный suite на каждый CSS-штрих. Не повторять одинаково неудачные попытки: при понятной проблеме среды/доступа сразу сообщить, что нужно от владельца. Не делать широкую замену числовых полей без различения денег, измерений и идентификаторов.

## Проверки и результат для владельца

Владелец разрешил осмысленный просмотр в браузере для визуальной доработки. Это не разрешение полного E2E, нагрузочных обходов и заполнения его БД тестовыми данными.

- После связных блоков адресно проверить изменённые экраны; финально полный экран и узкую боковую панель. Ориентиры 1440 и 1920 px, перестроение около 1024 px и zoom 125%; не перемножать все варианты без причины.
- Для сохранений использовать отдельную безопасную тестовую среду. Если её нельзя быстро поднять без вмешательства в пользовательскую — сообщить, не менять окружение втихую.
- Проверить ввод/вставку/редактирование, сохранение и повторное открытие, файл/картинку, завершение с результатом и без, ссылки, date-only, ошибку сохранения, повторный запрос.
- Визуально: пустые/заполненные формы, длинные тексты, несколько файлов, ошибки/loading, отступы, выравнивание, фото и footer сравнения. Не ограничиваться идеальными короткими данными.
- Сборка после связного изменения; целевые тесты значимых изменённых контрактов, а не декоративной разметки. Существующий подход к PostgreSQL/правам сохранить. Не подменять проверку изоляции моками. Не повторять успешные проверки без новых изменений/оснований.
- Не объявлять незапущенные проверки успешными. Несколько репрезентативных скриншотов «после», не сотни кадров. Сборка не является визуальной приёмкой.

Сдать короткий отчёт по R1–R12: что изменено, как проверено, что не подтверждено/заблокировано. Точные рабочая папка/ветка, статус hotfix, commit если разрешён, согласованные изменения хранения, пути скриншотов и шаги ручной приёмки. Не скрывать незавершённые пункты за общим «готово».

Результат — исправленное приложение в существующем стиле с подтверждёнными основными сценариями. Пользовательский сервер обновлять только по отдельному запросу после отчёта.
