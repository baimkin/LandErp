# ADR-001 — Платформа и версии Land ERP

**Статус:** Принято  
**Дата:** 6 сентября 2026 года  
**Владелец решения:** владелец продукта  
**Затрагивает:** Server, Worker, Agent, тесты, CI/CD и документацию

## 1. Решение

Для нового репозитория предлагается использовать:

- C# 14;
- .NET 10 LTS;
- ASP.NET Core 10;
- Blazor Web App;
- EF Core 10;
- совместимую основную версию `Npgsql.EntityFrameworkCore.PostgreSQL`;
- PostgreSQL 18 на актуальном minor-релизе;
- Microsoft.Playwright для локального агента и E2E-тестов;
- TypeScript только в изолированных браузерных и сложных UI-модулях.

PostGIS предусматривается инфраструктурой, но не становится обязательной
зависимостью первого вертикального среза.

Первая выпускаемая и тестируемая среда `LandErp.Agent` — Windows x64. Общая
логика, контракты, браузерный адаптер и outbox остаются кроссплатформенными там,
где это не добавляет отдельной эксплуатационной сложности. Интеграции с
хранилищем секретов, автозапуском, путями и установщиком изолируются за
ОС-специфичными интерфейсами. Поддержка Linux/macOS не входит в первый релиз.

Версии SDK и пакетов закрепляются в репозитории. Их major-обновление выполняется
отдельной задачей и не смешивается с продуктовой фичей.

## 2. Контекст

Первоначально рассматривались C# 13, .NET 9 и EF Core 9. На дату решения .NET 9
находится в завершающей фазе поддержки, которая заканчивается 10 ноября 2026 года.
.NET 10 является LTS и поддерживается до 14 ноября 2028 года. Для проекта, который
только начинает разработку, старт на .NET 9 почти сразу создаёт обязательную
миграцию платформы.

PostgreSQL 18 поддерживается до ноября 2030 года и соответствует исходному выбору.

## 3. Рассмотренные варианты

### Вариант A — .NET 10 LTS

Преимущества:

- более длинный срок поддержки;
- отсутствие срочной миграции сразу после запуска;
- согласованные major-версии ASP.NET Core и EF Core;
- подходящая основа для длительной ERP-разработки.

Недостатки:

- необходимо проверить готовность всех выбранных библиотек;
- команда использует C# 14 вместо первоначально выбранного C# 13;
- возможны различия с уже существующими внутренними заготовками на .NET 9.

### Вариант B — временный старт на .NET 9

Преимущества:

- полное соответствие первоначальному выбору;
- возможное повторное использование существующих наработок.

Недостатки:

- окончание поддержки практически в начале проекта;
- обязательная ранняя миграция;
- двойное тестирование инфраструктуры и агентских приложений;
- риск отложить обновление и остаться на неподдерживаемой версии.

### Вариант C — другая LTS-платформа

Не рассматривается без отдельной бизнес-причины, так как команда уже выбрала C#,
Blazor и PostgreSQL, а генеральный план строится вокруг этой экосистемы.

## 4. Последствия решения

### Положительные

- новый код создаётся на поддерживаемой LTS-основе;
- Server, Worker и Agent используют одну major-версию .NET;
- обновления платформы можно планировать, а не выполнять аварийно;
- примеры кода в планах фич имеют единую базу.

### Отрицательные и обязательства

- центральное управление версиями обязательно;
- CI должен проверять фактическую версию SDK;
- ежемесячные patch-обновления проходят контролируемую проверку;
- каждая новая библиотека проверяется на совместимость и лицензию;
- агентский протокол не должен зависеть от одновременного обновления всех машин.

## 5. Правила закрепления версий

- SDK фиксируется через `global.json` с осознанной политикой roll-forward.
- Общие версии NuGet-пакетов фиксируются централизованно.
- Центральная политика сборки задаёт nullable, analyzers и warnings.
- Плавающие версии и wildcard запрещены.
- ASP.NET Core, EF Core и Npgsql не обновляются независимо без проверки матрицы
  совместимости.
- PostgreSQL major закрепляется инфраструктурой; minor поддерживается актуальным.
- Версия Playwright-пакета и установленных браузеров обновляется согласованно.
- Версия Agent и минимально совместимая версия API видны серверу.

## 6. Эталонные конфигурационные примеры

Примеры ниже иллюстрируют требуемый стиль. Точные patch-версии определяются при
создании репозитория и не копируются из документа без проверки.

### 6.1. Закрепление SDK

```json
{
  "sdk": {
    "version": "10.0.x",
    "rollForward": "latestPatch",
    "allowPrerelease": false
  }
}
```

При создании реального `global.json` вместо `10.0.x` указывается существующая
проверенная полная версия SDK.

### 6.2. Общие параметры проектов

```xml
<Project>
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
    <LangVersion>14.0</LangVersion>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <AnalysisLevel>latest-recommended</AnalysisLevel>
  </PropertyGroup>
</Project>
```

## 7. Проверка совместимости до начала реализации

- создать минимальные Server, Worker и Agent;
- собрать их закреплённым SDK;
- проверить подключение EF Core/Npgsql к PostgreSQL 18;
- выполнить создание и откат тестовой миграции;
- запустить Playwright Chromium на Windows x64;
- проверить Blazor Web App в поддерживаемых браузерах;
- подтвердить работу Testcontainers в CI;
- проверить лицензии и поддержку библиотек первой волны.

## 8. Критерии исполнения решения

Решение считается технически подтверждённым, когда:

- определены полные patch-версии для начального commit;
- proof-of-concept совместимости зелёный;
- Playwright и локальный outbox проверены на Windows x64;
- в `clinerules.txt` и генеральном плане нет противоречащего активного стека.

## 9. Если выбран .NET 9

Если владелец осознанно выбирает .NET 9:

- этот ADR помечается `Отклонено` или заменяется новым;
- сразу создаётся обязательный план миграции на .NET 10;
- фиксируется дата завершения миграции до окончания поддержки;
- примеры планов используют только C# 13 и совместимые пакеты;
- фича не может попутно выполнить миграцию платформы.

6 сентября 2026 года владелец продукта принял вариант `.NET 10 LTS / C# 14 /

фиксируются bootstrap-задачей после проверки совместимости.
