# 01 — Входящие объявления

## Назначение

Первичный отбор **входящих предложений по объектам**, независимо от того, откуда они пришли. Это отдельный экран до очереди закупки.

Источником может быть Avito, Cian, Telegram, ручной ввод сотрудника, знакомый, агент/риелтор, прямой контакт собственника или будущая интеграция.

Главный объект экрана — нейтральный входящий элемент Catalog. Текущая production-сущность может временно называться `Listing`, но архитектурно это не должно означать «только объявление marketplace». `PropertyCase` на этом этапе может ещё не существовать.

Архитектурная граница и обязательная серверная коррекция зафиксированы в `docs/03-active/P0_CATALOG_PROCUREMENT_BOUNDARY.md`.

## Основной сценарий

Менеджер открывает входящее предложение, просматривает доступные данные и проходит короткий чек-лист:

- цена;
- площадь;
- локация;
- пропорции участка;
- категория / ВРИ;
- подъезд / техническое состояние.

После просмотра возможны действия:

- `Не подходит` → выбрать причины и отправить в архив первичного отбора;
- `Мониторинг цены` → указать интересующую цену предложения и/или цену за сотку; при выполнении любого заполненного условия элемент возвращается во входящие;
- `Взять в работу` → создать новый `PropertyCase` либо связать входящий элемент с уже существующим PropertyCase; входящий элемент сохраняется как источник данных, а дальнейшая работа идёт в Procurement.

`Взять в работу` не превращает Catalog item в PropertyCase и не переносит владение жизненным циклом в Catalog. После создания кейса закупочный процесс должен жить самостоятельно.

## Ручное добавление

На странице требуется действие `+ Добавить объявление / предложение`.

Для ручного источника достаточно минимальных известных данных:

- источник (`Telegram`, `Знакомый`, `Агент`, `Другое` и т.п.);
- название/локация;
- цена при наличии;
- площадь при наличии;
- ссылка при наличии;
- кадастровый номер или другие известные сведения при наличии;
- комментарий.

`ExternalId` и URL для ручного элемента не обязательны. Такой элемент попадает в тот же список входящих и проходит тот же первичный отбор, что и результат Avito/Cian parser.

Не создавать фиктивные Collector Agent/Job/Observation для ручных данных.

## Другие автоматические источники

В будущем мониторинг Telegram-групп или иные интеграции должны добавлять элементы в **тот же Catalog**, а не создавать отдельную закупочную сущность.

Интеграция отвечает только за ingestion/provenance. Решение `Взять в работу` остаётся границей между внешним входящим потоком и внутренним `PropertyCase`.

Catalog source classification должна принадлежать серверной модели, а не быть ограничена enum Collector Contract `Avito/Cian`.

## Отдельные классификации входящего элемента

Это не пункты чек-листа:

- `Дубль` — связать/сопоставить с существующим Catalog item или PropertyCase, не теряя источник и историю;
- `Фейк` — исключить из рабочего отбора как недостоверное предложение с причиной;
- `Снято` — исходное объявление больше не опубликовано, если источник поддерживает такой статус. Само по себе не означает продажу объекта;
- `Продано` — подтверждённый человеком факт о реальном объекте. Фиксируются дата, источник подтверждения и, если известна, цена сделки.

Данные о подтверждённых продажах в будущем могут использоваться для анализа спроса, предложения, экспозиции и рыночных цен.

## Что показывает список

Основные поля по мере доступности: объект/локация, источник, внешний ID если есть, цена, цена за сотку, площадь, категория/ВРИ, причина появления во входящих, полнота данных, время получения/последнего наблюдения.

Для parser sources дополнительно можно показывать поисковую конфигурацию и revision/observation status. Для Telegram/manual/referral эти технические поля не требуются.

Рабочие представления: новые, изменение цены, возможный дубль, неполные данные, возврат из мониторинга.

### Состояние просмотра и KPI

`Новые` — общая для организации очередь, а не персональный unread каждого менеджера. Входящий элемент считается новым, пока ни один сотрудник с доступом к очереди не открыл его подробную карточку. Первое подробное открытие фиксирует `CatalogEventKind.ReviewStarted`; каждое фактическое открытие отдельно пишется в Audit с пользователем и временем. Дополнительной кнопки «взять на разбор» нет.

Верхние KPI `Новые`, `Цена изменилась`, `Не хватает данных` и `Обработано сегодня` являются рабочими фильтрами. Клик по KPI открывает полный соответствующий сегмент и сбрасывает остальные фильтры, чтобы число в карточке совпадало с набором строк.

`Обработано сегодня` считается по календарному дню бизнес-таймзоны и включает уникальные Catalog items, по которым за день было принято решение первичного отбора: классификация, постановка на мониторинг, возобновление связанного PropertyCase или подтверждённая связь с PropertyCase через «Взять в работу». Простое открытие/просмотр в обработанные не входит.

При source-изменении цены новое событие хранит структурированные значения `PreviousObservedPrice → ObservedPrice` и соответствующую цену за сотку. В строке очереди и истории пользователь видит не только факт изменения, но и `было → стало`, абсолютную разницу в ₽ и процент. Старые события без previous-value продолжают отображаться в прежнем текстовом формате.

`Возможный дубль` основан на persisted duplicate-candidate model. Matching использует объяснимые признаки: извлечённый кадастровый номер, номер участка/КП при наличии, нормализованную похожесть описаний, площадь, локацию, продавца, цену и perceptual hash фотографий как сильный сигнал, устойчивый к разным URL, ресайзу и JPEG-сжатию. Разные уверенно извлечённые кадастровые номера или разные явно указанные номера участков исключают автоматического кандидата, даже если рекламный текст похож.

Кандидат хранится со статусом `Pending / Confirmed / Rejected`. Решение `Не дубль` сохраняется и предотвращает повторное предложение той же пары. Подтверждение переводит текущее входящее предложение в `Duplicate`, но не удаляет ни один источник. Кадастровый номер автоматически извлекается из заголовка/локации/описания, если найден ровно один уверенный номер. Фотографии обрабатываются фоновым Worker: исходные файлы в БД не сохраняются, хранится только компактный pHash. Совпавшие фото показываются менеджеру как объяснимая причина кандидата. Часто встречающиеся типовые изображения исключаются из усиления дубля. Пороговые значения доступны администратору в `/settings/duplicates` и применяются без перезапуска.

## Граница экрана

На этой странице нет полноценного Due Diligence, переговоров, задач закупки и управления приобретённым объектом.

После `Взять в работу` дальнейшая работа идёт через самостоятельный `PropertyCase` и очередь закупки. Изменение или исчезновение внешнего источника не должно закрывать или удалять PropertyCase.
