# FP-011 — Очередь заданий и локальные агенты

**Версия:** 0.2  
**Статус:** Черновик  
**Владелец:** администратор сбора / технический владелец  
**Модули:** Collection, Administration; приложение LandErp.Agent  
**Зависимости:** ADR-001, FP-001, FP-002, FP-010, ADR-003, ADR-004  
**Блокирует:** FP-012 и масштабирование сбора

## 1. Решение

Реализовать сохраняемую очередь CollectionTask в PostgreSQL и отдельное локальное
Agent-приложение. Agent получает подходящее задание с ограниченной арендой,
поддерживает heartbeat, выполняет браузерную операцию и сначала сохраняет результат
в локальный SQLite outbox. Сервер принимает результат идемпотентно. Потеря сети,
перезапуск Agent и истечение аренды не теряют уже извлечённые данные и не требуют
прямого доступа компьютера к PostgreSQL.

## 2. Ценность

- 3–5 компьютеров работают как единый управляемый пул.
- Сервер определяет, что, когда и с каким приоритетом выполнять.
- Большой первичный сбор не блокирует новые объявления и объекты в работе.
- Сбой одного компьютера не останавливает очередь.
- Повторная доставка не создаёт дубли наблюдений.
- Администратор может pause, drain или revoke устройство.

## 3. Границы

### Входит

- CollectionTask и PostgreSQL-очередь;
- приоритеты P0–P4;
- lease, heartbeat, completion, retry и dead-letter;
- регистрация Agent через FP-002;
- capabilities и совместимость версии;
- Agent polling с контролируемым backoff;
- локальный SQLite outbox;
- pause/drain/revoke;
- безопасная диагностика;
- серверные и агентские метрики;
- обновляемый Agent contract;
- один Agent и последующее подключение 3–5 машин.

### Не входит

- конкретные селекторы Авито;
- автоматический обход CAPTCHA;
- удалённое управление рабочим столом;
- прямой push заданий на Agent;
- внешний message broker;
- автоматическое самообновление до выбора доверенного канала;
- хранение cookies и браузерных профилей на сервере;
- массовая отправка сообщений продавцам.

## 4. Типы заданий первой очереди

- `CollectSearchResults` — пройти поисковую выдачу;
- `CollectListingDetails` — открыть подробную карточку;
- `CheckListingAvailability` — проверить доступность объекта по прямой ссылке;
- `ValidateAgentSession` — контролируемая диагностическая операция без бизнес-результата.

Новый тип задания добавляется версионированно и требует capability Agent.

## 5. Приоритеты

| Приоритет | Назначение | Пример |
|---|---|---|
| P0 | Ручная критичная операция | Администратор повторяет проблемную карточку |
| P1 | Новые объявления | Свежая выдача активного поиска |
| P2 | Объекты в работе и ценовые сигналы | Интересный объект проверяется по прямой ссылке |
| P3 | Подробные карточки новых ID | Обогащение после выдачи |
| P4 | Первичное наполнение и контрольная сверка | Глубокий фоновый проход |

Очередь должна предотвращать starvation P4: после настраиваемого окна часть
ресурса выделяется фоновым задачам.

## 6. Состояния задания

| Состояние | Смысл |
|---|---|
| Pending | Готово к выдаче после `AvailableAt` |
| Leased | Выдано Agent до `LeaseExpiresAt` |
| Running | Agent подтвердил начало; аренда активна |
| Completed | Результат принят идемпотентно |
| RetryScheduled | Попытка завершилась временной ошибкой |
| AttentionRequired | Требуется решение человека |
| Cancelled | Отменено сервером до завершения |
| DeadLetter | Автоматические попытки исчерпаны |

Истёкшая аренда не меняет бизнес-результат сама по себе. Reaper переводит задачу
в Pending/RetryScheduled атомарно, если completion ещё не принят.

## 7. Состояния Agent

- Offline;
- Idle;
- Busy;
- Paused;
- Draining;
- AttentionRequired;
- Revoked.

Agent сообщает наблюдаемое состояние, но сервер вычисляет итоговое состояние с
учётом heartbeat, отзыва и активной аренды.

## 8. Основной поток

1. Worker создаёт CollectionTask с deduplication key.
2. Agent аутентифицируется и отправляет heartbeat/capabilities.
3. Agent запрашивает одно подходящее задание.
4. Сервер атомарно выбирает задачу и создаёт lease.
5. Agent подтверждает начало и выполняет действие.
6. Результат записывается в локальный outbox до сетевой отправки.
7. Agent отправляет результат с TaskId, LeaseId и ResultId.
8. Сервер проверяет credential, тип, размер, lease и идемпотентность.
9. В одной транзакции сохраняются результат/событие и completion.
10. Сервер подтверждает ResultId.
11. Agent удаляет outbox-запись только после подтверждения.

## 9. Аренда

- Lease создаётся атомарно вместе с переходом Pending → Leased.
- Выбор учитывает priority, AvailableAt, capability и ограничения источника.
- LeaseId уникален для каждой выдачи задачи.
- Продление ограничено максимальной общей длительностью.
- Старый Agent не может продлить истёкшую или заменённую аренду.
- Completion со старым LeaseId может быть принят как запоздавший результат только
  по явной политике и никогда не откатывает более новое наблюдение.
- Отмена проверяется Agent между безопасными шагами.

## 10. Идемпотентность и дубли

### Создание задания

Deduplication key определяется типом:

- SearchRun + page/cursor + revision;
- Listing + desired detail level + observation window;
- manual command id.

Повтор команды возвращает существующую активную/завершённую задачу по политике.

### Приём результата

`ResultId` генерируется Agent до первой отправки и сохраняется в SQLite. Сервер
имеет уникальность AgentId + ResultId. Повтор возвращает прежнее подтверждение.

### Запоздавший результат

Он может дополнить историю, но актуальное представление вычисляется по времени
наблюдения, времени приёма и правилам качества; порядок HTTP-доставки не равен
порядку фактов.

## 11. Повторы и классификация ошибок

| Категория | Пример | Действие |
|---|---|---|
| TransientNetwork | Нет связи с сервером | Outbox и exponential backoff с jitter |
| SourceTemporary | Таймаут/5xx площадки | RetryScheduled с лимитом |
| RateLimited | Явный лимит источника | Увеличенная пауза и снижение нагрузки |
| AuthenticationRequired | Истекла сессия источника | AttentionRequired |
| CaptchaDetected | CAPTCHA | AttentionRequired, без обхода |
| PageStructureUnknown | Неизвестный тип страницы | AttentionRequired и безопасная диагностика |
| ExtractionQualityFailure | Нет обязательных полей | Остановка/инцидент по порогу |
| PermanentInput | Невалидный URL/тип задания | DeadLetter без бессмысленных повторов |
| AgentInternal | Ошибка браузера/процесса | Ограниченный retry, затем диагностика |

Политика повторов хранится сервером и версионируется; Agent не изобретает
бесконечные повторы самостоятельно.

## 12. Capabilities и совместимость

Agent сообщает:

- AgentVersion;
- ContractVersion range;
- OS и architecture;
- установленные браузеры;
- поддерживаемые SourceCode;
- типы заданий и версии adapter;
- доступность headed/headless по политике;
- статус браузерного профиля без передачи секретов.

Первая поддерживаемая комбинация — Windows x64 и Chromium, установленный
Playwright. Общие контракты, выполнение заданий, адаптер источника и SQLite
outbox не зависят от Windows API. За интерфейсами изолируются защищённое
хранилище credential, автозапуск/служба, пути и установщик. Linux/macOS могут
быть добавлены без изменения серверного протокола, но не входят в матрицу первого
релиза.

Сервер выдаёт только совместимое задание. Если минимальная версия повышена, старый
Agent остаётся видимым, но не получает несовместимую работу.

## 13. Локальный SQLite outbox

Минимальные поля:

- ResultId;
- TaskId;
- LeaseId;
- PayloadVersion;
- payload или ссылка на локальный пакет;
- CreatedAt;
- AttemptCount;
- NextAttemptAt;
- LastErrorCode;
- подтверждение сервера.

Outbox защищается от параллельной отправки одной записи. Локальные диагностические
файлы имеют лимит и очистку. Cookies не складываются в outbox.

## 14. Данные сервера

### CollectionTask

- Id, OrganizationId;
- TaskType и PayloadVersion;
- Priority;
- SourceCode;
- Payload;
- State;
- AvailableAt;
- DeduplicationKey;
- AttemptCount/MaxAttempts;
- CurrentLeaseId optional;
- CreatedAt/CompletedAt;
- CorrelationId;
- Parent SearchRun/Listing references.

### TaskLease

- Id, TaskId, AgentId;
- LeasedAt, ExpiresAt, LastHeartbeatAt;
- LeaseVersion;
- EndReason;
- completed/replaced timestamps.

### AgentExecutionResult

- Id/ResultId;
- TaskId, LeaseId, AgentId;
- ContractVersion;
- StartedAt/ObservedAt/FinishedAt/ReceivedAt;
- OutcomeCode;
- Payload location/hash/size;
- diagnostic summary;
- accepted/rejected reason.

### 16.3. Атомарная идея lease в PostgreSQL

```sql
WITH candidate AS (
    SELECT task_id
    FROM collection.collection_task
    WHERE state = 'pending'
      AND available_at <= now()
    ORDER BY priority, available_at, task_id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE collection.collection_task AS task
SET state = 'leased',
    current_lease_id = @lease_id
FROM candidate
WHERE task.task_id = candidate.task_id
RETURNING task.*;
```

Реальная команда дополнительно фильтрует source limits и capabilities и создаёт
TaskLease в той же транзакции.

## 17. Административный UI

### Список Agent

- имя и ID устройства;
- состояние и время последнего heartbeat;
- версия приложения и adapter;
- capabilities;
- активная задача и возраст;
- ошибки/AttentionRequired;
- pause, drain, revoke.

### Очередь

- глубина по priority/type/source;
- возраст старейшей задачи;
- Pending/Leased/Retry/Attention/DeadLetter;
- фильтр по SearchRun, Listing, Agent и correlation ID;
- повтор dead-letter только как явная команда с причиной;
- просмотр безопасной диагностики.

Опасные действия требуют подтверждения и аудита.

## 18. Безопасность

- Agent API использует отдельную authentication scheme.
- Agent видит только собственную identity и выданную задачу.
- Payload не содержит connection string и лишние бизнес-данные.
- URL и параметры задачи проходят серверную валидацию.
- Размер результата ограничен до десериализации больших данных.
- JSON/HTML считается недоверенным.
- Credential ротируется и отзывается.
- Логи не содержат cookies, auth headers и полный HTML.
- Команды администрирования защищены именованными permissions.

## 19. Наблюдаемость

Метрики:

- queue depth/age по типу и priority;
- lease success, expiration и extension;
- task duration и outcome;
- retry/dead-letter/attention;
- Agent online/version/capabilities;
- outbox depth/age локально;
- duplicate result acceptance;
- source rate limit и CAPTCHA events.

Трасса связывает SearchRun → Task → Lease → Agent execution → Result → Observation.

## 20. Тестирование

| Уровень | Обязательные случаи |
|---|---|
| Unit | priority, capability match, retry classification, lease expiry, backoff |
| Integration | конкурентный lease через SKIP LOCKED, уникальность ResultId, reaper, транзакция completion |
| Contract | Server и две соседние версии Agent contract |
| Resilience | потеря сети до/после отправки, crash Agent, crash Server, повтор completion |
| Security | чужой AgentId, revoked credential, oversized payload, Agent против user API |
| E2E system | создать task → lease → outbox → complete → подтверждение → очистка |

Нагрузочный тест первой версии проверяет 3–5 Agent, а не искусственные тысячи.

## 21. Вертикальные этапы

1. Один Agent регистрируется и отправляет heartbeat.
2. Сервер создаёт одну тестовую Task, Agent арендует и завершает её.
3. Добавляется SQLite outbox и повтор после потери сети.
4. Добавляются lease expiry/reaper и второй Agent.
5. Добавляются priority, capabilities, pause/drain/revoke.
6. Добавляются retry, attention, dead-letter и административный UI.
7. Проверяется пул 3–5 компьютеров на безопасной тестовой нагрузке.

## 22. Развёртывание и обновление

- Agent распространяется подписанным/проверяемым artifact.
- Конфигурация сервера отделена от локального browser profile.
- Обновление сначала проходит на одном Agent.
- Server сохраняет совместимость как минимум с текущей и предыдущей допустимой
  версией контракта в согласованном окне.
- Agent в Draining завершает работу перед обновлением.
- Схема SQLite мигрируется с резервным копированием outbox.
- Неудачное обновление не удаляет недоставленные результаты.

## 23. Definition of Ready

- утверждены ADR-003 и ADR-004;
- Windows x64 подтверждена как целевая ОС первого Agent;
- известен безопасный способ хранения credential;
- согласованы lease duration и heartbeat interval для пилота;
- определены типы заданий и начальные priorities;
- согласован максимальный размер payload;
- определён режим установки Playwright/browser;
- доступен тестовый компьютер, похожий на production Agent.

## 24. Definition of Done

- один и затем 3–5 Agent работают без прямого доступа к БД;
- конкурентный lease не выдаёт одну задачу двум Agent одновременно;
- crash и сеть не теряют outbox;
- повторный result не создаёт дубль;
- запоздавший result не откатывает более новое состояние;
- pause/drain/revoke работают и аудируются;
- CAPTCHA/unknown page ведут в AttentionRequired;
- очередь имеет метрики и административную диагностику;
- совместимость контрактов проверена автоматически;
- security/resilience/E2E tests зелёные.
