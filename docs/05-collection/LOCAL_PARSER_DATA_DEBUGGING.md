# Local Parser: нормализованные данные и отладка результатов

**Статус:** локальный этап Parser Agent  
**Область:** `LandErp.ParserSpike` и `LandErp.ParserSpike.Desktop`  
**Server / Collector V1:** вне этой задачи, не изменяются.

## 1. Цель

Локальный Parser должен сначала доказать качество извлечения данных на реальных источниках, а уже затем расширять серверный контракт. Особенности Cian, Avito и будущих источников остаются внутри source-adapter; локальное наблюдение использует универсальные поля.

## 2. Универсальные локальные поля

Помимо существующих ID, URL, цены, площади, адреса, описания, продавца и фото, локальное наблюдение хранит:

- `CadastralNumber` — кадастровый номер, только если источник явно его отдал;
- `SourcePublishedAtUtc` — время публикации/добавления на площадке, если есть надёжное структурированное значение;
- `Latitude` / `Longitude` — обычные географические координаты WGS84 (EPSG:4326);
- `DeclaredLandTypes[]` — все типы/назначения участка, которые площадка отдала структурированно;
- `InferredLandTypes[]` — все типы, найденные в названии и описании локальным классификатором;
- `LandTypeConflict` — диагностический признак несовпадения непустых наборов declared/inferred;
- `SourceCountHint` — подсказка площадки об общем количестве результатов поиска на уровне прохода.

Ни одно структурированное значение площадки не считается юридически подтверждённым фактом. Это только «заявлено в объявлении». Документально подтверждённый статус земли остаётся отдельной будущей ERP-семантикой.

## 3. Тип участка

Алгоритм не выбирает одну «истину»:

1. Если площадка отдаёт отдельное структурированное значение — оно нормализуется в `DeclaredLandTypes[]`.
2. Независимо от этого Title + Description анализируются в `InferredLandTypes[]`.
3. Для Avito и других источников без структурированного типа declared остаётся пустым, а текстовый fallback продолжает работать.
4. Если оба массива непустые и отличаются, UI показывает конфликт и отдельно:
   - что дополнительно найдено в тексте;
   - что заявлено источником, но в тексте не найдено.
5. Допускается несколько значений одновременно: например `ИЖС, ЛПХ`.

## 4. Cian: structured whitelist

Cian adapter читает из `window._cianConfig['frontend-serp'] -> initialState -> results.offers` только ограниченный whitelist, привязанный к публичной карточке по Cian ID:

- цена как fallback;
- площадь и единица площади;
- land status;
- описание;
- публичный адрес;
- WGS84 coordinates;
- `addedTimestamp`;
- кадастровый номер;
- полные URL фотографий;
- `results.totalOffers`.

DOM остаётся fallback и источником видимых данных карточки.

Не извлекаются и не сохраняются:

- позиция объявления в выдаче;
- premium / продвижение;
- Cian badges;
- внутренние Cian geo IDs;
- дополнительные характеристики/контакты продавца;
- телефоны;
- session/profile state;
- служебная конфигурация и технические поля embedded JSON;
- сырой embedded JSON целиком.

Если Cian помечает `isNeedHideExactAddress=true`, точный `geo.userInput` не используется: сохраняется только публично видимый адрес из DOM.

## 5. Polygon search и пагинация

Для Cian идентичность поиска сравнивается семантически:

- `p` не является частью поиска;
- `center`, `zoom`, `polygon_name` считаются presentation-only;
- числовые индексы массивов (`[0]`, `[1]` и т.д.) нормализуются;
- смена `noginsk.cian.ru` на `www.cian.ru` допустима;
- координаты `in_polygon`, bbox и бизнес-фильтры остаются частью идентичности и не могут измениться незаметно.

Таким образом канонизация URL самим Cian между страницами не ломает сбор, но изменение реальной области/фильтров по-прежнему отклоняется.

## 6. Просмотр результатов

Вкладка «Результаты» предназначена не только для просмотра, но и для проверки качества адаптера.

Таблица показывает ключевые бизнес-поля и поддерживает фильтры:

- источник;
- поисковая ссылка;
- конкретный запуск;
- предупреждения;
- конфликт типа участка;
- отсутствующая цена;
- отсутствующая площадь;
- отсутствующие координаты;
- отсутствующая дата публикации;
- отсутствующий кадастровый номер.

Карточка объявления имеет два режима:

- **обычный** — бизнес-поля, declared/inferred land types, конфликт, описание, фото, контекст сбора и история изменений;
- **технический** — Presence / Raw / Parsed, adapter version, provenance, warnings и остальные диагностические значения без сырого HTML/embedded JSON.

История сравнивает соседние наблюдения и показывает, какие значимые поля изменились.

## 7. Режим карточки

Настройка «Открывать карточку объявления»:

- **справа в рабочем окне**;
- **в отдельном окне**.

В отдельном режиме существует одно окно просмотра. При выборе другой строки оно обновляется. Если пользователь его закрыл, следующий выбор строки открывает новое окно.

Настройка сохраняется локально.

## 8. Хранение

Новые поля входят в JSON `ListingObservation`, который уже хранится в `local_observations` и `local_listings`. Новые SQL-колонки и миграция SQLite не требуются.

Compatibility локального сбора повышена до adapter generation 2, чтобы старый fresh-cache не подменял новый результат наблюдением без новых полей.

## 9. Что проверять вручную

На реальной polygon-ссылке Cian:

1. первая страница собирается без ошибки;
2. переход 1 → 2 и далее не блокируется из-за канонизации URL;
3. количество видимых карточек и `SourceCountHint` выглядят разумно;
4. площадь/цена/описание/фото совпадают с карточкой;
5. дата источника не подменяется `FirstObservedAt`;
6. координаты выглядят как обычные latitude/longitude;
7. structured land status показывается отдельно от текста;
8. конфликт вроде «заявлено ИЖС, в тексте СНТ» виден;
9. скрытый точный адрес не появляется;
10. переключение строк синхронно обновляет боковую карточку или одно отдельное окно;
11. фильтры качества позволяют быстро найти неполные/сомнительные результаты.

## 10. Следующий отдельный этап

После ручной проверки локального Parser отдельной задачей определяется окончательный Server/Collector contract и перенос только подтверждённых универсальных полей. Текущая задача сознательно не меняет Server, PostgreSQL, Catalog и `LandErp.Collector.Contracts`.
