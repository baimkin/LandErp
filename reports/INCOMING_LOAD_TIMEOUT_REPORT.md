# Анализ загрузки «Входящих» — INCOMING-LOAD-TIMEOUT

Дата: 20.11.2026. Только анализ и диагностические замеры; реализация ускорения
отложена по прямому уточнению владельца. Код приложения, схема, production,
ветка/индекс и работающий preview этим исследованием не изменялись.

## Вывод

Основная обнаруженная проблема — общий динамический count: на каждое открытие,
смену страницы/сортировки/фильтра он повторяет сложные условия всех сохранённых
фильтров во многих агрегатах. Принадлежность зоне при этом многократно выводится
из полной истории observations → jobs → searches → active groups.
Один SQL не означает однократную обработку этих связей.

На синтетической PostgreSQL-базе 25 000 объявлений / 500 000 observations /
50 зон / 50 сохранённых фильтров полное чтение заняло 11.031 с, из них 8.890 с —
SQL общего count. Бounded-чтение строк и их metadata без общего count/facets
заняло 1.009 с. Второй замер НЕ включает точный Total и потому не является
готовой заменой полного контракта или измерением готового исправления.

Рекомендуется сначала исправить форму запросов и отделить страницу от
информационных счётчиков, затем переиспользовать уже рассчитанные счётчики.
Начинать с отдельной таблицы попадания во все пользовательские фильтры,
нового сервиса или постоянного фонового полного пересчёта не требуется.

## Production evidence и граница доказанности

Владелец предоставил результат поиска Event 1101:

- OperationId: 01a1f951-dafb-7209-bf62-431a9dbeeaf8;
- Component IncomingCatalogV2, Action ReloadAsync, Phase Read;
- FailureType InvalidOperationException, DiagnosticCode DB_TIMEOUT;
- InnerFailureType TimeoutException, ElapsedMs 10396;
- /health/live и /health/ready вернули 200.

Доказан timeout на пути чтения. Глобальный EF command timeout действительно
10 секунд (LandErpDbContext.cs:81). Это лимит отдельной команды, не всей страницы:
локальная страница могла успешно загрузиться за 11 с, поскольку самая долгая
команда ещё укладывалась в 10 с. Health не проверяет тяжёлую выборку Incoming.

Production SQL, его execution plan, нагрузка/ожидания и объёмы не получены.
Поэтому нельзя утверждать, что именно исследованный count был единственной
командой, упавшей в указанном incident; блокировки, I/O и конкуренция также
не исключены. Локально доказан тяжёлый путь, согласующийся с симптомами.

## Фактический путь чтения

1. IncomingCatalogV2.ReadAsync (:1451) разрешает доступ, формирует applied filter.
2. IncomingCatalogReadService.ReadAsync (:28–112): повторная проверка доступа,
   чтение/проверка сохранённых фильтров, PrepareAsync, общий count, окно строк,
   справочники активных зон и enabled searches.
3. Если сохранённая страница вышла за TotalPages, UI выполняет полный ReadAsync
   ещё раз с правильным offset. Числа и справочники перечитываются повторно.
4. GroupMarketService.ReadIncomingAsync; при отсутствии выбранной зоны возвращает
   null без расчёта рынка. При выбранной зоне читает settings/участников и
   считает median/average. Его сбой сейчас может оборвать общий page read.
5. В режиме «выбраны все результаты» дополнительно выполняется fresh bulk preview
   с полным серверным отбором и stamp версий. Это не причина обычного первого
   открытия, но может существенно увеличивать последующие чтения.

GoToPageAsync, PageSizeChangedAsync, ToggleSortAsync, изменение source/zone,
среза/режима и debounce текста вызывают ReloadAsync. Обычная навигация страницы
не отделена от пересчёта всех информационных чисел. Пока выполняющийся read не
отменяется токеном: в UI передаётся CancellationToken.None.

Отдельные уже подготовленные QuickDismiss/FastOpenTransfer решают лишние reload
после конкретных действий; первичную загрузку и описанный общий count они
не заменяют. Их накопленные изменения сохранены.

## Где накапливается работа

### Общий count

IncomingCatalogReadService.cs:43–78 строит 12 + P + G предикатов, где P — число
применимых сохранённых фильтров, G — число их групп (включая ungrouped bucket).
Для 50 фильтров в 50 группах это 112 условных агрегатов. В текущем режиме
SavedFilters объединение всех фильтров повторяется в нескольких счётчиках.

IncomingCatalogQuery.CountAsync (:150) агрегирует по organizationItems — всему
каталогу организации; отдельные условия находятся внутри агрегатов. Условия
зоны (:60–74) содержат join истории и активных groups. Планировщик не устраняет
автоматически все повторения этих подзапросов. В локальном EXPLAIN для 50 фильтров
получено 705 SubPlan/InitPlan и 700 узлов, читающих observations.
Это 700 участков одного плана, НЕ 700 сетевых SQL-команд; число фактических loops
для каждого узла не измерялось (EXPLAIN без ANALYZE).

Общий объём работы зависит от размера каталога, глубины истории, количества
фильтров и их сложности. Текстовая классификация типа участка ILIKE по
Title/Description и деление Price/Area повторяются вместе с условиями фильтра.
Сокращение page size само по себе не сокращает этот count.

### Сохранённые фильтры и доступ

IncomingFilterPresetService.ReadForOrganizationAsync (:37–53) читает список,
затем ResolveAsync (:272–305) выполняет SELECT EXISTS active group по каждому
сгруппированному V2 фильтру. Для 50 таких фильтров — 1 + 50 SQL-команд metadata,
не считая разрешения доступа. Legacy V1 с SearchConfigurationId может потребовать
ещё один запрос на фильтр. Проверять те же group/search links можно пакетно
с прежней fail-closed семантикой, без длительного кеширования прав.

Внутри одного UI read доступ разрешается UI, incoming service, preset service
и market service. Каждое разрешение — запрос сотрудника/назначения и settings.
Это вторичный накладной расход, не объяснение 8.9 с count; public authorization
границы нельзя удалять ради ускорения. Возможен внутренний контекст только на
одну операцию после авторизации, без кеша прав на весь Blazor circuit.

### Окно строк и история

Сам список ограничен Skip/Take 25/50/100 до получения metadata; общей загрузки
всех Listing в память для страницы нет. Связанные данные читаются пакетно,
N+1 запроса на каждое объявление здесь не обнаружено.

Однако searchRows (:219–226) забирает все observations для ID страницы,
затем выбирает последнее наблюдение уже в памяти. eventRows (:232–245) также
получает историю SourceChanged/MonitoringTriggered с Message и вычисляет flags
в памяти. Поэтому объём metadata не ограничен числом строк страницы при росте
истории. Последнее наблюдение и булевы flags следует вычислять в PostgreSQL,
возвращая только итог для каждого ID. Историю не удалять и не обрезать.

### Рынок и массовые действия

CatalogMarketParticipants уже сворачивает repeated observations в SQL до
кандидатов по listing/group, потом выбирает представителя подтверждённой группы
источников и считает median/average. Участие определяется IncludeInCalculation
и eligibility. Отдельная стоимость есть при выборе зоны, но при обычном старте
без зоны этот расчёт отсутствует. Менять правила/галочки медианы не требуется.

CatalogBulkSelectionReader использует тот же серверный predicate и свежие версии.
Архивирование/медиана повторно проверяют состав и stamp в транзакции. Кеш
информационных счётчиков не должен становиться источником IDs или подтверждением
количества для таких записей. Полный entity read для preview — отдельная точка
дальнейшей оптимизации проекции Id/Version при сохранении stamp, не первый шаг.

## Локальные замеры текущего кода

Реальный PostgreSQL и runtime роль одноразовой БД, штатные migrations и indexes.
Никакой production БД/внешнего парсинга. Синтетические listing, groups, searches,
jobs и observations; 25 строк страницы, 50 зон, по одному фильтру на зону.
Сложный фильтр добавляет ИЖС, минимальную общую цену и максимум цены за сотку.

## Сравнение способов ускорения

| Подход | Сложность | Эффект / ограничение | Решение |
|---|---|---|---|
| Исправить общие SQL и пакетную metadata | Небольшая–средняя, без новой бизнес-схемы | Убирает повторную историю/OR из агрегатов; полезен и при холодном кеше | Первый шаг |
| Отделить rows + exact Total от tiles/alternative counts/market | Средняя, существующее window-чтение уже есть | Список доступен независимо от необязательных агрегатов; навигация не пересчитывает всё | Первый шаг вместе с SQL |
| Короткий кеш только информационных агрегатов | Небольшая–средняя после разделения | Снижает повторы между действиями/пользователями; не ускоряет первый cache miss сам по себе | Дополнение, не замена SQL |
| Только новые indexes | Маленькая правка, но миграция/серверный rollout | Помогают выбранному plan, не убирают сотни повторных ветвей | Адресно после EXPLAIN |
| Компактная listing↔search membership projection | Средняя, новая таблица + backfill + ingress | Убирает зависимость обычного отбора от глубины истории | Следующий уровень при доказанной необходимости |
| Предрасчёт listing↔каждый пользовательский фильтр | Большая | Потребует пересчёта по всем изменениям, тексту, черновикам и времени | Не начинать с этого |

## Рекомендуемый конкретный пакет без новой таблицы

1. Выделить чтение страницы с точным Total только текущего effective predicate.
   Проверить отдельный WHERE+COUNT(current), а не текущий массив условных count
   по всей организации. Окно/порядок/права/пагинация сохраняются.
2. Перестроить общий count так, чтобы current cohort, его event flags и membership
   не повторялись заново в каждой метрике. Альтернативы считать отдельно от current
   summary; совпадения по group/filter сначала сворачивать по ListingId.
   Кандидат для проверки — небольшое число set-based запросов по подходящим
   строкам вместо одного огромного conditional aggregate. Не заменять это сотней
   последовательных CountAsync по одному фильтру.
3. Пакетно разрешать metadata всех groups/searches сохранённых фильтров.
   Последнее наблюдение и flags страницы вернуть готовыми из SQL.
4. Отрисовывать строки после их чтения, счётчики/рынок — независимо; их ошибка
   показывает «не удалось обновить счётчики», не блокирует готовый список.
   При обновлении можно сохранять последнее число с временем обновления,
   а не показывать временный ноль. Ответ применяется только к своему scope/revision.
5. При page/size/sort не запускать общий пересчёт информационных альтернатив;
   использовать предыдущие числа, отдельный refresh по их сроку актуальности.
   Предлагаемый стартовый предел — 30–60 секунд, с явным временем обновления.
   Кеш ограничить размером/сроком, ключом org + effective criteria + текст + slice
   + выбранный preset/draft + versions зависимостей; page/size/sort для чисел
   исключить. Один выполняющийся расчёт на ключ предотвращает одновременные
   одинаковые запросы. Точные проверки доступа выполняются до использования кеша.
6. Известные собственные изменения обновляют строку/Total сразу; соответствующая
   сводка помечается устаревшей. Внешние изменения видны в информационных числах
   максимум после TTL/явного обновления. Если нужна немедленная межпользовательская
   актуальность, потребуется отдельная надежная инвалидизация — это уже больший
   scope. Нельзя обещать её одним IMemoryCache.Remove в одной UI-команде.
7. Перед записью и bulk action читать реальные данные/версии; число из кеша
   не является подтверждением состава. Смена фильтра, transient draft, архив,
   ProcessedToday и скользящий Age получают правильный отдельный scope/время.

Первый пакет не требует Redis, нового Worker job, новых пакетов или постоянного
хранения результатов фильтров. Таймаут остаётся защитой, его увеличение не
устраняет рост стоимости. При холодном кеше rows + exact Total должны успешно
работать независимо от facet rebuild.

## Что делать с индексами и дальнейшим ростом

В текущих mappings/snapshot уже есть observations(job_id), unique
observations(listing_id, observed_at, content_hash), searches(search_group_id),
jobs(search_id,state), listings(organization_id,changed_at), events(organization_id)
и events(catalog_item_id,recorded_at). Утверждать «индексов нет» неверно.
Для комментариев уже есть GIN(to_tsvector('simple',text)).

После исправления query shape проверить реальные планы. Кандидаты, не готовый
список миграций: covering observations(job_id,listing_id), составной/partial index
listings для текущего org/disposition/order, events для используемых kind/time/id.
ILIKE '%...%' и вычисляемая Price/Area не ускоряются автоматически обычным btree;
новые trigram extensions/поля не нужны без отдельного обоснования и измерения.

Если после первого пакета окно/COUNT(current) всё ещё зависит от большой истории,
следующий простой устойчивый слой — уникальные (organization_id,listing_id,search_id)
с last_observed_at. Ingress upsert выполняется идемпотентно в одной транзакции с
observation; старые данные заполняются backfill с проверкой равенства старому
отбору. Текущая зона выводится через search.SearchGroupId и active group, а не
фиксируется навсегда в этой таблице. Иначе перенос поиска/архив поменяет семантику.
История observations остаётся историей и не удаляется.

Полный предрасчёт произвольных фильтров намного сложнее: изменения цены/площади/
текстов/комментариев, review/disposition/links/duplicates/median, архив/перенос зоны,
версии фильтров, draft/text и границы времени могут менять membership без нового
парсинга. Сумма чисел нескольких пересекающихся фильтров не равна размеру их
объединения. Поэтому этот вариант сейчас не даёт лучшего отношения эффекта к риску.

## Приёмка будущей реализации

- Сравнить старый/новый отбор и все числа на пересекающихся фильтрах/группах,
  SavedFilters union/selected/draft, AllListings, Archive, Participants, New,
  ProcessedToday/Age, incompatible preset и чужой организации.
- Проверить 25/50/100, offset/последнюю страницу после изменения состава, выбор
  всех с исключениями и свежую bulk verification; не заменять её кешем.
- Проверить cold/warm cache, истечение/инвалидизацию, concurrent cache misses,
  ошибку facets при успешной странице, отмену/поздний ответ, архив/новый парсинг.
- На тех же синтетических объёмах и с несколькими пользователями измерить отдельно
  rows, exact Total, metadata, summary/alternatives, market, EF preparation.
  Цель — исчезновение repeated history в плане, устойчивое выполнение каждой
  команды ниже 10 с с запасом; численное SLA согласовать после замеров реализации.
- На production получить безопасные длительности этапов/теги запросов, не SQL,
  тексты объявлений/комментариев или параметры, и выполнить контрольный read.
