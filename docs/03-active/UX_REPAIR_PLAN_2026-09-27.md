Дата: 27.09.2026. Статус: план исправлений, не разрешение начать реализацию.

## Основание и границы

Проверена рабочая копия `C:/Users/user/.codex/worktrees/11de/LandErp`, ветка
`codex/t-01-case-tasks`: F-01–F-03, M-01–M-03, C-01/C-02, T-01/T-02 и

Использованы предоставленные владельцем скриншоты, актуальная разметка, CSS,
компоненты, контракты и адресные пути чтения/записи. Это статический технический
аудит пользовательских сценариев, не полный аудит всех ветвей серверного кода.
Новые сборки, тесты, браузерные сценарии и SQL к пользовательским данным не запускались.
Код, настройки, БД и работающий сервер при этом аудите не изменялись.

Основная проблема: функциональные изменения добавлялись без проверки целой
композиции экрана и без последовательного использования существующего UI-kit.
Переписывание бизнес-системы не требуется. Требуется исправление интерфейса и
нескольких контрактов взаимодействия. Исчезновение задачи пока не локализовано.

Последнее решение владельца: обычный текст + Ctrl+V изображения + прикрепление
изображения/файла. Панели форматирования и конструктор документов не нужны.
Это решение выше прежних требований C-01 о rich-text.

## Подтверждённые находки

1. **Разрушенная таблица.** `incoming-v2-workflow.css:267–275` использует
   `table-layout:fixed` и 35% для первого столбца. В `IncomingCatalogV2.razor:250`
   первым теперь условно добавляется выбор, вторым объявление, третьим медиана.
   Старая нумерация CSS не обновлена. Ширина объявления стала 10%, выбора 35%.
   Длинные адреса переносятся, строки растут. Без права обработки число колонок
   снова другое. Нужны именованные роли колонок, а не очередная перестановка nth-child.
2. **Нельзя снять часть общего выбора.** `IncomingCatalogV2.razor:265` явно
   задаёт `disabled = Busy || allCalculationResults`. Контракт
   `CatalogCalculationSelection` знает только явные ID либо все результаты:
   исключений из всех результатов нет. Только снять disabled недостаточно.
3. **Дублирующая сортировка.** Отдельная панель над таблицей добавлена F-03,
   при этом цена/площадь уже сортируются заголовками. ₽/сот. не имеет собственного
   столбца. Серверную сортировку до пагинации нужно сохранить.
4. **Перегруженное управление медианой.** Постоянная панель массовых действий,
   пояснение расчёта и многословное состояние в каждой строке. Это расширяет
   интерфейс, хотя главное действие — одна отметка участия.
5. **Автодобавление не отсутствует.** `IncomingCatalogV2.razor:825` содержит
   галочку, но в модальном окне сохранения/редактирования пресета, отдельно от
   раскрытых условий. Проблема обнаружения и разобщённости двух форм. Не создавать
   вторую настройку или новый независимый флаг.
6. **Полноценный редактор вместо поля.** `CaseRichNoteBlock` +
   `ClientAssets/case-notes.js` используют Tiptap/таблицы/панель инструментов,
   JSON-документ и SafeHtml. `CaseCheckEntry` повторно использует этот редактор.
   Просто удалить toolbar не равнозначно обычному текстовому полю.
7. **Дублирование способов проверки.** В `CaseWorkspace.razor:147–154` отдельные
   проверки и независимый свободный текст секции показываются рядом. Существующие
   данные обоих видов нельзя потерять при упрощении.
8. **Неодинаковые поля задач.** `CaseNextAction` выводит дату/время вне обычной
   `.field`, а собственный CSS задаёт только ширину времени. На скриншоте видны
   стандартные браузерные контролы среди стилизованных полей.
9. **Задача после общения: дефект заявлен, причина не доказана.** В
   `CaseCommunication.Save` NextTask создаётся только при непустом TaskTitle;
   backend сохраняет общение и задачу в одной транзакции. `CommunicationSaved`
   перезагружает карточку; `CaseNextAction` имеет key по CaseId/CaseVersion.
   Нельзя объявить отсутствие refresh причиной без проверки конкретного сохранения.
10. **Неодинаковые вложения.** `CaseCommunication.AllowAttachments` включает
    файлы в боковой панели, но не передаётся при открытии из полной карточки.
    Полная карточка и панель дают разный набор возможностей одной формы.
11. **Самодельная типографика ленты.** `CaseActivityFeed.razor.css` задаёт
    14/13/12 px вместо ролей токенов. У дат и авторов 12 px; нарушено правило
    читаемых подписей. Аналогичные локальные размеры есть в рыночном блоке.
12. **Растягивание карточки.** `CaseWorkspace.razor.css` использует stretch
    для hero/object-card; увеличение формы задач справа растягивает левый блок
    фото/описания. Это соответствует скриншоту, но точные размеры нужно проверить
    на отрисованном экране. Стили должны развязать рост редактора и фото.

## Что сохраняем

Общие фильтры организации; отбор по группе, включая добавленные ссылки; OR
сохранённых фильтров; единый predicate выдачи/счётчиков; архивные состояния;
серверную сортировку и пагинацию. Пустой рабочий отбор не превращается во всю базу.

Единую отметку участия объявления, расчёт отдельно по каждой группе, участие в
нескольких группах, исключение дубля/фейка/снятого, допустимость проданного.
Проданная цена источника не выдаётся за подтверждённую цену сделки.
Автодобавление только новых объявлений по явно включённой настройке фильтра,
без молчаливого возврата вручную исключённых. Старые ограничения расчёта не возвращаем.

Тест спроса как ручную цену за сотку с существующими правами. Историю,
организационную изоляцию, версии, повторяемость команд, существующие вложения.
Несколько независимых задач и правила их сохранения при закрытии объекта.
Уже введённые rich-text документы не преобразовывать с потерей таблиц/картинок.

## Последовательность задач для агента

### R-01. Диагностика и исправление задачи после общения — средняя сложность

Независимый первый этап. Один конкретный case и сохранённая запись: проверить
переданный TaskTitle, наличие WorkTask и события создания, результат ReadTasks,
версию карточки и обновление UI. Читать только нужные записи, не выгружать всю БД.
Если воспроизведения нет — честно оставить причину неподтверждённой, запросить
минимальное уточнение, не менять логику наугад.

Файлы: CaseCommunication, CaseWorkspace, CaseNextAction, ProcurementWorkspace,
ProcurementCaseTasks; соответствующие контракты/тест только при необходимости.
Исправить реальный дефект. Сообщение об успехе должно различать «Общение сохранено»
и «Общение и задача сохранены». Задача сразу видна в полной карточке и панели,
после обновления страницы сохраняется. Повтор команды не создаёт дубль.
Проверка: один адресный сценарий на найденную причину и короткий ручной проход.

### R-02. Входящие, выбор и фильтры — высокая связность, средняя/высокая сложность

Первый целый экран, который приводим к эталону. Внутри этапа сначала геометрия,
затем выбор и настройки фильтра; не смешивать с карточкой закупки.

- Именованные колонки/colgroup с корректным read-only вариантом. Выбор 40–48 px,
  чекбокс около 20 px с областью нажатия не меньше 36 px. Основное место объявлению.
  Без гигантских пустот и принудительного растяжения строк. Локальная прокрутка
  таблицы на узком экране, нормальный размер текста.
- Отдельные «Цена», «Цена за сотку», «Площадь», сортировка только заголовками.
  Направление заметно; неизвестные значения остаются последними.
- Короткая колонка «В медиане» с переключателем. Причина недоступности только
  для соответствующей строки; наличие отметки и фактическую пригодность не путать.
- Заголовочный чекбокс выбирает страницу. «Выбрать все N результатов» — отдельное
  явное действие. Любую строку можно снять в обоих режимах; есть частичное состояние,
  подсветка и точный счётчик. Смена условий сбрасывает выбор.
- Расширить контракт all-results исключениями ID и серверным predicate, сохранить
  preview/stamp/version защиты. Не загружать все ID базы в браузер. Preview и apply
  обязаны использовать один состав выборки, включая исключения и страницы.
- Панель действий появляется только при выборе. Выбор строк сам по себе не
  меняет отметки участия. Убрать постоянное техническое пояснение расчёта.
- Условия и настройки сохранённого фильтра показывать согласованно. В форме явно
  доступны имя, группа и существующая галочка автодобавления. Её смысл — новые
  объявления; существующие включаются отдельным действием с видимым количеством.
  Не превратить каждое применение условий в сохранение общего фильтра.
- Числа у фильтров, «Новые», «Найдено», архив и список участников сохраняют
  действующие границы отбора. У новых элементов не должно быть скрытых фильтров.

Файлы: IncomingCatalogV2.razor/.css, incoming-v2-sizing/workflow.css,
CatalogCalculationContracts/Service, существующие preset contracts/service при
реальной необходимости. Read service сортировки не переписывать без дефекта.
Проверки: все N минус исключения между страницами; смена фильтра; права чтения;
сортировка; совпадение preview/apply. Ручная приёмка нормального и узкого desktop.

### R-03. Обычный текст и вложения — высокая сложность совместимости

Зависит от согласованных требований, не от R-02. Один лёгкий компонент ввода:
textarea, Ctrl+V изображения, скрепка, миниатюры/имена файлов с удалением из
черновика, Сохранить/Отмена. Без contenteditable, toolbar, таблиц и оформления.
Вставка обычного текста остаётся обычной вставкой. Изображения не сохраняются
base64 в бизнес-тексте. Используем защищённый текущий storage и доступ по case.

Применение: рабочие заметки, свободный текст секций проверок, результат отдельной
проверки, запись общения в полной карточке и панели. Контексты сохранения разные,
поэтому переиспользуем ввод/вложения, а не объединяем разные бизнес-сущности.

Сначала определить минимальную совместимость хранимого текста и ссылок на файлы.
Рекомендуется сохранить текущие таблицы и защищённое хранилище; поддержать простой
текст и ссылки вложений через ограниченный серверный адаптер. Legacy rich-doc
оставить читаемым без разрушительного flatten при первом сохранении.
Точный формат адаптера выбирается после адресного анализа CaseNoteDocument;
не обещать отсутствие миграции до проверки связи «файл — конкретная запись».
Не связывать файлы с записью по имени или времени и не создавать новое хранилище.

Отмена не должна незаметно публиковать вложение как часть сообщения. Ошибка
загрузки сохраняет черновик; ошибка файла после записи не создаёт дубль сообщения.
Не выполнять массовое удаление старых файлов и Tiptap-данных. Удаление зависимости
Tiptap — только когда нет действующих потребителей, а не отдельная цель этапа.

Файлы: CaseRichNoteBlock, CaseCheckEntry, CaseCommunication, ClientAssets/case-notes.js,
существующие CaseNoteDocument/attachment contracts и адресные команды сохранения.
Проверки: текст, Ctrl+V, файл, отмена, ошибка/retry, права, legacy-документ с фото/таблицей.

### R-04. Проверки как простой рабочий экран — средняя сложность

После R-03. Сохранить базовую и глубокую секции. Существующие проверки — компактные
строки: название, результат, вложения; состояние и действие редактирования вторичны.
Добавление и редактирование рядом с записью; текст/изображения/файл через R-03.
Без обязательного назначения, срока, стоимости и настройки шаблона для записи результата.
Не создавать третий способ ввода. Общий текст секции остаётся доступен как
«Общие заметки», а не ещё одна постоянно раскрытая большая форма.

Права, blocker и legacy-состояния не уничтожать. Убрать служебные объяснения
«отдельный признак», «прежнее состояние», «сохраняются» из обычного чтения;
важный реальный запрет и блокирующий вопрос должны оставаться понятны.
Блокер не включается от редактирования текста или выбора «Есть вопросы».
Файлы: CaseWorkspace check section, CaseCheckEntry, R-03 компонент; никаких
изменений workflow ради верстки. Приёмка: быстро записать результат, отредактировать,
прочитать старый, увидеть вложения и понять реальный блокер.

### R-05. Карточка, задачи и общение — средняя сложность

После R-01/R-03. Привести поля, кнопки типов/каналов, сроки, ошибки к UI-kit.
Размещение задач компактное, все действия самостоятельны. Форма добавления не
растягивает фото и основную карточку; группы цены/времени соразмерны данным.
Не скрывать цены и следующую задачу общения в сворачиваемые секции — владелец
от этого явно отказался. Не сокращать интерфейс уменьшением шрифта.
Файлы: CaseNextAction, CaseCommunication, CaseWorkspace и их CSS; общий
небольшой date/time control только если реально повторяется, без конструктора форм.
Приёмка: две независимые задачи, редактирование/выполнение/удаление, сообщение
с задачей, вложения в двух местах, длинное название, ограниченная ширина.

### R-06. Ленты и рыночные показатели — небольшая/средняя сложность

После стабилизации карточки и таблицы. Сохранить колонки дата/бизнес-текст/автор
и тип, восстановить токены шрифтов и отступов. Автор/дата не должны вытеснять смысл.
Старые содержательные комментарии и системные события не удалять ради краткости.
Сохранить fallback U-01 для неоднозначного legacy-события, не угадывать связь.

Рыночный блок: группа, средняя, медиана, тест спроса, число участников; согласованные
места сохраняются. Убрать повтор числа участников в Home и технический язык
«отмеченные пригодные источники». Тест спроса редактируется существующим правом,
единицы ₽/сот. ясны. Нет группы — просьба выбрать, несколько групп — явный выбор.
Участники доступны из показателя; их выдача не ограничивается входящими/рабочим OR.
Файлы: CaseActivityFeed/CaseFeedFormat, GroupMarketPrices/DemandTestPrice,
Home/ProcurementQueueV2/IncomingCatalogV2 только места встраивания.
Приёмка: длинная запись, старые поля, узкая панель, отсутствие группы/данных,
несколько групп, переход в участников, редактирование теста спроса.

## Как передавать работу и принимать результат

Один этап — одна активная задача. Не передавать весь этот документ как разрешение
на всю реализацию. R-01 и R-02 лучше отдельными заданиями; R-03/R-04 тесно связаны
и могут идти последовательно в одном чате. R-05/R-06 — после них. Новый чат получает
точный checkpoint, незавершённые ограничения и только нужные reference-файлы.

Перед началом сохранить согласованную базу, не смешивать изменения других этапов.
Новый функционал (канбан, решения, popup изменений источника, обзор) пока не начинать.
Всё выше — исправление уже заказанного поведения, кроме явно отмеченных решений
о совместимости хранения, которые требуют технического обоснования.

У каждого этапа две независимые отметки: код/адресные проверки и ручная проверка
сценария/внешнего вида. Предыдущие зелёные тесты не являются приёмкой UX.
Обязательная ручная выборка: 1440 и 1280 px, узкая боковая панель, обычная/компактная
плотность, длинные тексты, пустые данные, ошибки, read-only. 1920 px — контроль,
что поля и строки не растянулись бессмысленно. Масштаб браузера 100% для сравнения.
Браузерная автоматизация остаётся отключена; ручной просмотр не заменяется догадкой.
Агент заранее сверяет разметку с эталоном и готовит точный короткий сценарий проверки,
