# 09 — Аудит действий

**Статус:** approved UI reference  
**Экран:** человекочитаемая история значимых действий системы  
**UI reference:** `docs/14-ui-kit/prototypes/landerp_audit_v1_1.html`

## Назначение

Аудит должен отвечать на простые рабочие вопросы:

- кто сделал действие;
- когда;
- с каким объектом;
- что именно изменилось;
- к какому разделу относится событие.

Текущий Stage 1 экран выводит технические `Action`, `ObjectType`, GUID и сырой JSON. Эти данные нужны для диагностики, но не должны быть основным пользовательским представлением.

## Основной список

Главная лента показывает события человеческим языком, например:

- `Владелец вошёл в систему`;
- `Создан поисковый запрос`;
- `Поставлено задание на парсинг`;
- `Подключён новый парсер`;
- `Добавлен сотрудник «Анастасия»`;
- `Создана должность`;
- `Создан отдел`.

В строке события показываются:

- локальное время организации;
- тип/иконка события;
- понятный заголовок;
- краткий контекст;
- автор с display name;
- понятный объект;
- переход в подробности.

GUID, raw action name и JSON в основной таблице не показывать.

## Группировка и фильтры

События группируются по дням.

Минимальные фильтры:

- полнотекстовый поиск по сотруднику, объекту и описанию действия;
- период (`Сегодня`, `7 дней`, `30 дней`, произвольный);
- сотрудник;
- раздел;
- быстрые категории `Все / Изменения данных / Входы и доступ / Парсинг / Закупка`.

Время в UI отображается в `Organization.BusinessTimeZone`. UTC остаётся техническим способом хранения.

## Подробности события

Клик по событию открывает drawer.

Верхний блок:

- когда;
- кто;
- раздел;
- объект.

Главный блок — **`Что изменилось`**. Он должен быть семантическим и зависеть от типа события.

Примеры:

### Добавлен сотрудник

Показывать:

- ФИО;
- логин;
- отдел;
- команду;
- должность;
- руководителя;
- роль;
- область доступа;
- состояние.

Не показывать в этом событии поля поискового запроса или другого объекта.

### Создан поисковый запрос

Показывать:

- название;
- источник;
- предел страниц;
- при наличии — группа и расписание.

### Создан отдел / должность / команда

Показывать имя созданной сущности и её начальное состояние.

### Изменение существующей сущности

Для изменённых значений желательно показывать `Было → Стало`. Не нужно выводить поля, которые не изменились.

### Системное действие

Для событий без business diff, например успешного входа или постановки job по расписанию, `Что изменилось` показывает результат/причину/новое состояние, а не искусственный Before/After.

## Технические данные

Технические данные сохраняются и доступны по кнопке `Показать`, но по умолчанию скрыты:

- raw `Action`;
- `ObjectId`;
- `ActorId`;
- `CorrelationId`;
- raw audit payload JSON.

Это диагностический слой, а не основной UX.

## Server read model

Текущий `AuditView` недостаточен для production UI: он отдаёт только `RecordedAt`, `Action`, `ObjectType`, `ObjectId`, `ActorId`, `Changes`.

Для страницы нужен отдельный read model/проектор, который сервер формирует из immutable audit event и связанных справочных данных.

Минимально вернуть:

- `RecordedAtUtc`;
- display time через timezone организации;
- `Category` / `Module`;
- human-readable `Title`;
- `Summary`;
- `ActorId` + `ActorDisplayName`;
- `ObjectType` + `ObjectId` + `ObjectDisplayName`;
- семантический список изменений `Field / Before / After`;
- технические данные для drawer.

Не обязательно менять физическую таблицу `AuditEvents`, если текущего immutable payload достаточно. Человекочитаемое представление можно строить в read/query layer.

## Имена событий

Не выводить `CollectionSearchCreated`, `AssignmentChanged`, `EmployeeInvited` напрямую пользователю.

Для известных action codes нужен явный mapping/formatter. Если появляется неизвестное событие, UI должен безопасно показать нейтральное описание и сохранить raw technical details, а не падать.

Formatter должен учитывать тип события: один общий разбор arbitrary JSON в UI не использовать.

## Actor и object display name

Вместо GUID автора сервер должен по возможности возвращать display name сотрудника/пользователя на момент чтения.

Для бизнес-объекта возвращать понятное имя/номер, например:

- сотрудник — ФИО;
- поиск — Label;
- PropertyCase — business number / краткое имя;
- отдел/команда/должность — Name;
- parser Agent — Name.

Если связанная сущность уже архивирована или удалена технически, audit event всё равно должен оставаться читаемым. Поэтому для значимых событий полезно сохранять в payload достаточный snapshot display-данных.

## Pagination и период

Текущий `Take(100)` заменить на серверную пагинацию/курсор и фильтрацию.

Не загружать всю историю в браузер.

Запрос должен поддерживать минимум:

- organization scope;
- from/to;
- actor;
- category/module;
- action/category;
- search term, если реализуемо без тяжёлой схемы;
- page/cursor + page size.

Для Stage 1 достаточно обычной пагинации и разумного page size.

## Статистика

Верхние карточки — вспомогательные и считаются по выбранному периоду:

- всего событий/сегодня;
- число активных авторов;
- изменения данных;
- события безопасности.

Если расчёт этих карточек заметно усложняет сервер, они не должны блокировать основную реализацию списка.

## Экспорт

`Экспорт CSV` допустим как простой admin action. Экспорт должен уважать текущие фильтры и permissions. Raw secrets в экспорт не включать.

## Security и immutable history

События аудита не редактируются и не удаляются через UI.

Audit payload не должен содержать:

- plaintext passwords;
- invitation tokens;
- session/cookie secrets;
- parser credentials;
- другие секреты.

Доступ к экрану остаётся под `audit.read` и organization scope.

## Server delta относительно текущего Stage 1

Минимальная доработка:

1. заменить `ReadAuditAsync()` с `Take(100)` на фильтруемый paged query;
2. добавить human-readable actor names;
3. добавить object display names;
4. добавить server-owned mapping action code → title/category/module;
5. для известных actions преобразовывать `Changes` в семантические поля;
6. отдать raw technical details отдельно для drawer;
7. форматировать время в UI по `BusinessTimeZone`;
8. сохранить immutable audit storage и существующий raw payload;
9. добавить аудит новых административных действий из экрана `Организация`, не записывая временные пароли.

Не строить универсальную event-sourcing платформу ради страницы. Нужен небольшой понятный audit read layer поверх существующей таблицы.

## UI reference

`landerp_audit_v1_1.html` фиксирует композицию, фильтры, группировку и drawer.

Демо-данные в HTML не являются production data. В v1.1 каждый демонстрационный event имеет собственный релевантный блок `Что изменилось`; нельзя использовать одну статическую заглушку для всех типов событий.

Production UI реализуется на текущем Blazor/UI-kit стеке проекта.

## DoD

Экран можно считать готовым, когда:

- список не показывает GUID/raw JSON как основные данные;
- авторы и объекты читаются по имени;
- время показывается в timezone организации;
- работают период, actor/module/category filters и пагинация;
- drawer каждого события показывает данные именно этого события;
- `Было → Стало` корректно работает для update actions;
- технические поля доступны отдельно;
- неизвестное action code не ломает страницу;
- audit остаётся immutable;
- секреты не попадают ни в payload, ни в UI, ни в экспорт;
- permissions проверяются сервером.
