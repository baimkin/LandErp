# FP-001 — Архитектурный каркас и среды

**Версия:** 0.1  
**Статус:** Черновик  
**Владелец бизнес-решения:** владелец продукта  
**Технический владелец:** архитектор / ведущий разработчик  
**Зависимости:** генеральный план, ADR-001, ADR-002  
**Блокирует:** все продуктовые фичи

## 1. Решение в одном абзаце

Создать минимальный, но эксплуатационно правильный каркас Land ERP: единое
решение с Server, Application, Infrastructure, Worker, Agent и AgentContracts;
модульными границами и Vertical Slices; подключением PostgreSQL; управляемыми
миграциями; базовой наблюдаемостью; автоматическими архитектурными проверками;
средами Local/Test/Staging/Production и CI. Каркас не содержит искусственных
бизнес-фич, но позволяет следующему плану добавлять полноценный вертикальный
сценарий без переделки фундамента.

## 2. Почему делаем сейчас

- Все следующие планы зависят от структуры решения и правил зависимостей.
- Ошибка в каркасе размножится на каждый модуль и станет дорогой для исправления.
- Server, Worker и локальный Agent имеют разные модели запуска и отказа.
- Инвесторский доступ требует заложить области данных до появления экранов.
- Миграции, логи и тесты должны появиться раньше реальных данных.

## 3. Измеримый результат

| Показатель | Цель |
|---|---|
| Чистая сборка | Всё решение собирается одной документированной командой |
| Автоматические тесты | Unit, architecture и минимальный integration smoke-test выполняются в CI |
| Развёртывание | Server и Worker запускаются независимо на Local и Test |
| PostgreSQL | Подключение и миграция проверяются на чистой реальной БД |
| Наблюдаемость | Каждый HTTP-запрос и Worker-операция имеют correlation ID и структурный лог |
| Архитектура | Запрещённые зависимости ловятся автоматическим тестом |
| Воспроизводимость | Новый разработчик запускает каркас по одной актуальной инструкции |

## 4. Границы

### Входит

- структура solution и проектов;
- правила ссылок между проектами;
- модульный каталог Application;
- минимальный Shared Kernel;
- Server и Worker hosts;
- Agent host без реального адаптера площадки;
- AgentContracts с версией протокола;
- PostgreSQL и пустая начальная миграция служебной схемы;
- централизованные версии и параметры сборки;
- конфигурация Local/Test/Staging/Production;
- health checks, Problem Details, correlation ID и структурные логи;
- CI build/test/format/architecture gates;
- архитектурные и smoke-тесты;
- базовая инструкция локального запуска.

### Не входит

- полноценная аутентификация и роли — FP-002;
- поисковые ссылки и расписания — FP-010;
- очередь заданий — FP-011;
- Playwright-парсинг Авито — FP-012;
- бизнес-таблицы Listing и PropertyCase;
- кабинет инвестора;
- production cloud provider и окончательный pipeline поставки;
- сложная геомодель и PostGIS-функции.

## 5. Целевая структура solution

```text
LandErp.slnx
src/
  LandErp.Server/
  LandErp.Application/
    Modules/
      IdentityAccess/
      Administration/
      Collection/
      PropertyCatalog/
      ManagerWorkspace/
      DueDiligence/
      ProjectsFinance/
      InvestorPortal/
      Reporting/
  LandErp.Infrastructure/
  LandErp.Worker/
  LandErp.Agent/
  LandErp.AgentContracts/
tests/
  LandErp.UnitTests/
  LandErp.IntegrationTests/
  LandErp.ArchitectureTests/
  LandErp.ContractTests/
  LandErp.EndToEndTests/
docs/
```

Точные имена solution и namespace утверждаются ADR-002. Структура не должна
создавать отдельный проект на каждый Use Case или превращать модульный монолит в
распределённую систему.

## 6. Правила зависимостей

| Проект | Может ссылаться на | Не может ссылаться на |
|---|---|---|
| Server | Application, Infrastructure | Agent |
| Worker | Application, Infrastructure | Server UI, Agent |
| Application | AgentContracts при необходимости, BCL | Server, Worker, Infrastructure |
| Infrastructure | Application | Server UI, Agent |
| Agent | AgentContracts и собственная инфраструктура | Application, Infrastructure, PostgreSQL |
| AgentContracts | BCL и минимальные контрактные библиотеки | Любой серверный проект |

Server и Worker собирают композицию зависимостей. Application содержит бизнес-
сценарии и интерфейсы инфраструктуры, но не знает о конкретном DbContext,
файловом провайдере или браузерном движке.

## 7. Модульный каркас

На этом этапе создаются только границы и регистрация модулей. Пустые классы ради
кажущейся полноты не создаются. Первый реальный Vertical Slice появится в FP-002
и FP-010.

Каждый модуль в будущем содержит:

- публичный контракт модуля;
- папки конкретных Use Case;
- принадлежащие модулю модели и состояния;
- регистрацию зависимостей и endpoint;
- внутренние события;
- тесты границ.

Межмодульный вызов разрешён только через публичный контракт или событие. Handler
одного Use Case не является публичным API для другого.

## 8. Конфигурация

### 8.1. Источники конфигурации

Порядок наложения:

1. безопасные значения по умолчанию в коде;
2. общая конфигурация приложения;
3. конфигурация среды;
4. переменные среды;
5. секреты утверждённого хранилища;
6. аргументы запуска только для разрешённых параметров.

Секреты не хранятся в Git. Production connection string не доступен Agent.

### 8.2. Проверка конфигурации

Критичная конфигурация валидируется при старте. Приложение не должно запускаться в
полурабочем состоянии с отсутствующим connection string, неверным issuer или
пустым ключом машинной аутентификации.

### 8.3. Разделение Server и Worker

Server может работать без активного выполнения фоновых заданий. Worker может быть
временно остановлен без недоступности пользовательского интерфейса. Общая версия
релиза и схема БД остаются совместимыми.

## 9. PostgreSQL и миграции

### 9.1. Первый контур БД

- отдельный DbContext либо чётко определённый основной DbContext;
- служебная схема для истории миграций;
- русские комментарии для создаваемых таблиц и столбцов;
- `timestamptz` для времени;
- UUIDv7 для бизнес-ID;
- единая политика имён таблиц, индексов и ограничений;
- приложение использует минимально необходимые права.

Выбор «один DbContext или DbContext на модуль» фиксируется ADR-002 после короткого
proof-of-concept. Для первой версии предпочтителен один физический DbContext с
модульно разделёнными конфигурациями и владельцами таблиц, если это не разрушает
границы тестов.

### 9.2. Миграции

- Генерация миграции выполняется разработчиком/CI, а не production-сервером.
- Production-миграция является отдельным шагом поставки.
- Каждая миграция проверяется на чистой БД и на обновлении предыдущей схемы.
- Опасная операция требует expand–migrate–contract.
- Откат приложения не должен зависеть от мгновенного удаления нового столбца.

### 9.3. PostGIS

Расширение можно включить в инфраструктуру среды, но доменная модель этапа не
содержит обязательных geometry-полей. Подключение NetTopologySuite и первая
геометрия выполняются в FP-060.

## 10. Наблюдаемость

### 10.1. Логи

Минимальные поля:

- timestamp UTC;
- level;
- service (`Server`, `Worker`, `Agent`);
- application version;
- environment;
- correlation/trace ID;
- module и use case;
- результат и стабильный код ошибки;
- безопасные идентификаторы сущностей.

Не логируются connection strings, токены, cookies, пароли и полный недоверенный
HTML.

### 10.2. Health checks

- `/health/live` — процесс способен отвечать;
- `/health/ready` — критичные зависимости доступны;
- БД проверяется коротким запросом без тяжёлой бизнес-логики;
- readiness Worker не должен делать недоступным Server;
- health endpoint не раскрывает секреты и внутренние исключения.

### 10.3. Метрики каркаса

- HTTP request count, duration и errors;
- активные соединения БД и ошибки пула;
- Worker executions и failures;
- версия работающих процессов;
- время старта и readiness.

## 11. Ошибки API

Все HTTP-ошибки используют Problem Details с:

- стабильным `type`/error code;
- понятным `title`;
- корректным HTTP status;
- correlation ID;
- безопасными validation details.

Stack trace и внутренние исключения доступны только в защищённой диагностике.

## 12. Среды

| Среда | Назначение | Данные | Особенности |
|---|---|---|---|
| Local | Разработка | Синтетические | Быстрый запуск и отладка |
| Test | Автоматические тесты | Изолированные на прогон | Testcontainers и детерминированное время |
| Staging | Проверка релиза | Обезличенные/синтетические | Близкая к production конфигурация |
| Production | Рабочая система | Реальные | Строгие секреты, аудит, backup и мониторинг |

Нельзя использовать production cookies источников в автоматических тестах.

## 13. CI

Минимальный pipeline:

1. восстановление зависимостей из закреплённых версий;
2. проверка форматирования;
3. build с warnings as errors;
4. unit tests;
5. architecture tests;
6. integration tests с PostgreSQL;
7. contract tests при наличии фикстур;
8. сборка Server, Worker и Agent artifacts;
9. публикация отчёта тестов и диагностик без секретов.

Ветка не может пройти проверку при отключённых архитектурных тестах.

## 14. Архитектурные тесты

Первый набор проверяет:

- Application не зависит от Infrastructure, Server и Worker;
- Agent не зависит от серверных проектов и EF Core;
- AgentContracts не зависит от доменных модулей;
- модуль не обращается к внутренним namespace другого модуля;
- endpoint/transport DTO не являются EF entities;
- нет папок-свалок `Common`, `Helpers`, `Utils` внутри модулей;
- каждый Use Case находится в своей папке после появления первых срезов.

## 15. Эталонные примеры

Примеры предполагают утверждение .NET 10. Их задача — закрепить стиль, а не
реализовать продуктовую фичу.

### 15.1. Регистрация модуля

```csharp
namespace LandErp.Application.Modules;

public interface ILandErpModule
{
    static abstract void AddServices(IServiceCollection services, IConfiguration configuration);

    static abstract void MapEndpoints(IEndpointRouteBuilder endpoints);
}
```

Конкретный механизм может быть скорректирован ADR-002; автоматическая магия
сканирования сборок не обязательна, если явная регистрация проще для чтения.

### 15.2. Проверяемая конфигурация

```csharp
public sealed class DatabaseOptions
{
    public const string SectionName = "Database";

    public required string ConnectionString { get; init; }
}

services
    .AddOptions<DatabaseOptions>()
    .BindConfiguration(DatabaseOptions.SectionName)
    .Validate(
        options => !string.IsNullOrWhiteSpace(options.ConnectionString),
        "Database connection string is required.")
    .ValidateOnStart();
```

### 15.3. Correlation ID middleware

```csharp
public sealed class CorrelationIdMiddleware(RequestDelegate next)
{
    public const string HeaderName = "X-Correlation-ID";

    public async Task InvokeAsync(HttpContext context)
    {
        string correlationId = context.Request.Headers.TryGetValue(HeaderName, out var value)
            && !string.IsNullOrWhiteSpace(value)
                ? value.ToString()
                : Guid.CreateVersion7().ToString();

        context.TraceIdentifier = correlationId;
        context.Response.Headers[HeaderName] = correlationId;

        await next(context);
    }
}
```

В реальном коде входное значение дополнительно ограничивается по длине и
допустимым символам.

## 16. Тестовая стратегия

| Уровень | Обязательная проверка |
|---|---|
| Unit | Валидация критичной конфигурации и чистые базовые типы |
| Integration | Старт приложения, подключение к PostgreSQL и применение миграции |
| Architecture | Все правила раздела 14 |
| E2E smoke | Server стартует, health доступен, неизвестный маршрут возвращает безопасную ошибку |
| Security | Секреты и stack trace не попадают в ответ и лог теста |

## 17. Вертикальные этапы

### Этап 1. Воспроизводимое решение

Server, Worker и Agent собираются; версии централизованы; есть инструкция запуска.

### Этап 2. Реальная БД

Server и Worker подключаются к изолированной PostgreSQL; миграция применяется и
проверяется integration test.

### Этап 3. Архитектурные границы

Созданы модули и автоматические тесты зависимостей; намеренное нарушение делает
CI красным.

### Этап 4. Наблюдаемость и CI

Логи, correlation ID, health, Problem Details и полный минимальный pipeline
работают вместе.

Каждый этап разворачиваем и проверяем; не создаётся отдельный commit «только
папки» без работающего результата.

## 18. Развёртывание и откат

- Первая поставка предназначена для Local/Test.
- Staging добавляется после выбора инфраструктуры.
- Каркас не выполняет production-миграции при старте.
- Откат возвращает предыдущий Server/Worker artifact; схема остаётся совместимой.
- Agent обновляется отдельно и не включён в автоматический server deployment.

## 19. Definition of Ready

- ADR-001 утверждён;
- предварительно согласованы имя решения и структура;
- известны целевые ОС разработчиков и CI;
- доступна PostgreSQL 18 для integration tests;
- выбран минимальный CI-провайдер;
- определён владелец секретов и инфраструктуры.

## 20. Definition of Done

- решение собирается из чистого checkout;
- Local-инструкция проверена вторым человеком;
- Server, Worker и Agent запускаются независимо;
- чистая PostgreSQL поднимается и мигрируется автоматически в тесте;
- архитектурные тесты реально ловят запрещённую зависимость;
- CI выполняет все обязательные проверки;
- логи, health и Problem Details не раскрывают секреты;
- версии и артефакты сборки однозначно определяются;
- документация соответствует фактическому каркасу.

## 21. Открытые вопросы

| Вопрос | Блокирует |
|---|---|
| Окончательное имя продукта и корневой namespace | Создание solution |
| GitHub, GitLab или другой CI | Конкретный pipeline |
| Docker доступен на машинах разработчиков и CI | Стратегию integration tests |
| Целевая ОС локальных агентов | Сборку Agent artifact |
| Облачный провайдер | Staging/Production, но не Local/Test |
| Один DbContext или DbContext на модуль | Схему Infrastructure и миграций |
