# SPIKE-001 — Проверка жизнеспособности парсинга Avito

**Версия:** 0.1  
**Статус:** Черновик  
**Тип:** техническое исследование с ограниченным прототипом  
**Владелец решения:** владелец продукта  
**Исполнители:** разработчик Agent / технический аналитик  
**Ориентир длительности:** 5–10 рабочих дней  
**Связанные документы:** ADR-001, ADR-006, FP-001, FP-012, FP-014, OP-011  
**Блокирует:** начало промышленной реализации адаптера Avito по FP-012

## 1. Решение

До разработки серверного контура сбора и промышленного `LandErp.Agent` выполнить
ограниченное исследование Avito на C# и Microsoft.Playwright. Прототип должен
доказать или опровергнуть возможность стабильно распознавать поисковую выдачу и
подробную карточку объявления в разрешённом режиме работы браузера.

Результат Spike — не готовый парсер и не субъективное заключение «страница
открылась», а воспроизводимый набор экспериментов, измерений, фикстур,
диагностики и решение `Go`, `Conditional Go` или `No-Go`.

## 2. Почему Spike выполняется первым

Главный ранний технический риск LandErp находится не в PostgreSQL, Blazor или
серверной архитектуре, а в нестабильности внешнего источника:

- динамическая загрузка и изменение разметки;
- различные варианты выдачи и карточки;
- авторизация, CAPTCHA и ограничения частоты;
- рекламные и рекомендательные блоки внутри страницы;
- различия между сохранённым HTML и реальной браузерной страницей;
- неполные, противоречивые и отсутствующие поля;
- различия сессий на нескольких Windows-компьютерах.

До подтверждения управляемого режима сбора нельзя считать архитектуру первого
вертикального пути доказанной.

## 3. Цель

Ответить на пять вопросов:

1. Можно ли надёжно классифицировать состояние страницы до извлечения данных?
2. Можно ли стабильно выделить основную выдачу, не смешав её с рекламой,
   рекомендациями и объявлениями других регионов?
3. Можно ли извлечь достаточный набор полей выдачи и карточки с измеримым
   качеством?
4. Можно ли работать в консервативном режиме на локальных Windows-компьютерах
   без автоматического обхода защитных механизмов?
5. Какой объём ручного вмешательства потребуется для авторизации, CAPTCHA и
   восстановления сессий?

## 4. Гипотезы

| ID | Гипотеза | Способ проверки |
|---|---|---|
| H-01 | Playwright открывает сохранённую поисковую ссылку в headed Chromium | Серия запусков с новым и постоянным профилем |
| H-02 | Тип страницы определяется до парсинга полей | Набор обычных, CAPTCHA, login, error и unknown страниц |

| H-05 | Ключевые поля извлекаются с приемлемой полнотой | Field-level отчёт по выдаче и detail |
| H-06 | Постоянный browser profile снижает повторные входы | Сравнение чистого и постоянного профиля |
| H-07 | Ошибка разметки не выглядит как успешная пустая выдача | Негативные фикстуры и намеренно изменённая структура |

## 5. Границы исследования

### Входит

- локальное консольное приложение или минимальный executable без полноценного UI;
- C# 14, .NET 10 и Microsoft.Playwright;
- Windows x64 как первая целевая среда;
- Chromium, установленный Playwright;
- headed-режим как основной режим исследования;
- один явно разрешённый локальный browser profile;
- ручная авторизация и ручная реакция на CAPTCHA;
- предоставленные HTML-файлы выдачи и карточки;
- ограниченная живая выборка Avito;
- уровень 1: поисковая выдача;
- уровень 2: подробная карточка;
- сохранение результата в локальный JSON;
- структурные логи, screenshot/HTML/trace только по диагностической политике;
- проверка минимум на двух Windows-компьютерах, если они доступны в период Spike;
- отчёт и решение о дальнейшем пути.

### Не входит

- сервер LandErp, PostgreSQL и очередь заданий;
- production-ready `LandErp.Agent`;
- системный трей, автообновление и установщик;
- работа со всеми 30–50 поисковыми ссылками;
- круглосуточный или массовый сбор;
- Cian и другие источники;
- отправка сообщений продавцам;
- показ или сбор телефонных номеров;
- скачивание всех оригиналов фотографий;
- обход CAPTCHA, маскировка автоматизации или противодействие блокировкам;
- ротация чужих аккаунтов, прокси и подмена цифрового отпечатка;
- автоматическое юридическое или инвестиционное решение;
- использование прототипа как production-компонента без переработки.

## 6. Предусловия и стоп-условия

### Предусловия

- владелец процесса подтверждает допустимый сценарий исследования;
- используются только принадлежащие компании или разрешённые учётные записи;
- подтверждено, какие страницы и данные допустимо сохранять;
- предоставлены исходные HTML-примеры и поисковые ссылки;
- определён ответственный за ручную авторизацию и CAPTCHA;
- в рабочей папке и логах отсутствуют пароли, cookies и токены;
- задан консервативный лимит навигаций и пауз между сессиями.

### Немедленная остановка

Исследование останавливается, если:

- для продолжения требуется обход CAPTCHA или иного ограничения;
- площадка явно запрещает дальнейшую автоматизированную работу в выбранном режиме;
- возникает риск блокировки важного рабочего аккаунта;
- диагностика начала сохранять cookies, токены, сообщения или иные секреты;
- поведение прототипа вышло за утверждённый лимит страниц или действий;
- источник возвращает неизвестное состояние, которое прототип ошибочно трактует
  как успешную пустую выдачу.

Остановка считается корректным результатом исследования, а не провалом
исполнителя.

## 7. Технологическая база прототипа

| Область | Решение для Spike |
|---|---|
| Язык | C# 14 |
| Runtime | .NET 10 LTS |
| Автоматизация браузера | Microsoft.Playwright |
| Браузер | Playwright Chromium |
| ОС | Windows x64 |
| Режим | Headed по умолчанию; headless только как отдельный сравнительный опыт |
| Хранение результата | Локальные JSON-файлы |
| Логи | Структурированные локальные логи без чувствительных данных |
| Тестирование | Unit для чистого разбора + fixture/contract tests |
| Зависимости | BCL и Microsoft.Playwright; дополнительные пакеты только по отдельному решению |

В Spike не добавляются DI-контейнеры, ORM, очереди, desktop UI framework и другие
инфраструктурные зависимости, если они не нужны для проверки гипотезы.

## 8. Минимальная структура прототипа

Прототип разделяется на независимые части:

- запуск браузера и управление профилем;
- навигация и ожидание наблюдаемого состояния;
- классификация страницы;
- адаптер поисковой выдачи;
- адаптер подробной карточки;
- типизация однозначных значений;
- формирование отчёта качества;
- безопасная диагностика;
- экспорт результата.

DOM-селекторы и правила Avito изолируются от запуска браузера и моделей
результата. Даже в Spike запрещено смешивать навигацию, извлечение полей и запись
JSON в одном большом классе.

## 9. Классификация страницы

До извлечения данных прототип обязан вернуть одно состояние:

| Состояние | Требуемая реакция |
|---|---|
| `SearchResults` | Разрешить извлечение выдачи |
| `ListingDetails` | Разрешить извлечение detail |
| `AuthenticationRequired` | Остановить задачу и запросить ручное действие |
| `Captcha` | Остановить задачу и запросить ручное действие |
| `RateLimited` | Завершить с контролируемой ошибкой; не повторять без решения человека |
| `ListingUnavailable` | Зафиксировать состояние только конкретного объявления |
| `SourceError` | Завершить с диагностикой |
| `Unknown` | Завершить с диагностикой; не возвращать пустой успех |

Критическое правило: отсутствие ожидаемого контейнера не означает, что
объявлений нет.

## 10. Данные уровня 1 — выдача

Для каждой карточки проверяется возможность извлечь:

- внешний ID объявления;
- прямой и нормализованный URL;
- заголовок;
- цену и исходный текст цены;
- цену за сотку, если она показана площадкой;
- площадь и исходный текст площади;
- назначение/категорию, если она видна;
- локацию;
- исходный текст даты публикации;
- краткое описание;
- имя и тип продавца, если присутствуют;
- badges и признаки профиля;
- URL или метаданные preview-изображения;
- позицию в основном контейнере;
- номер страницы или иной маркер продолжения;
- происхождение элемента: основной результат или иной блок.

Счётчик «найдено N» сохраняется отдельно и не считается количеством успешно
разобранных карточек.

## 11. Данные уровня 2 — карточка

Проверяется возможность извлечь:

- внешний ID и canonical URL;
- заголовок;
- цену и цену за единицу;
- площадь;
- структурированные характеристики;
- адрес и видимую локацию;
- координаты только при надёжном происхождении;
- полное описание;
- упомянутые кадастровые номера как заявление продавца;
- сведения о продавце и типе профиля;
- доступные способы связи без раскрытия телефона;
- badges и проверки площадки;
- дату публикации/изменения, если явно доступна;
- метаданные фотографий;
- доступность объявления;
- наличие и состояние каждого ожидаемого блока.

Противоречия вроде `8,4 сот.` в параметрах и `8,37 сот.` в описании не
исправляются и не усредняются: оба исходных значения сохраняются отдельно.

## 12. Модель качества значения

Каждое проверяемое поле должно различать:

- `NotInspected` — текущий проход поле не проверял;
- `Absent` — блок достоверно отсутствует в распознанной странице;
- `Empty` — блок есть, но значение пустое;
- `Present` — значение извлечено;
- `ParseFailed` — исходный текст найден, но типизация не удалась.

Для значения отдельно сохраняются исходный текст, типизированное значение и
коды предупреждений. Это правило проверяется в Spike, потому что от него зависит
безопасное обновление истории объявлений.

## 13. Контрольный набор

### Offline fixtures

Минимальный набор обезличенных HTML-фикстур:

- обычная выдача;
- выдача с рекомендациями или другими городами;
- следующая страница/прокрутка;
- повтор одного external ID;
- карточка частного продавца;
- карточка агентства;
- карточка с противоречивой площадью;
- снятое объявление;
- login page;
- CAPTCHA;
- source error;
- пустой основной контейнер;
- намеренно изменённая или неизвестная разметка.

Для каждой fixture фиксируются источник, дата, ожидаемый тип страницы и
ожидаемые ключевые значения. Cookies, токены, персональные сообщения и активные
сессионные данные удаляются.

### Live-набор

Для живой проверки используется небольшая репрезентативная выборка:

- 3–5 сохранённых поисковых ссылок с разным количеством результатов;
- сортировка по дате и стандартная сортировка, если обе реально используются;
- 20–30 подробных карточек разных продавцов и наполненности;
- минимум три временных окна в разные дни;
- повтор части объявлений для проверки воспроизводимости;
- последовательный запуск на втором Windows-компьютере.

Количество не является целью. При признаках ограничения исследование
останавливается раньше.

| E-06 | Live выдача | Ручная контрольная выборка и JSON | Полнота и загрязнение блоками |
| E-07 | Live detail | Страница и JSON | Полнота detail-полей |
| E-08 | Повторный запуск | Один URL в разные окна | Воспроизводимость |

Spike не исследует способы увеличения скорости ценой обхода ограничений.

## 15. Метрики

### Надёжность страницы

- доля корректно классифицированных страниц;
- число `Unknown`, CAPTCHA, login, rate limit и source error;
- число ложных успешных пустых результатов — должно быть нулевым;
- время навигации и ожидания готовности страницы;
- доля запусков, потребовавших ручного вмешательства.

### Качество выдачи

- число DOM-карточек основного контейнера;
- число успешно извлечённых карточек;
- доля карточек без external ID;
- полнота title, price, area, location и publication text;
- число дубликатов ID;
- число элементов из рекомендаций/других регионов, ошибочно принятых за основной
  результат;
- расхождение с ручной контрольной разметкой.

### Качество detail

- полнота каждого поля, а не один усреднённый процент;
- доля `ParseFailed`;
- доля корректно распознанных unavailable-состояний;
- число выявленных противоречий;
- различие результатов повторных проходов одной неизменившейся карточки.

### Эксплуатация

- время работы сессии;
- частота повторной авторизации;
- частота CAPTCHA/ограничений;
- различия между компьютерами;
- объём диагностических файлов;
- возможность объяснить каждую неуспешную попытку.

## 16. Предварительные пороги решения

Пороги являются начальными и уточняются до запуска live-части, но не меняются
задним числом ради положительного результата.

| Показатель | Минимум для `Go` |
|---|---|
| Классификация контрольных fixtures | 100% |
| Ложный успешный пустой результат | 0 случаев |
| External ID и direct URL в основном контейнере | не менее 99% карточек |
| Title и состояние price | не менее 98% карточек |
| Area и location | не менее 90% там, где поле визуально присутствует |
| Попадание рекомендаций/других регионов в основной результат | 0 подтверждённых случаев |
| Повторяемость неизменной fixture | 100% по значимым полям |
| Необъяснённые live-ошибки | 0; каждая имеет classification и диагностику |
| Работа на втором компьютере | ключевые сценарии воспроизведены |
| Секреты в JSON, логах и fixtures | 0 случаев |

CAPTCHA или rate limit сами по себе не измеряются как «допустимый процент», пока
не определён реальный рабочий режим. Для `Go` нужно подтвердить, что при
консервативной нагрузке они не делают регулярный сбор операционно бессмысленным.

## 17. Критерии решений

### `Go`

- обязательные пороги достигнуты;
- два уровня парсинга работают раздельно;
- постоянный профиль и ручные действия имеют понятный процесс;
- ошибки безопасно классифицируются;
- выбранный режим воспроизводится минимум на двух Windows-компьютерах;
- оценён реалистичный объём ручного сопровождения;
- нет необходимости в обходе защитных механизмов;
- определён минимальный контракт результата для FP-011–FP-013.

Решение: разрешить подготовку TP для промышленного адаптера и минимального
вертикального Server–Agent пути.

### `Conditional Go`

Подход технически работает, но требуется одно или несколько ограничений:

- только headed-режим;
- только авторизованный или только неавторизованный сценарий;
- уменьшенный набор полей;
- ручной запуск или ограниченные временные окна;
- меньшая частота detail-проходов;
- пилот на одном компьютере;
- обязательная ручная обработка части состояний.

Условия записываются как архитектурные и операционные ограничения. До их
принятия промышленная реализация не начинается.

### `No-Go`

- внешние ID или основной контейнер нельзя извлекать надёжно;
- защитные состояния систематически делают сбор непригодным;
- для работоспособности требуется запрещённый обход ограничений;
- неизвестная страница неотличима от пустого результата;
- второй компьютер не воспроизводит ключевой сценарий;
- диагностические данные нельзя безопасно отделить от секретов;
- ручное сопровождение сопоставимо с текущим ручным просмотром или тяжелее него.

Решение: не строить production Agent на этом подходе; рассмотреть разрешённый
импорт, ручное добавление ссылок, официальный канал данных или другой источник.

## 18. Этапы выполнения

### Этап 1. Подготовка

- утвердить вопросы, границы и стоп-условия;
- зафиксировать версии .NET, Playwright и Chromium;
- обезличить имеющиеся HTML-примеры;
- составить ручную эталонную разметку;
- определить лимиты live-сессии;
- подготовить изолированный тестовый browser profile.

### Этап 2. Offline parsing

- реализовать классификацию fixtures;
- реализовать извлечение выдачи;
- реализовать извлечение detail;
- сформировать field-level отчёт;
- доказать безопасный отказ на неизвестной разметке.

### Этап 3. Ограниченная live-проверка

- открыть одну поисковую ссылку в headed Chromium;
- сравнить DOM и сохранённый HTML;
- проверить основной контейнер;
- выполнить ограниченный detail-проход;
- повторить в разные временные окна;
- зафиксировать ручные вмешательства и ограничения.

### Этап 4. Переносимость

- воспроизвести согласованный набор на втором Windows-компьютере;
- сравнить версии браузера, сессию и результаты;
- определить минимальные требования к установке будущего Agent.

### Этап 5. Решение

- рассчитать метрики;
- перечислить подтверждённые и опровергнутые гипотезы;
- оформить ограничения и долги прототипа;
- принять `Go`, `Conditional Go` или `No-Go`;
- определить изменения для FP-001, FP-011, FP-012, FP-014 и OP-011.

## 19. Артефакты результата

По завершении должны существовать:

- исходный код экспериментального прототипа;
- README с однозначным запуском на Windows;
- lock/manifest фактически использованных версий;
- обезличенный набор fixtures;
- ожидаемые результаты fixture-тестов;
- JSON Schema или точное описание результата выдачи и detail;
- структурированные отчёты каждого эксперимента;
- таблица field-level completeness;
- журнал CAPTCHA, login, rate limit и unknown без чувствительных данных;
- перечень устойчивых и хрупких способов поиска элементов;
- перечень требований к browser profile;
- итоговый отчёт `SPIKE-001_RESULT.md`;
- одно зафиксированное решение `Go`, `Conditional Go` или `No-Go`.

## 20. Что разрешено переносить в промышленный код

Автоматически не переносится ничего. После `Go` проводится короткий review.

Можно перенести после проверки:

- типы page classification;
- модели raw/parsed/presence;
- очищенные fixtures и ожидаемые результаты;
- чистые функции типизации;
- подтверждённые правила отделения основного контейнера;
- коды ошибок и метрики;
- интерфейс границы source adapter, если он согласован с FP-012.

Нельзя переносить без переработки:

- временный CLI orchestration;
- абсолютные пути и локальные настройки;
- секреты и browser profile;
- бесконтрольные retries и задержки;
- экспериментальные селекторы без fixture-тестов;
- debug-сохранение полного HTML;
- код, смешивающий Playwright, parsing и файловую запись;
- любой механизм обхода защитных ограничений.

## 21. Риски и ответы

| Риск | Ответ |
|---|---|
| Разметка изменилась во время Spike | Версионировать fixture и adapter; считать это полезным испытанием |
| Сохранённый HTML не равен live DOM | Тестировать оба контура и явно фиксировать различие |
| CAPTCHA возникла на малой нагрузке | Остановить опыт, зафиксировать и оценить операционную пригодность |
| Аккаунт заблокирован | Не продолжать; использовать только согласованный безопасный сценарий |
| Успешен только один компьютер | `Conditional Go` до выяснения причины |
| Результат кажется хорошим на малой выборке | Не делать вывод без повторов в разные дни и ручной проверки |
| Прототип начал превращаться в продукт | Остановить расширение; вынести реализацию в TP после решения |
| Хочется сразу добавить Cian | Отдельный Spike после решения по первому источнику |

## 22. Definition of Ready

- настоящий план просмотрен владельцем продукта;
- определён исполнитель и ответственный за ручные действия;
- доступны две исходные HTML-страницы: выдача и карточка;
- выбраны 3–5 тестовых поисковых ссылок;
- определён допустимый browser profile;
- согласованы live-лимиты и стоп-условия;
- подготовлена изолированная рабочая папка без production-секретов;
- подтверждён второй Windows-компьютер либо явно оформлено исключение;
- текущие версии ADR-001 и FP-012 доступны исполнителю.

## 23. Definition of Done

- все обязательные эксперименты выполнены или имеют объяснённую остановку;
- каждая гипотеза получила статус `подтверждена`, `частично` или `опровергнута`;
- fixture-тесты воспроизводятся одной документированной командой;
- live-результаты сверены человеком;
- нет ложного пустого успеха;
- рекомендации и другие регионы не загрязняют основной результат;
- метрики рассчитаны по каждому значимому полю;
- CAPTCHA/login/rate limit/unknown различаются;
- диагностические материалы не содержат секретов;
- проверена переносимость на втором компьютере либо принято явное ограничение;
- подготовлен итоговый отчёт;
- владелец продукта зафиксировал `Go`, `Conditional Go` или `No-Go`;
- связанные планы актуализированы по результатам.
