# OP-001 — Локальная среда разработки

**Версия:** 0.1  
**Статус:** Черновик  
**Владелец:** технический владелец  
**Зависимости:** ADR-001, ADR-002, ADR-005, FP-001

## 1. Результат

Новый разработчик по одной инструкции поднимает Server, Worker, PostgreSQL и
локальное файловое хранилище, применяет миграции, создаёт тестового администратора
и запускает тесты. Процедура не требует общих Production-секретов и не зависит от
ручного редактирования базы.

Инструкция станет исполняемой после bootstrap репозитория. До этого документ
фиксирует обязательный состав и критерии, а не выдуманные команды/порты.

## 2. Поддерживаемые режимы

| Режим | Назначение |
|---|---|
| Server development | UI/API + Worker + инфраструктура в контейнерах |
| Agent development | локальный Agent, браузер и тестовый серверный контур |
| Integration tests | изолированные PostgreSQL/хранилище через контейнеры |
| UI/E2E | приложение и управляемые тестовые данные |

Server/Worker должны разрабатываться на Windows и Linux при наличии
поддерживаемого .NET SDK и контейнерного runtime. Целевая ОС Agent утверждается
отдельно; минимально проверяется фактическая ОС 3–5 рабочих компьютеров.

## 3. Предварительные требования

- закреплённый в `global.json` .NET SDK;
- Git;
- Docker Desktop, Podman либо другой утверждённый runtime;
- браузеры Playwright установленной репозиторием версии;
- Node.js только если реально нужен TypeScript build;
- доверенный локальный HTTPS certificate;
- отсутствие обязательного глобального `psql` и ручных SQL-скриптов.

`README` обязан ссылаться на одну официальную инструкцию, а не содержать вторую
расходящуюся последовательность.

## 4. Конфигурация и секреты

- Несекретные значения находятся в versioned Development-конфигурации.
- Секреты — в .NET user-secrets или локальном secret store; `.env` с секретами не
  коммитится.
- В репозитории есть `.env.example` только с именами и безопасными примерами.
- Production connection strings, Agent credentials и аккаунты источника не
  выдаются разработчику для локального запуска.
- Seed создаёт вымышленные данные и локальные роли.

## 5. Ожидаемый путь первого запуска

После bootstrap он должен сводиться к следующим действиям:

1. клонировать репозиторий и проверить закреплённый SDK;
2. поднять PostgreSQL и файловое хранилище одной compose-командой;
3. задать локальные секреты по шаблону;
4. применить миграции штатной командой приложения;
5. загрузить идемпотентный Development seed;
6. запустить Server и Worker;
7. открыть health и войти тестовым администратором;
8. при необходимости запустить Agent в Development-режиме;
9. выполнить unit, architecture и integration tests.

Финальные команды фиксируются в репозитории и проверяются CI. Если шаг нельзя
повторить автоматически, он считается долгом bootstrap-задачи.

## 6. Данные разработки

Seed содержит роли, одного администратора, несколько поисков, фиктивные задания,
объявления и историю цены. Он не копирует Production и не содержит реальные
телефоны, cookies, документы инвесторов или сырые страницы.

Повтор seed безопасен. Сценарии E2E создают данные через test API/factory и
очищают только собственную изолированную БД.

## 7. Миграции

- Разработчик не применяет SQL вручную для нормального запуска.
- Миграции создаются владельцем изменяемого модуля и проверяются review.
- Локальная команда может пересоздать только явно именованную Development-БД.
- Команда очистки обязана проверить окружение и отказаться работать не в
  Development/Test.
- Production migration выполняется только по OP-002.

## 8. Agent development

Agent имеет отдельный Development identity и отдельный браузерный профиль.
Поддерживаются запись фикстуры из разрешённой тестовой страницы и replay уже
сохранённого HTML без обращения к площадке. CAPTCHA не обходится; сценарий
эмулируется fixture/test page.

SQLite outbox располагается в документированной папке приложения. Для тестов
используется отдельный временный файл, чтобы не удалить реальные недоставленные
результаты разработчика.

## 9. Диагностика типовых проблем

Инструкция должна покрывать:

- занят порт;
- контейнер PostgreSQL не готов;
- не применена миграция;
- недоверенный HTTPS certificate;
- не установлен браузер Playwright;
- несовместим SDK/браузер/Agent contract;
- неверный локальный секрет;
- зависшая тестовая аренда;
- повреждённый локальный outbox.

Каждый совет начинается с безопасной проверки. Удаление volume/БД/outbox не
предлагается как первый способ исправления.

## 10. Проверка инструкции

- чистая виртуальная машина либо CI-job проходит путь с нуля;
- `dotnet build` и все обязательные тесты зелёные;
- повторный запуск compose/seed/migrate не ломает среду;
- секреты отсутствуют в Git и логах;
- Server/Worker корректно останавливаются;
- недоставленный Agent result сохраняется после перезапуска;
- документация соответствует поддерживаемым ОС.

## 11. Definition of Done

- реальные команды и версии добавлены после создания репозитория;
- CI повторяет сборку и тесты;
- один новый участник прошёл инструкцию без устных шагов;
- очистка ограничена локальными Development-ресурсами;
- troubleshooting проверен хотя бы на одном Windows Agent и серверной ОС.

## 12. Открытые вопросы

- целевые ОС разработки и Agent;
- выбранный контейнерный runtime;
- имя solution и локальные порты;
- нужен ли Node.js в первом вертикальном срезе.
