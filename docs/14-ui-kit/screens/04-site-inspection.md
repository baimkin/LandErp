# 04 — Осмотр участка

## Назначение

Мобильный экран полевого осмотра уже выбранного `PropertyCase`. Главная цель — дать сотруднику на участке быстро зафиксировать факты без длинного ручного текста: отметить пункт, ввести значение, снять фото/видео или надиктовать аудио.

Результат осмотра сохраняется в `PropertyCase` и затем просматривается руководителем в блоке проверок/материалов карточки объекта.

## Композиция экрана

Сверху показывается карточка объекта с основным фото и краткими данными. Фото не скрывается.

Ниже расположен общий блок материалов:

- фото;
- видео;
- аудио;
- текстовый комментарий.

Эти материалы относятся к осмотру в целом и не требуют привязки к конкретному пункту чек-листа.

## Чек-лист

Чек-лист выводится одним плоским логически отсортированным списком без визуальных групп, аккордеонов и выбора пункта из отдельного списка.

Для каждого пункта UI использует подходящий тип ответа:

- факт `Да / Нет`, где зелёный вариант означает норму, а красный — проблему;
- числовое значение + единица (`м`, `км` и т.п.);
- процент;
- выбор из справочных значений;
- составное значение, если это действительно нужно бизнес-процессу.

Подписи должны отражать фактический смысл. Например для болота: `Нет ✓ / Есть ×`, для газа наоборот: `Есть ✓ / Нет ×`.

Справа у каждого пункта находится `+`. Через него добавляются материалы именно к этому пункту:

- фото;
- видео;
- аудио;
- комментарий;
- отметка `Не проверено`.

## Поведение заполненных пунктов

После заполнения пункт автоматически уходит из рабочей части списка вниз, в подблок `Заполнено`.

В верхней части экрана поэтому всегда остаются только пункты, которые ещё требуют внимания. Это важно, поскольку реальный чек-лист может расширяться до нескольких десятков пунктов.

`Не проверено` считается обработанным состоянием и также переносится вниз, но должно визуально отличаться от подтверждённого ответа.

Заполненный пункт можно открыть повторно и изменить.

## Текущий состав демонстрационного чек-листа

В эталонном прототипе показаны, среди прочего:

- дорога до ближайшего населённого пункта;
- дорога до участка;
- рельеф;
- ближайший центр / население;
- расстояние до крупного города;
- наличие соседей;
- уровень деревни;
- наличие магазинов / ТЦ;
- наличие водоёмов;
- расстояние до ЛЭП;
- магистральный газ;
- зарастание участка;
- лес на участке;
- болото;
- проезд через другие участки;
- мёртвая деревня / отсутствие соседей;
- свалка / полигон / МСЗ / военная база;
- скотомогильник;
- кладбище;
- промышленные объекты / свалки до 1 км.

`Кадастровая стоимость` в полевой чек-лист не входит.

## Важное требование к backend/domain model

Состав чек-листа **не должен быть жёстко зашит в UI или production-код страницы**.

Пункты осмотра должны приходить из настраиваемого шаблона/справочника LandErp. Как минимум должны настраиваться:

- активность пункта;
- отображаемое название;
- порядок;
- тип ответа;
- допустимые варианты выбора;
- единицы измерения;
- семантика нормального/проблемного ответа;
- возможность прикладывать материалы;
- при необходимости обязательность пункта.

Это позволит добавлять, убирать и переставлять пункты без изменения кода страницы.

Демонстрационный массив пунктов внутри HTML-прототипа существует только для автономной работы прототипа и не является production-моделью данных.

## Голос и offline

В поле текстовый ввод вторичен. Аудиозаметка должна быть полноценным способом фиксации комментария. В дальнейшем допустима автоматическая расшифровка аудио в текст, при этом исходная аудиозапись должна оставаться доступной.

Черновик осмотра должен сохраняться локально при плохой связи. Конкретная production-реализация offline media/sync определяется отдельно; `localStorage` и `ObjectURL` из HTML-прототипа не являются техническим решением для production.

## UI reference

Утверждённый автономный прототип:

`docs/14-ui-kit/prototypes/landerp_site_inspection_flat_v5.html`

Прототип является эталоном композиции, плотности, порядка работы и interaction patterns. Demo-данные, JavaScript и локальное хранение из прототипа не должны копироваться как backend/business logic. Production-реализация должна использовать существующий Blazor UI, LandErp tokens/components и реальные данные `PropertyCase`.
