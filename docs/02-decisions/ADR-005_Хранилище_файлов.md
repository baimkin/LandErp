# ADR-005 — Хранилище файлов

**Статус:** Принято  
**Дата:** 6 сентября 2026 года  
**Владелец решения:** технический владелец и владелец данных  
**Затрагивает:** диагностику парсинга, документы, фото, InvestorPortal и backup

## 1. Решение

Бинарные файлы хранить во внешнем файловом или объектном хранилище, а в
PostgreSQL — метаданные, права, хеш, версию и непрозрачный ключ. Прикладной код
использует собственный узкий интерфейс `IFileStorage`, поэтому конкретный
провайдер и его API не проникают в доменные модули.

Для локальной разработки допустима файловая реализация с теми же контрактными
тестами. Production-файлы не размещаются на локальном диске Server и не
записываются BLOB в основную БД по умолчанию.

## 2. Классы файлов

| Класс | Пример | Особенность доступа |
|---|---|---|
| SourceEvidence | HTML, скриншот ошибки, диагностический фрагмент | только сотрудники с правом сбора; ограниченный retention |
| ListingMedia | фото объявления, если сохранение допустимо | происхождение, URL источника, политика площадки |
| DueDiligenceEvidence | выписка, карта, заключение, фото осмотра | доступ по объекту и роли |
| ProjectDocument | договор, смета, акт, отчёт | чувствительные данные и версии |
| InvestorPublication | опубликованная копия/версия документа | только назначенные инвесторы проекта |
| Export | временный отчёт/выгрузка | короткий срок и аудит скачивания |

Класс определяет допустимый размер, MIME, retention, проверку и аудит. Нельзя
разрешать публичное чтение общего каталога или смешивать права разных классов.

## 3. Модель метаданных

`StoredFile` содержит `Id`, `OwnerModule`, `Purpose`, `StorageKey`, исходное имя,
MIME, размер, SHA-256, статус, автора/источник и время. Связь с объектом хранит
модуль-владелец. Публикация инвестору — отдельная сущность с версией,
`PublishedAt`, `PublishedBy`, `RevokedAt`; она не меняет внутренний документ.

Состояния: `PendingUpload`, `Quarantined`, `Available`, `Rejected`, `Deleted`.
Удаление бизнес-связи не обязано немедленно физически удалить файл: действует
retention и legal hold.

## 4. Загрузка и скачивание

Первая безопасная реализация передаёт файлы через Server. Если выбранный backend
поддерживает короткоживущие подписанные ссылки, они могут быть добавлены позже
после отдельной проверки авторизации и класса файла. После загрузки Server
проверяет размер, MIME/signature, hash и завершает запись.

Перед каждым скачиванием инвесторского файла право проверяется заново. Ссылка
провайдера не становится публичным бизнес-URL. Имя объекта генерируется системой
и не содержит персональные данные.

## 5. Безопасность

- каталоги/buckets/containers закрыты от публичного чтения;
- шифрование при передаче и хранении;
- least privilege для Server/Worker;
- allowlist типов и лимиты размеров по назначению;
- защита от path traversal и подмены расширения;
- quarantine до проверки потенциально опасных документов;
- аудит загрузки, публикации, скачивания чувствительных файлов и отзыва;
- секреты доступа находятся в secret store окружения;
- резервные копии и lifecycle не заменяют бизнес-retention.

Антивирусный движок и способ проверки выбираются операционно. Пока он не выбран,
внешние исполняемые/макро-содержащие типы не допускаются в Production.

## 6. Сырые материалы парсинга

Полный HTML и скриншот не сохраняются при каждом успешном проходе бессрочно.
Предлагается:

- обязательная диагностическая выборка для ошибок/неизвестной разметки;
- настраиваемая контрольная выборка успешных проходов;
- редактирование/исключение cookie, токенов, переписки и лишних персональных данных;
- отдельный короткий retention, утверждаемый владельцем;
- ссылка из ParseRun/ExtractionReport на evidence.

Право и условия сохранения материалов площадки требуют отдельной юридической
проверки; техническая возможность не означает разрешение на сбор.

## 7. Рассмотренные варианты

| Вариант | Решение |
|---|---|
| Внешнее хранилище через `IFileStorage` + метаданные PostgreSQL | Принято |
| Яндекс Диск через официальный REST API | Рекомендуемый пилотный backend с ограничениями раздела 8 |
| S3-совместимое объектное хранилище | Целевой вариант при росте, требованиях к signed URL и lifecycle |
| Файлы на диске Server | Только Development; мешает масштабированию и восстановлению |
| BLOB в PostgreSQL | Допустим лишь для очень маленьких системных артефактов после обоснования |
| Публичные URL | Запрещены для внутренних и инвесторских данных |

## 8. Яндекс Диск в пилоте

Активную подписку Яндекс Диска на 1 ТБ можно использовать в пилоте. Адаптер
реализуется через официальный REST API обычным `HttpClient`; сторонний SDK/NuGet
для этого не добавляется. WebDAV допустим как резервный технический вариант, но
REST API предпочтительнее для явных операций, ошибок и метаданных.

Обязательные ограничения:

- отдельное приложение OAuth и ротируемый токен; предпочтительно отдельная
  служебная учётная запись, а не личная сессия владельца;
- доступ к файлам только через авторизованный Server, без публичных ссылок для
  сотрудников и инвесторов;
- в PostgreSQL сохраняются класс, владелец, версия, размер, SHA-256, статус и
  непрозрачный путь провайдера;
- Яндекс Диск не считается резервной копией: нужен отдельный проверяемый export
  или backup;
- в первом пилоте там допустимы диагностические HTML/скриншоты, фотографии и
  некритичные рабочие документы;
- договоры, персональные данные и финансовые документы инвесторов допускаются
  только после проверки модели доступа, восстановления, шифрования и юридических
  требований;
- должна существовать фоновая процедура сверки метаданных/хешей и последующей
  миграции в объектное хранилище без изменения бизнес-ID файлов.

Выбор Яндекс Диска как фактического backend пилота фиксируется настройкой среды и
операционной задачей; архитектура уже допускает его без изменения домена.

## 9. Переносимость провайдера

Интерфейс должен покрывать upload, read, delete marker, metadata и короткую
выдачу доступа, если backend её поддерживает, но не пытаться абстрагировать весь
API провайдера. Контрактные тесты идут против локальной и Production-реализации.
StorageKey не показывается как бизнес-ID и может измениться при миграции.

## 10. Резервное копирование и удаление

OP-003 согласует восстановление БД и объектов как единой временной точки.
Проверка восстановления включает существование файла, hash и разрешение доступа.
Физическое удаление выполняется фоново после retention и фиксируется аудитом.

## 11. Критерии исполнения решения

- утверждены классы, лимиты и начальный retention;
- подтверждён допустимый объём материалов источника;
- есть тест запрета чужого ProjectId и отозванной публикации;
- backup/restore проверяет БД и файлы совместно;
- контрактные тесты проходят для локального и выбранного Production-backend;
- секреты и персональные данные не попадают в имена объектов или логи.

## 12. Зафиксированное решение и открытые настройки

6 сентября 2026 года принят провайдер-независимый `IFileStorage` и хранение
метаданных/прав в PostgreSQL. Яндекс Диск признан допустимым и рекомендуемым
кандидатом для пилота. До отдельного подтверждения открыты фактическое включение
этого backend, retention по классам и перечень чувствительных документов.
