# OP-003 — Резервное копирование и восстановление

**Версия:** 0.1  
**Статус:** Черновик  
**Владелец:** владелец данных / эксплуатация  
**Зависимости:** ADR-003, ADR-005, OP-002

## 1. Результат

Команда умеет восстановить PostgreSQL, файлы и критичную конфигурацию в новый
контур, доказать целостность и вернуть работу по понятному runbook. Наличие
автоматической backup-задачи без проверенного restore не считается защитой.

## 2. Предлагаемые целевые показатели пилота

До отдельного бизнес-утверждения предлагаются:

- **RPO:** не более 1 часа для центральной БД;
- **RTO:** не более 4 часов для основного Server/Worker;
- файлы: восстановление согласуется с метаданными БД и не теряет опубликованный
  проектный документ после подтверждённой загрузки;
- локальный Agent outbox восстанавливается самим Agent после перезапуска и не
  является центральной backup-копией.

Эти значения — предложение для расчёта стоимости. Владелец может выбрать другой
баланс после оценки допустимого простоя и повторного ручного труда.

## 3. Что защищаем

| Набор | Метод | Проверка |
|---|---|---|
| PostgreSQL | managed backup + point-in-time recovery/WAL | restore в изолированный контур |
| Object storage | versioning/replication/lifecycle по классу | existence, size, hash, access |
| Конфигурация IaC/deploy | Git и защищённые артефакты | развёртывание чистого окружения |
| Секреты | возможности выбранного secret store | контролируемое восстановление/rotation |
| Agent package | immutable release artifact | hash и установка на тестовой машине |
| Локальный outbox | SQLite durability на устройстве | restart/crash test и повторная доставка |

Логи и метрики могут иметь собственный retention; они не заменяют аудит в БД.

## 4. Политика копий — предложение

- непрерывный WAL/PITR с окном не менее 7 дней;
- ежедневная полная/managed backup;
- 7 ежедневных, 4 еженедельных и 6 ежемесячных точек как начальный ориентир;
- отдельная защита от удаления/изменения учётной записью приложения;
- шифрование и географическое размещение по выбранным требованиям;
- object versioning и lifecycle по классам ADR-005;
- сохранение релизных артефактов, необходимых для восстановления совместимой
  версии приложения.

Финальные сроки зависят от стоимости, юридических требований и политики аудита.

## 5. Согласованная точка БД и файлов

Файл становится бизнес-доступным только после подтверждения загрузки и записи
метаданных. Восстановление на время T должно:

1. восстановить БД на согласованную точку;
2. предоставить версии объектов, существовавшие на T;
3. выявить метаданные без объекта и объект без метаданных;
4. сверить hashes для контрольной выборки и всех критичных документов;
5. оставить несогласованные файлы недоступными до разбора.

## 6. Сценарии восстановления

### Ошибочное удаление одной записи/публикации

Не выполняется прямой restore Production поверх текущей БД. PITR поднимается во
временный изолированный контур, нужные данные сравниваются и возвращаются
контролируемой операцией с аудитом.

### Повреждение схемы или массовых данных

Остановить записи/Worker, зафиксировать время, сохранить доказательства, выбрать
точку восстановления, поднять новый контур, проверить миграции и бизнес-smoke,
затем переключить трафик по утверждённому решению.

### Потеря объекта хранения

Восстановить нужную версию, сверить hash и права, только затем снять quarantine.
Если файл восстановить нельзя, метаданные не удаляются для сокрытия проблемы.

### Компрометация credential

Сначала отозвать/ротировать credential и ограничить доступ. Restore без устранения
причины не возвращает систему в безопасное состояние.

### Потеря Agent-компьютера

Отозвать Agent identity, перевыдать задания после lease expiry и зарегистрировать
новую машину. Неподтверждённый локальный outbox может быть потерян, поэтому
площадка повторно наблюдается; центральные подтверждённые данные не страдают.

## 7. Runbook восстановления

Runbook обязан содержать:

- критерий объявления инцидента и роли принимающих решение;
- точные идентификаторы окружения без широких destructive-команд;
- способ остановить новые записи и сохранить диагностику;
- выбор точки по времени и оценку потери;
- создание изолированного restore-контура;
- application/DB/files versions;
- проверки целостности и авторизации;
- бизнес-smoke: вход, поиск, lease/result, каталог, очередь менеджера, файл;
- решение о переключении, уведомление и журнал;
- post-incident review и устранение причины.

## 8. Проверка восстановления

- ежемесячный автоматизированный restore последней копии в изоляции;
- ежеквартальное учебное восстановление полного контура в пилотный период;
- отдельный тест PITR на выбранное время;
- тест удаления/восстановления версии файла;
- проверка Project scope после restore;
- измерение фактических RPO/RTO;
- отчёт содержит только отклонения, результат и действия — без бюрократической
  стенограммы.

Периодичность может быть упрощена после измерений, но первый успешный restore
должен состояться до хранения критичных инвесторских документов.

## 9. Безопасность копий

- backup identity отделена от приложения;
- доступ ограничен, MFA для операторов;
- копии зашифрованы;
- удаление/сокращение retention — критичная аудируемая операция;
- восстановленные данные не оставляются в тестовом контуре;
- restore из Production не раскрывает данные разработчикам;
- регулярная rotation ключей не делает старые допустимые копии невосстановимыми.

## 10. Definition of Done

- выбранные RPO/RTO утверждены и измерены;
- backup PostgreSQL и object storage включён;
- полный restore выполнен и задокументирован;
- рассогласование БД/файлов обнаруживается;
- права инвестора проверены после восстановления;
- назначены владельцы runbook и emergency-доступа;
- мониторинг сообщает о пропущенной или непроверяемой копии.

## 11. Требуется решение пользователя

Утвердить допустимую потерю данных/простой, сроки хранения аудита и бюджет
резервирования после выбора облака. До этого значения раздела 2 и 4 считаются
рекомендуемым стартовым ориентиром.
