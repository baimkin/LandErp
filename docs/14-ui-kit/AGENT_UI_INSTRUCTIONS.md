# Инструкция для UI-задач LandErp

Этот каталог содержит обязательный визуальный и поведенческий эталон интерфейса LandErp.

## Единый визуальный стандарт от 17 сентября 2026 года

Для размеров и адаптивности действует `docs/03-active/GATE-UI-CONSISTENCY.md`.
Старые размеры из HTML-прототипов не копировать: они остаются эталоном состава
блоков и действий, но не типографики. Общие значения находятся в `ui-kit/tokens.css`
и синхронном `src/LandErp.Server/wwwroot/css/tokens.css`.

- `--text-body` — основной текст/описания (16 px при базе 16);
  `--text-ui` — таблицы, кнопки, поля, меню (15);
  `--text-sm` — даты, подписи, пояснения (14);
  `--text-xs` — только короткие метки (12);
  `--text-section` — заголовки разделов (18);
  `--text-title`/`--text-metric` — заголовки страниц/показатели (28).
- Системный стек `--font-sans`, веса `--weight-normal/medium/semibold` (400/500/600).
  Произвольные page-local font-size/font-weight не добавлять. Компактность меняет
  `--control-h`, `--row-h`, `--row-rich-h`, `--cell-py`, `--panel-pad`, но не шрифт.
- Рабочие списки занимают ширину workspace с `--page-gutter`; ограничивать следует
  длину длинного текста/форм, а не всю страницу таблицы. Минимальная ширина таблицы
  сохраняется внутри локальной прокрутки, без уменьшения букв.
- Меню: expanded 248 px / compact 64 px; на узком экране — выездная панель с
  подписями. Использовать `--shell-sidebar-w` для привязанных к workspace элементов.
- Правые панели используют `--drawer-w`; заголовок/действия не сжимаются, основное
  содержимое прокручивается. На узком экране панель занимает доступную ширину.
- У длинных имён/адресов должны быть переносы; KPI и важные сведения не скрывать
  только ради компактного экрана. Фильтры и действия перестраивать, а не обрезать.

Для текущего Gate браузерные тесты отключены по прямому запросу владельца;
визуальная приёмка выполняется им вручную. Это исключение не отменяет проверки
адаптивности в будущих задачах.

## Перед задачей по конкретной странице

1. Прочитай этот файл.
2. Найди краткую спецификацию страницы в `docs/14-ui-kit/screens/`.
3. Прочитай связанные FP/ADR только в объёме, нужном этой странице.
4. Открой указанный в screen spec автономный HTML из `docs/14-ui-kit/prototypes/`.
5. Проверь общие токены и компоненты в `docs/14-ui-kit/ui-kit/`.

Приоритет источников для UI-задачи:

1. актуальный screen spec — бизнес-UX конкретной страницы;
2. reference HTML — композиция, визуал, плотность и interaction pattern;
3. FP/ADR — доменные правила, права, данные и архитектурные ограничения;
4. общий UI-kit — единый визуальный язык и переиспользуемые компоненты.

Если между ними есть реальное противоречие, не додумывай решение — укажи его владельцу до реализации.

## Обязательные правила реализации

- Основной стек: C#, .NET, Blazor и локальный CSS проекта.
- Reference HTML не вставляется в production целиком. Переноси экран в Razor-компоненты и существующую архитектуру LandErp.
- Demo-данные, mock-расчёты и JavaScript прототипа не являются доменной моделью или бизнес-логикой.
- Bootstrap не использовать как зависимость нового UI. Не добавлять Bootstrap JS, Tailwind, Material UI, внешние шрифты, CDN или UI-пакеты без отдельного согласования.
- Для нового production UI использовать собственные reset/base styles, design tokens и компоненты LandErp.
- JavaScript применять только там, где возможностей Blazor недостаточно; JS interop изолировать по компонентам.
- Не копировать произвольные цвета, отступы и размеры в страницы: использовать общие CSS custom properties и компоненты.
- Сохранять системный стек шрифтов; внешние шрифты не загружать.
- Цвет не должен быть единственным носителем смысла: статус сопровождается текстом или понятным значком.
- Для loading, empty, error, forbidden, stale и disabled предусматривать явные состояния.
- Формы должны иметь label и понятные validation/disabled состояния.
- Таблицы должны корректно работать с длинными значениями, пустыми полями, фильтрами, сортировкой, выбором и пагинацией там, где это нужно сценарию.
- Не менять общий визуальный язык ради одной страницы. Если общего компонента не хватает, сначала определить его контракт и только затем добавлять.
- Не расширять функциональность страницы сверх screen spec и связанных планов без явного решения владельца.

## Ориентир по Blazor-компонентам

```text
Components/
  Primitives/       кнопки, поля, статусы
  Feedback/         уведомления, ошибки, loading/empty
  Navigation/       меню, breadcrumbs, вкладки, пагинация
  DataDisplay/      таблицы, KPI, карточки, timeline
  Overlays/         dialog, drawer, confirmation
  Domain/           доменные UI-компоненты по мере необходимости
Layout/
  ErpLayout.razor
  InvestorLayout.razor
wwwroot/css/
  base.css
  tokens.css
  components.css
  pages.css
```

Это ориентир, а не разрешение создавать компоненты заранее. Компонент появляется, когда он нужен реальной функции и имеет понятный контракт.

## Критерии готовности UI-задачи

- экран соответствует своему screen spec и reference HTML;
- используются существующие backend/application contracts, а не mock-модель прототипа;
- нет новых внешних UI-зависимостей;
- повторяющиеся элементы вынесены в компоненты там, где это оправдано;
- проверены desktop, узкий desktop/tablet и заявленные mobile-сценарии;
- keyboard/focus/accessibility не потеряны;
- loading/empty/error/forbidden/disabled состояния предусмотрены;
- права проверяются сервером, а не только скрытием кнопок;
- бизнес-правила не размещены внутри визуальных компонентов;
- тесты покрывают значимое поведение, а не декоративную разметку.

## Короткий префикс задания агенту

> Реализуй страницу LandErp по её screen spec из `docs/14-ui-kit/screens/` и указанному там reference HTML из `docs/14-ui-kit/prototypes/`. Перед изменениями прочитай связанные FP/ADR и общие правила `docs/14-ui-kit/AGENT_UI_INSTRUCTIONS.md`. Reference HTML — визуальный и UX-эталон, но не production-код и не доменная модель. Используй Blazor, существующие backend contracts, tokens и компоненты LandErp. Bootstrap и новые внешние UI-зависимости не добавлять. Не расширяй функциональность страницы без согласования.

## Важно

Файлы в `ui-kit/` и `prototypes/` — эталоны интерфейса, а не готовая архитектура приложения. Авторизация, API, хранение данных, права и бизнес-правила реализуются в соответствующих слоях LandErp.
