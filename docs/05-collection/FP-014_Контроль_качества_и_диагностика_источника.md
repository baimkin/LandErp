# FP-014 — Контроль качества и диагностика источника

**Версия:** 0.1  
**Статус:** Черновик  
**Владелец:** администратор сбора / аналитик качества  
**Модули:** Collection, PropertyCatalog  
**Зависимости:** FP-012, FP-013, ADR-005  
**Блокирует:** безопасный массовый сбор и FP-015

## 1. Бизнес-результат

Изменение разметки, CAPTCHA или частичная загрузка страницы не превращаются в
массовое «объявления сняты» и не заполняют каталог правдоподобными, но неверными
данными. Администратор видит конкретное отклонение, приостанавливает затронутый
контур и проверяет диагностический материал.

## 2. Измеримый результат пилота

- для каждого ParseRun рассчитан отчёт качества;
- обязательные поля измеряются раздельно, без скрывающего среднего процента;
- новая версия адаптера проходит контрольный набор до включения;
- массовое исчезновение/обнуление блокирует применение опасных изменений;
- ошибка имеет Source, AdapterVersion, PageKind, SearchRevision и CorrelationId;
- человек может отличить проблему сайта от проблемы конкретного объявления.

Начальные пороги предлагаются в этом плане, но калибруются по контрольному набору
и первой неделе пилота. Они не считаются вечными бизнес-нормами.

## 3. Что входит

- классификация полученной страницы;
- extraction report с полнотой и предупреждениями;
- контрольные HTML-фикстуры и ожидаемые результаты;
- агрегаты по прогону, поиску, Agent и версии адаптера;
- anomaly rules и защитные блокировки;
- canary выпуска адаптера;
- ограниченное диагностическое evidence;
- ручное подтверждение возобновления;
- аудит изменения порогов и kill switch.

Не входят обход CAPTCHA, юридическое разрешение на сбор, автоматическая починка
селекторов и автоматическое бизнес-решение по участку.

## 4. Термины

| Термин | Значение |
|---|---|
| PageKind | SearchResults, ListingDetails, Captcha, AuthRequired, NotFound, Blocked, Unknown |
| ExtractionReport | поля, способ извлечения, предупреждения и оценка применимости результата |
| QualityRule | версионируемая проверка одного конкретного риска |
| QualityIncident | подтверждённое отклонение, требующее реакции/наблюдения |
| Fixture | сохранённый обезличенный пример страницы с ожидаемым результатом |
| Canary | ограниченный запуск новой версии без массового применения |

## 5. Уровни проверки

### 5.1. До извлечения

Проверяются HTTP/навигация, конечный URL, видимость ожидаемого контейнера,
PageKind, CAPTCHA/auth и признаки неполной загрузки. Неизвестная страница не
обрабатывается как пустая выдача.

### 5.2. Отдельная запись выдачи

Для найденного объявления обязательны стабильный внешний ID/URL, заголовок и
цена либо явное состояние «цена не указана». Площадь, адрес, продавец и дата
могут быть неизвестны, но отсутствие получает причину, а не значение по умолчанию.

### 5.3. Подробная карточка

Проверяется согласованность ID/URL, наличие ключевого контейнера, разбор цены и
единиц, признаки объявления/ошибки и допустимость каждого извлечённого поля.
Противоречие с выдачей сохраняется как два наблюдения, а не стирается.

### 5.4. Прогон

Сравниваются количество карточек, доли обязательных полей, дубликаты ID, новые/
исчезнувшие ID, структура ошибок, длительность и изменение относительно последних
успешных прогонов той же SearchRevision.

## 6. Начальные защитные правила

Предложение для пилота:

- `ExternalId/CanonicalUrl` извлечён минимум у 99% распознанных карточек;
- `Title` и корректный тип цены — минимум у 95%;
- доля дубликатов внешнего ID в одной выдаче — не более 1%;
- падение числа результатов более чем на 50% относительно медианы последних
  успешных прогонов переводит результат в review, если это не объяснено фильтром;
- PageKind Unknown/Captcha/AuthRequired никогда не подтверждает отсутствие;
- три последовательных структурных сбоя одного адаптера включают source/revision
  pause по политике;
- один корректный `NotFound` недостаточен для массовой смены статусов.

Порог применяется к конкретному правилу. Красный `ExternalId` нельзя скрыть
зелёной полнотой второстепенных полей.

## 7. Применение результата

| Оценка | Действие |
|---|---|
| Accepted | сохранить наблюдения и обновить разрешённые актуальные поля |
| AcceptedWithWarnings | сохранить факты, показать предупреждение, не делать рискованных выводов |
| Quarantined | сохранить сырой результат/evidence, не обновлять актуальное представление |
| Rejected | не применять данные, зафиксировать причину |
| AttentionRequired | остановить соответствующий поток и создать действие администратору |

Качество конкретного поля может отличаться от качества всего документа.

## 8. Модель данных

- `ExtractionReport`: TaskId, ResultId, AdapterVersion, PageKind, ruleset version,
  field results, warnings, evidence reference;
- `QualityEvaluation`: правило, факт, порог, outcome;
- `QualityIncident`: scope, severity, state, owner, first/last occurrence;
- `AdapterRelease`: version, fixture result, canary state, enabled scopes;
- `SourceControlState`: active/paused scope, reason, actor, expiry/review time.

Состояния incident: `Open`, `Acknowledged`, `Monitoring`, `Resolved`, `FalseAlarm`.
Закрытие сохраняет причину и ссылку на исправление/решение.

## 9. Контракты

Agent возвращает наблюдаемые признаки и ExtractionReport, но итоговую политику
применения решает Server. Это позволяет изменить пороги без одновременного
обновления 3–5 машин.

Эталон формы результата:

```csharp
public sealed record FieldExtraction<T>(
    string Field,
    T? Value,
    ExtractionStatus Status,
    string Method,
    IReadOnlyList<string> Warnings);

public sealed record ExtractionReport(
    string AdapterVersion,
    PageKind PageKind,
    IReadOnlyList<FieldExtraction<object>> Fields,
    IReadOnlyList<string> DocumentWarnings);
```

Контракт не передаёт DOM как доверенную бизнес-модель. Большое evidence загружается
по ADR-005, а в результате хранится ссылка.

## 10. Административный поток

1. Система создаёт/обновляет QualityIncident.
2. FP-015 показывает влияние: поиски, задачи, Agent и число quarantined results.
3. Администратор смотрит правила и безопасный фрагмент evidence.
4. Он оставляет pause, запускает один диагностический retry либо выбирает
   исправленную AdapterRelease для canary.
5. Canary проходит на fixture и ограниченном поиске/Agent.
6. После нормальных метрик администратор расширяет включение.
7. Incident закрывается с причиной и аудитом.

## 11. Fixture-набор и выпуск адаптера

Набор включает выдачу с разными карточками, подробную карточку, удалённое
объявление, CAPTCHA/auth, неполную страницу и ранее ломавшуюся разметку. Fixture
обезличивается и не содержит активных cookies/токенов.

Любое изменение extractor обновляет ожидаемый результат осознанно. Массовое
автоматическое принятие нового snapshot запрещено. Release сначала проходит все
фикстуры, затем один canary scope, и только после этого становится основной.

## 12. Безопасность и данные

- диагностические материалы доступны только разрешённым ролям;
- cookie, authorization headers, чат и лишние персональные поля редактируются;
- retention задаётся классом SourceEvidence;
- скачивание и публикация evidence аудируются;
- содержимое страницы считается недоверенным вводом и экранируется;
- текст ошибки не может содержать секрет Agent.

## 13. Наблюдаемость

Метрики: result outcome, полнота каждого ключевого поля, PageKind, quarantine,
incident count/age, fixture pass, canary error rate, pause duration и recovery.
Алерт создаётся на отклонение, требующее действия, а не на каждую единичную
ошибку пользователя/объявления.

## 14. Тесты

- unit-тест каждого QualityRule;
- fixture/regression каждого PageKind;
- интеграционный тест quarantine без обновления каталога;
- ложное массовое NotFound не снимает объявления;
- изменение порога имеет аудит;
- pause не выдаёт новые затронутые задания;
- canary не меняет основной адаптер;
- evidence не содержит тестовых секретов;
- поздний качественный результат корректно снимает incident по политике.

## 15. Вертикальные этапы

1. ExtractionReport и field-level результаты для одной карточки.
2. Агрегат качества одного SearchRun.
3. Quarantine и запрет ложного снятия.
4. Incident + pause/resume.
5. Fixture gate и AdapterRelease.
6. Canary и административная диагностика.

## 16. Definition of Ready

- утверждены поля первого адаптера и PageKind;
- есть исходные HTML-примеры выдачи и карточки;
- согласована минимальная политика evidence;
- FP-012/013 определили идемпотентность наблюдений.

## 17. Definition of Done

- каждый результат имеет отчёт качества;
- неизвестная страница не создаёт ложное отсутствие;
- защитные правила проверены на фикстурах;
- pause/resume и изменение порогов аудируются;
- новая AdapterRelease проходит fixture + canary;
- администратор понимает причину без доступа к БД;
- фактические пороги откалиброваны и записаны как решение.

## 18. Открытые вопросы

- допустимость и retention HTML/скриншотов;
- кто подтверждает новую AdapterRelease;
- какие поиски войдут в контрольную выборку;
- сколько корректных проверок нужно для подтверждения снятия объявления.
