# ADR-002 — Структура решения и границы модулей

**Статус:** Принято  
**Дата:** 6 сентября 2026 года  
**Владелец решения:** технический владелец  
**Затрагивает:** весь серверный код, Worker, Agent, тесты и структуру репозитория

## 1. Решение

Развивать Land ERP как модульный монолит с отдельными исполняемыми приложениями:

- `LandErp.Server` — HTTP API и Blazor Web App;
- `LandErp.Worker` — расписания, очередь и фоновые процессы;
- `LandErp.Agent` — локальное приложение сбора;
- `LandErp.AgentContracts` — версионируемые контракты Server–Agent;
- серверные доменные модули с Vertical Slices;
- отдельные проекты тестов и архитектурных проверок.

На первом этапе Server и Worker используют одну PostgreSQL и один основной
`DbContext`, но таблицы, команды и события имеют явного владельца-модуль.
Переход к нескольким контекстам или сервисам допустим только по отдельному ADR.

## 2. Контекст

ERP будет расти от парсинга к работе менеджера, проверкам, проектам, финансам и
кабинету инвестора. Один слой `Services` быстро смешает правила этих областей,
а ранние микросервисы усложнят транзакции, развёртывание и поддержку небольшой
команды. Нужны физически проверяемые границы без лишней распределённости.

## 3. Модули верхнего уровня

| Модуль | Владеет | Не владеет |
|---|---|---|
| IdentityAccess | пользователи, роли, проектный доступ, Agent identity | бизнес-статусы объектов |
| Administration | настройки, справочники, Agent registry, feature flags | задания сбора и объявления |
| Collection | поиски, ревизии, расписания, задания, прогоны, результаты агента | решение менеджера по объекту |
| PropertyCatalog | объявления, наблюдения, история цены, PropertyCase, связи | проверки и бюджеты проектов |
| ManagerWorkspace | очередь решений, назначения, комментарии, напоминания | исходные факты объявления |
| DueDiligence | проверки, вопросы, доказательства, выводы специалиста | данные источника как таковые |
| ProjectsFinance | сделки, проекты, работы, лоты, бюджеты, движения | внешняя публикация инвестору |
| InvestorPortal | назначения инвесторов и опубликованные представления | изменение внутренних финансов |
| Reporting | согласованные read models и агрегаты | первичные транзакционные данные |

`Reporting` не получает право записывать в таблицы модулей. InvestorPortal читает
только подготовленные для публикации данные, а не внутренние таблицы проектов.

## 4. Направление зависимостей

Внутри модуля допустим путь `Endpoint/UI → Application → Domain`. Infrastructure
реализует интерфейсы Application и регистрируется на внешней границе.

Запрещено:

- ссылаться на `Internal` другого модуля;
- вызывать handler другого модуля как метод;
- читать чужие EF entities для обхода публичного контракта;
- помещать бизнес-логику в Server, Worker или универсальный `Common`;
- создавать циклические ссылки проектов.

Между модулями используются публичные команды, события или согласованный read
model. Синхронный контракт применяется, когда ответ нужен для текущего решения;
событие — когда потребитель может обработать факт после транзакции владельца.

## 5. Вертикальные срезы

Каждый use case хранит рядом command/query, validator, handler, endpoint,
контракт ответа и профильные тесты. Общий код появляется только при реальном
повторном использовании, а не заранее.

Предлагаемый ориентир:

```text
Modules/Collection/
  Public/
  Internal/Searches/CreateSearch/
  Internal/Searches/ReviseSearch/
  Internal/Tasks/LeaseTask/
  Domain/
  Infrastructure/
```

Рабочее имя решения и корневой namespace утверждены как `LandErp`. Проекты,
публичные контракты и пространства имён используют этот префикс. Читаемое имя
продукта в интерфейсе — `Land ERP`.

## 6. Данные и транзакции

- Одна физическая база упрощает атомарный первый контур.
- Таблицы группируются по схемам модулей либо по строгому префиксу; вариант
  выбирается в bootstrap-задаче.
- Конфигурации EF располагаются у модуля-владельца.
- Чужой модуль не изменяет entity через navigation property.
- Интеграционное событие создаётся в той же транзакции через transactional outbox.
- Миграции выпускаются единым упорядоченным набором приложения.

## 7. Рассмотренные варианты

### A. Один DbContext и проверяемые модульные границы — рекомендуется для старта

Плюсы: простые транзакции, миграции и диагностика. Минус: границы нужно защищать
архитектурными тестами и ревью, иначе они останутся договорённостью.

### B. DbContext на каждый модуль

Границы заметнее, но межмодульные транзакции, миграции и общие соединения сложнее.
Имеет смысл, если команда начнёт независимо развивать несколько крупных модулей.

### C. Микросервисы

Не принимается для первой версии: стоимость надёжной доставки, наблюдаемости,
совместимости контрактов и эксплуатации выше текущей пользы.

## 8. Автоматические ограничения

Архитектурные тесты проверяют:

- разрешённые project references;
- отсутствие циклов между модулями;
- запрет зависимости Public-контрактов от Infrastructure/EF/UI;
- запрет возврата EF entities через API;
- отсутствие ссылок Agent на серверные проекты и драйвер PostgreSQL;
- отсутствие межмодульного доступа к namespace `Internal`.

## 9. Когда пересматривать решение

ADR пересматривается, если появляются независимо выпускаемые команды, разные
требования масштабирования, конфликтующие циклы релизов или доказанная проблема
одного DbContext. Размер таблицы или желание «сделать современно» сами по себе не
являются основанием для микросервиса.

## 10. Критерии принятия

- согласован список модулей и их владельцы данных;
- выбраны имя solution/namespace и способ группировки таблиц;
- минимальный каркас проходит архитектурные тесты;
- FP-001 не противоречит физической структуре;
- владелец продукта понимает, что статус ADR не выбирает облако или UI-дизайн.

## 11. Зафиксированное решение

6 сентября 2026 года принят вариант A: модульный монолит, отдельные
`LandErp.Server`, `LandErp.Worker`, `LandErp.Agent`, один основной `DbContext` на
старте и проверяемые владельцы данных. Имя solution и корневой namespace —
`LandErp`.
