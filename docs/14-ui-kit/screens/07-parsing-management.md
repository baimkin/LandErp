# 07 — Поиски и парсинг

**Статус:** approved UI reference  
**Экран:** серверное управление поисковыми ссылками, расписанием, общей очередью и состоянием локальных парсеров  
**UI reference:** `docs/14-ui-kit/prototypes/landerp_parsing_management_v1_3.html`

## Назначение

Экран управляет тем, **что и когда собирать**, но не назначает конкретный компьютер на конкретный поиск.

Целевой поток:

`SearchConfiguration -> расписание -> ServerCollectionJob(Pending) -> общий пул Collector Agent -> Claim/Lease -> результат -> единый список "Входящие объявления"`

Все найденные объявления организации поступают в общий входящий список. Маршрутизация результата в `Department`/`Team` на уровне поисковой ссылки не используется.

Эта спецификация фиксирует только **серверную часть**. Внутреннее устройство локального Parser/Collector Agent, браузерная автоматизация, cookies/session, CAPTCHA flow и клиентские retry здесь сознательно не проектируются.

## SearchConfiguration

Целевая поисковая ссылка описывает только сам поиск:

- `Id`;
- `OrganizationId`;
- `SearchGroupId?`;
- `Label`;
- `Source`;
- `Url`;
- `MaxPages`;
- `Enabled`;
- типизированные параметры расписания;
- `NextRunAt` и служебные поля планировщика;
- optimistic concurrency / audit fields по действующим соглашениям проекта.

В `SearchConfiguration` **не должно быть** обязательных `AgentId`, `DepartmentId`, `TeamId` и другой логики назначения конкретного исполнителя.

Поиск не владеет найденным `Listing` и не определяет менеджера/команду. Происхождение данных сохраняется через `CollectionJob` / `ListingObservation`.

## Группы поисков

`SearchGroup` нужен только для удобной организации 30–50+ ссылок: `Королёв`, `Химки`, `Раменское` и т.п.

Группа принадлежит организации, имеет стабильный ID, имя, порядок сортировки и active/archive flag. Она **не содержит расписания, не назначает Agent, отдел или команду и не наследует настройки на дочерние ссылки**.

Предпочтительно использовать существующую систему справочников, если она уже поддерживает типизированный справочник уровня организации, стабильные ID, сортировку и архивирование. Тогда завести тип `SearchGroup` / `Группы поисков` и не создавать отдельный сложный aggregate.

Если существующий справочник этих требований не обеспечивает, допустима маленькая `collection.search_groups`. Не расширять общий справочный механизм специально ради этой страницы.

Используемую группу не удалять физически: архивировать. Для старых данных допустима `SearchGroupId = null` / `Без группы`.

## Расписание

Расписание хранится на сервере и только создаёт задания в общей очереди. Для Stage 1 достаточно:

1. `Interval` — каждые N минут/часов/дней;
2. `FixedTimes` — список локальных времён (`08:00, 14:00, 20:00`);
3. `Manual` — только ручной запуск.

Не хранить UI-строку вроде `Каждый час` как источник истины и не требовать cron-expression от пользователя. Сервер хранит типизированные параметры, display text формируется отдельно.

Часовой пояс берётся из настроек организации; `NextRunAt` хранится/вычисляется в UTC.

Планировщик:

- выбирает включённые поиски с наступившим `NextRunAt`;
- создаёт `Pending` job;
- не создаёт второй активный job того же поиска при существующем `Pending`/`Leased`;
- пересчитывает следующий запуск;
- `Запустить сейчас` использует тот же enqueue path.

## Общая очередь и Claim

`ServerCollectionJob` при создании **не назначается конкретному Agent**.

- `SearchId` обязателен;
- `AgentId` / `ClaimedByAgentId` = `null` в `Pending`;
- первый enabled + registered Agent с подходящим capability может взять job;
- Agent записывается атомарно только в момент `Claim`;
- одновременно создаются `LeaseId` и `LeaseExpiresAt`;
- после истечения lease незавершённый job может получить другой совместимый Agent;
- завершённый job навсегда хранит фактического исполнителя.

Существующие короткие транзакции, `FOR UPDATE ... SKIP LOCKED`, lease fencing и idempotent delivery сохранить: они хорошо подходят для общего worker pool.

При выборе работы учитывать `OrganizationId`, `SearchConfiguration.Enabled`, `Pending`/просроченный `Leased` и capability Agent для `Source`.

## Результаты и входящие объявления

Каталог продолжает идентифицировать объект по действующей natural identity: `Organization + Source + ExternalId`.

**Все результаты идут в единый экран "Входящие объявления".**

Не копировать из поисковой ссылки в `Listing`: `DepartmentId`, `TeamId`, `AgentId`, `SearchGroupId`.

Назначение менеджера/команды начинается уже в рабочем контуре входящих и закупки. Один объект может встретиться в нескольких поисках: это не создаёт несколько бизнес-объектов; происхождение видно по jobs/observations.

## Метрики и read-model страницы

Для каждой ссылки сервер отдаёт:

- последнее выполнение;
- фактический Agent;
- state/result code;
- обработано;
- новых объявлений;
- изменившихся объявлений;
- следующий запуск.

`NewListingsCount` и `ChangedListingsCount` считать на сервере при применении результата к каталогу; UI не должен вычислять это из observations.

Строка группы агрегирует **последний завершённый запуск каждого поиска группы**:

- количество поисков / active / paused;
- источники;
- `Разные`, если расписания отличаются;
- последний запуск = max;
- обработано / новых / изменений = сумма последних запусков дочерних поисков;
- ближайший запуск = min `NextRunAt`;
- `Требует внимания`, если хотя бы один последний релевантный job имеет `AwaitingManualAction` или `Failed`.

История обработки показывает отдельные jobs и фактический Agent. `LeaseId`, raw error, correlation id и другие технические поля доступны в деталях/аудите, но не являются основным UI.

## Состояние локальных парсеров на сервере

На этой странице сервер показывает только операционную сводку: имя, enabled/revoked, online/offline по heartbeat, версия/capabilities, свободен/выполняет job, требует внимания при соответствующем source/job status.

Точная логика локального приложения при CAPTCHA/авторизации/блокировках будет отдельно пересмотрена вместе с Agent.

## Токены

Серверная модель токенов остаётся простой:

- создать credential;
- raw token вернуть один раз;
- хранить только hash;
- rotate;
- revoke;
- audit.

Создание токена не связывает Agent ни с одной поисковой ссылкой.

## Создание поиска из локального приложения

Сервер должен разрешать создание обычной `SearchConfiguration` как из web UI, так и из авторизованного локального приложения.

Обе точки входа используют одну application command/validation: organization scope, `Label`, `Source`, `Url`, `MaxPages`, `SearchGroupId?`, schedule и audit origin (`WebUser` / `CollectorAgent`).

Поиск, созданный локальным Agent, **не становится его поиском**. Он попадает в общий пул и впоследствии может исполняться любой свободной совместимой машиной.

Для Stage 1 локальное приложение выбирает существующую группу или оставляет поиск без группы; создание новых групп самим Agent не требуется.

## Права и аудит

Использовать существующие Collection/Agents permissions, не вводя новую модель доступа только ради страницы.

Аудитировать создание/изменение/архивирование группы; создание/изменение/включение/паузу поиска; расписание; ручной enqueue; create/rotate/revoke token. Claim/completion/error job остаются частью технической истории.

## Дельта относительно текущего Collection-модуля

Перед production-реализацией страницы серверную модель нужно упростить:

1. убрать `AgentId` из `SearchConfiguration`;
2. убрать `DepartmentId` и `TeamId` из `SearchConfiguration`;
3. убрать обязательный Agent из `CreateSearch`;
4. `ServerCollectionJob.AgentId` сделать nullable до `Claim`;
5. `Enqueue` создаёт общий `Pending` job без Agent;
6. `Claim` больше не фильтрует `j.agent_id = currentAgent`, а атомарно выбирает совместимый job организации;
7. при `Claim` записывается фактический Agent + lease;
8. добавить серверное расписание и `NextRunAt`;
9. добавить `SearchGroupId?`;
10. read-model дополнить group summaries, next run и понятными result counters;
11. новые Listings больше не получают Department/Team из SearchConfiguration.

Существующие authentication/token hash, heartbeat, capability registration, lease, `SKIP LOCKED`, idempotency и catalog observations сохранять, если отдельный аудит Agent не даст конкретной причины их менять.

## Миграция

- старые `SearchConfiguration.AgentId` перестают использоваться для назначения работы;
- существующим searches можно оставить `SearchGroupId = null` до ручной группировки;
- безопасный default для старых searches без расписания — `Manual`;
- старые незавершённые `Pending` jobs можно освободить от Agent assignment;
- завершённые jobs сохраняют старый `AgentId` как исторический факт;
- `Listing`, `ListingObservation` и их история не пересоздаются.

## Вне этой спецификации

Браузер и парсинг Avito/Cian, CAPTCHA handling, cookies/session, client retry, локальная очередь, auto-update и другая внутренняя логика Parser Agent. Эти вопросы согласуются отдельно при очистке локального приложения.
