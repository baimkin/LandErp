# 10 — Обзор

**Статус:** approved UI reference  
**Экран:** главная операционная страница LandErp  
**UI reference:** `docs/14-ui-kit/prototypes/landerp_overview_v1_4_market_per_group_production_fonts.html`

Версия v1.4 заменяет v1.2 как визуальный authority. Диалоги и расширенные окна,
добавленные для рабочих сценариев, используют ту же production typography.

## Назначение

`Обзор` — не страница-ссылочник и не декоративный дашборд. Это рабочий стол, который за несколько секунд отвечает на три вопроса:

1. что происходит в закупке сейчас;
2. где требуется внимание;
3. что конкретно должен сделать текущий пользователь.

Старые крупные карточки-ссылки `Закупка / Сотрудники / Аудит` убрать. Эти разделы уже доступны из основной навигации.

## Компоновка

Верхняя строка содержит четыре операционных показателя:

- `Новые входящие`;
- `В закупке`;
- `Требуют внимания`;
- `Ждут решения`.

Основная область разделена на две ровные колонки.

Между верхними показателями и двухколоночной областью расположен полноширинный
блок `Рынок по группам поиска`.

Левая, более широкая:

- `Требует внимания`;
- `Закупка сейчас`;
- `Моя работа`.

Правая:

- `Сбор данных`;
- `Быстрые действия`;
- `Команда закупки`.

Внутри карточек строки и значения должны иметь общую сетку и единые внутренние отступы. Не центрировать списки внутри правой колонки: индикатор, название и правое значение должны образовывать стабильные вертикальные линии.

## Показатели

### Новые входящие

Количество новых входящих предложений в общем Catalog, которые ещё не обработаны менеджером.

Catalog является универсальным входящим потоком: Avito, Cian, Telegram, ручное добавление и будущие источники.

### В закупке

Количество активных внутренних объектов закупки (`PropertyCase` в коде), находящихся в рабочем цикле и ещё не завершённых как `Куплено`/отклонено.

### Требуют внимания

Не просто сумма ошибок. Сюда входят только ситуации, где человеку действительно нужно действие, например:

- просрочено следующее действие;
- объект возвращён руководителем на доработку;
- объект долго стоит без следующего шага;
- сбор данных требует ручного вмешательства;
- важные новые входящие требуют разбора.

Каждая строка должна вести в конкретный объект/поиск/рабочий экран.

### Ждут решения

Объекты, ожидающие явного решения руководителя закупки или другого согласующего пользователя.

## Блок «Требует внимания»

Сортировка по приоритету и сроку: критичные и просроченные выше.

Для каждой строки:

- понятное имя объекта или поиска;
- краткая причина;
- срок/состояние;
- следующее предлагаемое действие;
- переход непосредственно к месту работы.

Не показывать GUID, enum, внутренний action code или имя класса.

## Блок «Рынок по группам поиска»

Для каждой активной Search Group показываются медианная и средняя цена за сотку,
размер фактически включённой выборки, число отсечённых настройками объявлений и
отдельное число исключённых `Фейк`, если оно ненулевое. Компактный блок ограничен
пятью строками; `Посмотреть все группы` открывает постраничный список.

Шестерёнка строки доступна только при праве управления сбором данных и меняет
только выбранную группу: период `7 / 30 / 90 / 180`, разрешённые типы участков,
минимальную и максимальную цену за сотку. Диалог сохраняет production typography
эталонного макета.

Расчёт выполняется сервером. Исходная выборка — уникальные source listings,
наблюдавшиеся поисками группы за настроенный период. Текущее положение объявления
в процессе, включая архивные/отклонённые рабочие состояния, не исключает его.
`Fake / Фейк` не участвует в median, average или IncludedCount и учитывается
отдельно от статистического отсечения. UI не получает массив объявлений для
клиентского пересчёта.

## Блок «Закупка сейчас»

Компактная воронка состояния текущего потока:

`Входящие → В работе → Глубокая проверка → Решение → Куплено`

`Куплено` на главной рекомендуется показывать за ограниченный период, по умолчанию последние 30 дней, чтобы показатель оставался операционным.

Это не аналитический BI-график. Здесь важны текущие объёмы и быстрый переход в соответствующий список.

## Блок «Моя работа»

Показывает ближайшие действия по объектам, за которые отвечает текущий пользователь:

- объект;
- текущий этап;
- следующее действие;
- короткий контекст;
- срок;
- признак просрочки.

Обычный сотрудник видит только доступный ему контур. Руководитель/владелец также может перейти к общей очереди.

## Блок «Сбор данных»

Только короткая операционная сводка, без дублирования полной страницы управления:

- сколько сборщиков работает;
- количество активных поисков;
- сколько записей обработано сегодня;
- последний успешный сбор;
- поиски/сборщики, требующие внимания;
- время последнего нового предложения.

Полное управление остаётся на отдельной странице `Сбор данных`.

## Блок «Быстрые действия»

Stage 1:

- `+ Добавить предложение`;
- `Открыть входящие`;
- `Очередь закупки`;
- `Мои объекты`.

Не дублировать здесь `Организацию`, `Аудит` и техническое администрирование.

## Блок «Команда закупки»

Показывается только пользователям, которым по правам доступна командная картина.

Минимум:

- сотрудник;
- число активных объектов;
- краткий индикатор проблем, например `1 просрочен`.

Это индикатор загрузки, а не отдельный отчёт производительности.

## Ролевая видимость

Один и тот же экран адаптируется существующими permissions/scope:

- менеджер видит прежде всего свои объекты, свои действия и доступные ему входящие;
- руководитель видит ожидания решений, командную загрузку и доступный ему отдел/команду;
- Owner/организационный администратор может видеть организационный итог.

Не создавать отдельные версии главной страницы для каждой роли.

## Обязательное правило терминологии UI

Пользовательский интерфейс **не должен напрямую выводить внутренние имена сущностей, enum и технические состояния**.

Примеры:

- `PropertyCase` → `объект закупки`, `объект в работе` или нормальное имя объекта;
- `Collector` / `CollectorAgent` → `сбор данных`, `сборщик` или `парсер` по контексту;
- `CollectionJob` → `задание на сбор данных`;
- `AwaitingManualAction` → `требует ручного действия`;
- `AccessScope.Organization` → `Вся организация`;
- `DD` → `глубокая проверка` / `юридическая проверка`;
- GUID и correlation id не показываются в обычном UI.

Внутренние названия допустимы только в явно технических/диагностических деталях для администратора или разработчика.

Это правило относится не только к `Обзору`, а ко всему LandErp.

## Server read model

Для главной страницы нужен отдельный серверный read model, условно `OverviewView`, а не набор независимых вызовов из UI.

Он должен возвращать уже подготовленные для отображения данные в рамках `OrganizationId + AccessContext`, например:

- `NewIncomingCount`;
- `ActiveProcurementCount`;
- `AttentionCount`;
- `WaitingDecisionCount`;
- `AttentionItems`;
- `ProcurementStageCounts`;
- `MyNextActions`;
- `CollectionSummary`;
- `TeamWorkload` при наличии права.

Не заставлять Blazor вычислять бизнес-состояние из сырых списков.

### Производительность

- избегать N+1;
- агрегаты считать на сервере/БД;
- ограничивать списки на главной небольшим числом наиболее важных записей;
- детальные данные загружаются уже на целевых страницах;
- итоговый read должен учитывать существующие permissions/scope до возврата данных клиенту.

## Источники данных после P0 Catalog/Procurement

После исправления границы Catalog → Procurement:

- `Новые входящие` считаются от универсального Catalog;
- рабочая закупка и её стадии считаются от самостоятельного объекта закупки, а не от внешнего объявления;
- отсутствие или удаление объявления Avito/Cian не должно ломать показатели закупочного объекта;
- одно и то же внутреннее дело с несколькими внешними источниками считается как один объект закупки.

## Не входит в Stage 1

Пока не добавлять на главную:

- финансовые графики;
- доходность инвестиций;
- продажи LandAsset;
- полноценные KPI сотрудников;
- красивые графики ради визуального наполнения;
- инвесторский кабинет.

После появления пост-покупочного контура обзор можно расширить отдельным уровнем `Наши объекты / Продажи / Финансы`, не меняя текущую основу.

## Acceptance

Экран считается реализованным, если:

1. за 5–10 секунд пользователь понимает, где требуется его действие;
2. каждый проблемный элемент ведёт в конкретное рабочее место;
3. данные соответствуют permissions/scope пользователя;
4. нет внутренних терминов `PropertyCase`, enum-кодов, GUID и технических названий;
5. блоки выровнены по единой сетке, особенно списки правой колонки;
6. главная не дублирует отдельные административные страницы;
7. показатели считаются сервером из актуальных Catalog/Procurement/Collection данных, а не захардкожены в UI.
