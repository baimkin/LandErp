# FP-003 — Единая дизайн-система Land ERP

**Версия:** 0.2  
**Статус:** Черновик  
**Владелец бизнес-решения:** владелец продукта  
**Технический владелец:** frontend-разработчик / UX-дизайнер  
**Зависимости:** генеральный план, ADR-001, ADR-006, FP-001, FP-002  
**Блокирует:** полноценные административные, менеджерские и инвесторские экраны

## 1. Решение в одном абзаце

Создать компактную дизайн-систему для всей ERP до массовой разработки экранов:
единые токены, базовые компоненты, формы, таблицы, статусы, карточки, обратную
связь и шаблоны страниц. Система должна делать большие объёмы данных читаемыми,
отделять источник от подтверждённого факта, прогноз от факта и внутренние данные
от опубликованных инвестору. Она не является отдельным дизайн-проектом ради
красоты: каждый компонент появляется из реального сценария первой волны.

## 2. Почему делаем сейчас

- ERP быстро накопит административные таблицы, карточки объектов и финансовые блоки.
- Без общих правил каждая фича создаст собственные кнопки, статусы и отступы.
- Статус доступности объявления, интерес бизнеса и качество данных нельзя кодировать
  одним цветом без подписи.
- Кабинет инвестора должен использовать общую платформу, но иметь более спокойную
  и ограниченную навигацию.
- Доступность и адаптивность дешевле заложить в базовые компоненты.

## 3. Измеримый результат

| Показатель | Цель |
|---|---|
| Повторное использование | Все экраны первой волны собраны из утверждённых базовых компонентов |
| Произвольные стили | Нет локальных цветов и размеров без токена или причины |
| Состояния | Каждый загружаемый блок имеет loading, empty, error, forbidden и success |
| Доступность | Клавиатурная навигация и видимый focus для интерактивных компонентов |
| Статусы | Цвет не является единственным способом передачи значения |
| Адаптивность | Основные операции доступны на распространённом desktop и tablet размере |
| Инвесторская ясность | Прогноз, согласованное и факт визуально и текстово различаются |

## 4. Пользователи и режимы интерфейса

### Сотрудник

- высокая плотность данных;
- быстрые фильтры и массовое чтение;
- видимые источники, причины и диагностика;
- действия в контексте роли;
- возможность открыть детали без потери очереди.

### Администратор

- таблицы конфигураций и состояния систем;
- безопасные опасные действия;
- диагностические детали;
- причины остановки и ручные перезапуски.

### Инвестор

- только назначенные проекты;
- спокойная навигация без административных элементов;
- опубликованные данные;
- ясные метки прогноза и факта;
- документы и хронология проекта.

## 5. Принципы визуального языка

1. **Сначала смысл.** Главное действие и причина состояния видны без изучения формы.
2. **Плотность с иерархией.** ERP может быть компактной, но не превращается в
   бесконечную сетку одинакового текста.
3. **Цвет дополняет текст.** Любой статус имеет название и при необходимости значок.
4. **Источник виден.** Значение из объявления отличается от подтверждённого факта.
5. **Прогноз виден.** Прогноз, согласованное значение и факт нельзя спутать.
6. **Опасность не маскируется.** Удаление, отзыв доступа и остановка источника
   требуют ясного подтверждения.
7. **Одна задача — один центр внимания.** Модальное окно и страница не конкурируют
   несколькими равнозначными primary-кнопками.
8. **История доступна.** Изменение цены, статуса и бюджета не скрывается за текущим
   значением.

## 6. Информационная архитектура оболочки

### 6.1. Основная навигация сотрудника

- Рабочая очередь;
- Объявления и объекты;
- Проверки;
- Проекты;
- Инвесторы;
- Отчётность;
- Администрирование — только по праву.

Пункты первой версии появляются по мере готовности модулей. Пустые разделы не
показываются в production.

### 6.2. Оболочка инвестора

- Портфель;
- Проекты;
- Документы и отчёты;
- Обращения;
- Профиль и безопасность.

Инвестор не видит меню поиска, агентов, внутренних проверок и управления
пользователями.

## 7. Токены

### 7.1. Категории

- цвет фона, поверхности, текста, границы и акцента;
- semantic colors: info, success, warning, danger, neutral;
- типографическая шкала;
- шаги отступов;
- радиусы;
- тени;
- размеры контролов;
- z-index слои;
- длительность и easing анимаций;
- ширины контента и breakpoints.

### 7.2. Правило semantic tokens

Компонент использует `surface-muted` или `status-warning`, а не конкретный hex.
Темы и контраст меняются централизованно. Цвет статуса не закрепляется за одним
доменным состоянием навсегда: подпись остаётся обязательной.

### 7.3. Начальная визуальная направленность

- светлый нейтральный рабочий фон;
- белые или слегка тонированные поверхности;
- тёмно-синий основной текст;
- синий рабочий акцент;
- зелёный только для подтверждённого успешного результата;
- янтарный для внимания и неопределённости;
- красный для ошибки, риска или опасного действия;
- серый для неактивных и вторичных сведений.

Окончательные значения утверждаются по реальным макетам, а не этим описанием.

### 7.4. Типографика и плотность

- Основной шрифт — системный стек
  `system-ui, -apple-system, "Segoe UI", Roboto, Arial, sans-serif`.
- Внешний web-font в первом контуре не загружается.
- Базовый размер текста — 16 px; плотные табличные сведения допускают 14 px.
- Стандартная высота control — 40 px.
- Стандартная строка таблицы — 44 px; компактный режим — 36 px.
- Компактный режим включается явно для рабочих таблиц, а не применяется ко всему
  кабинету инвестора.

### 7.5. CSS-основа

Используется локальный Bootstrap CSS из шаблона Blazor как базовая сетка,
utilities и оформление форм. Цвета, размеры, focus и компоненты определяются
токенами Land ERP. Bootstrap JS и готовая сторонняя Blazor component library в
первую версию не входят.

## 8. Базовые компоненты первой волны

### 8.1. Обязательные

- `AppShell`;
- `PageHeader` и `Breadcrumbs`;
- `Button` с primary/secondary/quiet/danger;
- `IconButton` с доступным названием;
- текстовые, числовые, денежные, площадные и date/time поля;
- `Select`, `Combobox`, `Checkbox`, `Radio`, `Switch`;
- `FieldMessage` и summary ошибок;
- `DataTable`;
- `FilterBar`;
- `StatusBadge`;
- `SourceBadge` и `ConfidenceBadge`;
- `Card`, `SummaryCard` и `KeyValueList`;
- `Tabs`;
- `Drawer` для быстрого просмотра из очереди;
- `Dialog` и `DangerConfirmation`;
- `Toast` для некритичного краткого результата;
- `InlineAlert` для сохраняющейся проблемы;
- `EmptyState`, `ErrorState`, `ForbiddenState`, `LoadingState`;
- `Pagination` или виртуализация по сценарию;
- `AuditTimeline` и `PriceHistory` позже на реальных данных.

### 8.2. Не создавать заранее

- универсальный конструктор форм;
- универсальную таблицу со всеми возможными режимами;
- сложный low-code UI;
- карту без утверждённых сценариев;
- отдельную библиотеку компонентов на каждый модуль;
- анимации, не помогающие понять изменение состояния.

## 9. Таблицы и очереди

### 9.1. Таблица

- заголовок столбца объясняет значение;
- сортировка имеет видимое направление;
- фильтр сохраняется в URL или рабочем состоянии по плану фичи;
- числовые данные выровнены последовательно;
- деньги всегда показывают валюту;
- площадь показывает единицу;
- длинный текст не разрушает строку;
- действия строки доступны с клавиатуры;
- выбор строк не смешивается с переходом в карточку;
- массовое действие показывает число выбранных объектов.

### 9.2. Очередь менеджера

Каждая строка отвечает на четыре вопроса:

1. Что это за объект?
2. Почему он появился сейчас?
3. Что изменилось или неизвестно?
4. Какое следующее действие ожидается?

Цена, площадь и локация важны, но причина попадания в очередь должна иметь такой
же визуальный приоритет.

## 10. Формы

- label видим постоянно и не заменяется placeholder;
- обязательность обозначена единообразно;
- серверная и клиентская ошибки показываются рядом с полем и в summary при
  большой форме;
- сохранение блокирует повторный submit, но не замораживает весь интерфейс;
- несохранённые изменения защищены от случайной потери;
- денежные поля не допускают неявного изменения валюты;
- дата и время показывают бизнес-часовой пояс;
- опасное значение не применяется автоматически после закрытия формы.

## 11. Статусы и уровни доверия

### 11.1. Нельзя смешивать

- доступность объявления;
- качество сбора;
- интерес бизнеса;
- стадию проверки;
- стадию проекта;
- публикацию инвестору.

На экране показываются только нужные для сценария измерения, но они не сводятся в
одно универсальное «цветное состояние».

### 11.2. Источник и подтверждение

Рядом со значимым полем при необходимости доступны:

- значение;
- тип источника;
- дата актуальности;
- уровень подтверждения;
- наличие противоречия;
- действие «показать происхождение».

### 11.3. Финансовые значения

| Тип | Визуальное правило |
|---|---|
| Исходное | Нейтральная метка с источником |
| Допущение | Нейтрально-янтарная метка и возможность открыть основание |
| Прогноз | Явная подпись «Прогноз», не зелёный успех |
| Согласовано | Метка версии и автора согласования |
| Факт | Наиболее ясное значение с датой подтверждения |

## 12. Состояния асинхронного интерфейса

Каждый компонент, загружающий данные, обязан определить:

- initial;
- loading;
- refreshing без исчезновения уже показанных данных;
- empty;
- partial data;
- validation error;
- recoverable error с повтором;
- forbidden;
- conflict;
- success.

Skeleton применяется там, где форма содержимого известна. Spinner не должен быть
единственной обратной связью длительной операции.

## 13. Опасные действия

К опасным относятся:

- отзыв роли или project access;
- отзыв Agent;
- остановка источника/расписания;
- архивирование или удаление сущности;
- отзыв опубликованного отчёта;
- утверждение/корректировка финансового события;
- будущая отправка сообщения.

Диалог подтверждения показывает конкретный объект, последствие и обратимость.
Ввод названия для подтверждения используется только для редких действительно
разрушительных действий, а не повсеместно.

## 14. Доступность

- соответствие WCAG 2.2 AA как целевой уровень;
- видимый focus;
- полная клавиатурная навигация основных потоков;
- semantic HTML;
- label и accessible name у контролов;
- состояние не передаётся только цветом;
- достаточный контраст;
- таблица имеет заголовки и понятный порядок чтения;
- dialog удерживает и возвращает focus;
- анимация учитывает prefers-reduced-motion;
- ошибки доступны screen reader и связаны с полями.

## 15. Адаптивность

Приоритет — desktop-работа менеджера и администратора. Tablet поддерживает
основные операции. Телефон в первой версии предназначен для просмотра срочных
сведений и простых действий, но не обязан вмещать сложную многостолбцовую
аналитику без упрощённого представления.

### 16.1. Начальные CSS tokens

```css

  --color-bg-surface: #ffffff;
  --color-bg-muted: #eef2f6;
  --color-text-primary: #15263c;
  --color-text-secondary: #5f7085;
  --color-border: #d8e0e8;
  --color-accent: #2563b8;
  --color-success: #19734a;
  --color-warning: #a66500;
  --color-danger: #b42318;

  --space-1: 0.25rem;
  --space-2: 0.5rem;
  --space-3: 0.75rem;
  --space-4: 1rem;
  --space-6: 1.5rem;
  --space-8: 2rem;

  --radius-sm: 0.375rem;
  --radius-md: 0.625rem;

```

Значения считаются первоначальным направлением и утверждаются после проверки
макетов контрастом и на реальных экранах.

### 16.2. Типизированный badge без бизнес-логики цвета в Razor

```csharp
public enum UiTone
{
    Neutral,
    Info,
    Success,
    Warning,
    Danger
}

public sealed record StatusBadgeModel(
    string Label,
    UiTone Tone,
    string? AccessibleDescription = null);
```

Бизнес-модуль преобразует своё состояние в presentation model. Общий компонент
не должен знать все доменные статусы ERP.

### 16.3. Явные состояния загрузки

```razor
@switch (ViewState)
{
    case PageViewState.Loading:
        <LoadingState Label="Загружаем поисковые ссылки" />
        break;
    case PageViewState.Empty:
        <EmptyState Title="Поисковых ссылок пока нет" />
        break;
    case PageViewState.Forbidden:
        <ForbiddenState />
        break;
    case PageViewState.Error:
        <ErrorState OnRetry="LoadAsync" />
        break;
    case PageViewState.Ready:
        <SearchDefinitionsTable Items="Items" />
        break;
}
```

## 17. Документация компонентов

Для каждого компонента достаточно практической страницы/каталога с:

- назначением;
- вариантами и состояниями;
- доступностью;
- допустимыми и недопустимыми примерами;
- параметрами API;
- реальными местами использования.

Выбор Storybook, отдельного Blazor-host или другого каталога закрепляется после
proof-of-concept. Не строить сложный портал документации раньше первых 10–15
компонентов.

## 18. Тестирование

| Уровень | Обязательные проверки |
|---|---|
| Unit/component | Варианты, disabled, loading, события и форматирование данных |
| Accessibility | Keyboard, focus, labels, contrast, dialog focus trap |
| Visual regression | Ключевые компоненты и 3–5 основных экранов |
| E2E | Форма с ошибкой, таблица с фильтром, опасное подтверждение, forbidden |
| Security | Скрытая кнопка не заменяет серверную авторизацию |
| Responsive | Desktop и tablet контрольные viewport; телефон для заявленных сценариев |

## 19. Вертикальные этапы

### Этап 1. Foundations

Токены, типографика, focus, кнопки, поля и состояния страницы на одном служебном
экране.

### Этап 2. Административный набор

PageHeader, FilterBar, DataTable, StatusBadge, Dialog и Toast применяются в первом
реальном экране FP-002 или FP-010.

### Этап 3. Рабочая очередь

Компоненты плотной строки, drawer, причина события и быстрые решения проверяются
на FP-020.

### Этап 4. Проект и финансы

KeyValue, timeline, plan–fact, происхождение поля и документы проверяются на
реальном проекте.

### Этап 5. Инвесторская оболочка

Общая база компонентов используется в отдельной упрощённой навигации и
проверяется на изоляцию внутренних функций.

## 20. Развёртывание

- Компоненты поставляются вместе с Server, отдельный npm-пакет в первой версии не нужен.
- Bootstrap хранится локально как статический CSS asset; CDN и отдельная npm-
  сборка для него не используются.
- Интерактивность реализуется Blazor/нативным HTML; Bootstrap JS подключается
  только после обоснования конкретным сценарием.
- Изменение token не должно неожиданно ломать все экраны без visual regression.
- Разрушающее изменение API компонента проходит поиск всех потребителей.
- Новая тема или dark mode не входят в первую поставку без отдельной ценности.

## 21. Definition of Ready

- согласована визуальная направленность на 2–3 реальных экранах;
- определены поддерживаемые браузеры и viewport;
- выбрана стратегия CSS и изоляции стилей;
- доступен каркас Blazor;
- известны первые реальные компоненты FP-002 и FP-010;
- определён способ visual regression.

## 22. Definition of Done

- токены централизованы;
- базовые компоненты применены минимум в двух реальных фичах;
- нет произвольных локальных цветов и размеров без причины;
- loading, empty, error, forbidden и success реализованы единообразно;
- клавиатура и focus проверены;
- статус не передаётся только цветом;
- финансовые типы визуально различаются;
- опасные действия используют единый диалог;
- visual/component/E2E tests зелёные;
- документация компонентов содержит реальные примеры.

## 23. Открытые вопросы

| Вопрос | Блокирует |
|---|---|
| Какой фирменный стиль и логотип использовать | Финальную визуальную направленность |
| Поддерживаемые браузеры и минимальная ширина | Responsive и E2E matrix |
| Нужен ли dark mode в обозримом будущем | Архитектуру тем, но не первую версию |
| Нужна ли мобильная работа менеджера или только просмотр | Mobile UX |
| Как отображать конфиденциальные финансовые данные на экране/скриншоте | Privacy UX |
