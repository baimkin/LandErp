## 1. Способ работы и границы

Первые три задачи выполняются последовательно в режиме чата с реальными коммитами в удалённую рабочую ветку. Четвёртая выполняется в рабочей среде: сначала проверяет накопленные изменения, затем добавляет свою реализацию и проверяет весь пакет. Передача первых трёх задач через патчи не является выбранным процессом.

GitHub-подключение текущего подготовительного шага предоставляет создание веток и запись файлов с коммитами. Не выводить секреты и не требовать передачи токенов в чат. В новом сеансе проверять фактические возможности инструментов, а не считать прежние заявления о доступности или недоступности доказательством.

Цель пакета — надёжный результат сохранения, непротиворечивый жизненный цикл закупки и управляемая ответственность сотрудников.

Stage 1 остаётся контуром от входящего предложения до подтверждённой покупки. Не добавлять постпокупочный учёт, кабинет инвестора, новый workflow engine, универсальную платформу идемпотентности или глобальный редизайн. Не проводить повторный полный аудит репозитория. Локальный Parser/Collector в этом пакете не изменяется.

Находки исходного аудита подтверждены статическим чтением, но не воспроизведены в исполняемой среде этого аудита. Перед изменением каждого механизма адресно сверить актуальный код, требования и относящиеся к нему тесты. Уже исправленную проблему закрывать доказательством, а не повторным изменением.

### Статусы

- **Не начата** — реализации нет.
- **Реализована, опубликована, исполнение не проверено** — код и тесты записаны в ветку; статическая проверка выполнена, но сборка и тесты не запускались.

В B1-01–03 тесты пишутся вместе с исправлениями. На B1-04 переносится их исполнение, а не проектирование проверок. Не обозначать написанный тест как пройденный. Правило 3+1 ограничивает накопление непроверенных изменений, но не запрещает более ранний рабочий прогон при существенном риске.

## 3. B1-01 — результат сохранения и диагностика

### Ожидаемое поведение

Разделить результат команды и результат последующего обновления экрана. Если команда успешно выполнена, ошибка перечитывания не должна сообщать «сохранение не выполнено» и предлагать повторное создание. Показывать подтверждённую запись и отдельную проблему обновления; повторять именно чтение.

Неопределённый результат при потере подтверждения записи отличать от подтверждённого успеха и подтверждённого отказа. Не утверждать ни отсутствие записи, ни успех без основания.

Для затронутых операций добавления определить устойчивый идентификатор команды либо другой проверяемый механизм безопасного повтора. Перед изменением контрактов перечислить конкретные команды и область защиты. `Busy` не заменяет защиту повторной доставки. Не распространять новую инфраструктуру на весь проект без необходимости.

Добавить безопасную диагностику с идентификатором операции, доступным пользователю и журналу. Не логировать пароли, токены, содержимое документов, полный пользовательский payload или формы с персональными данными. Вложенные исключения также не должны раскрывать чувствительные значения.

### Предварительные точки работы

`src/LandErp.Server/Components/WorkspaceComponent.cs`; затронутые обработчики `Components/Pages` и `Components/Procurement`; только необходимые методы `ProcurementWorkspace.cs`, application contracts и endpoint adapters; targeted tests в существующем тестовом проекте.

Перед записью составить точный перечень файлов по актуальному коду. Новую таблицу квитанций не считать заранее обязательной. При необходимости изменения схемы подготовить отдельную forward migration штатным способом; не подделывать результат её генерации или применения.

### Критерии проверки

1. Успешная команда с последующим сбоем чтения показывает корректный результат и не провоцирует повторное создание.
2. Отказ валидации сохраняет ввод и не создаёт запись.
3. Повтор одной защищённой операции не создаёт два бизнес-факта. Если введён command ID, одинаковый payload возвращает прежний результат, другой payload отклоняется, чужая организация не получает квитанцию.
4. Конфликт версии и запрет доступа не превращаются в сообщение об успехе.
5. Ошибка команды и ошибка обновления различимы в безопасной диагностике.
6. Модальная форма после подтверждённой записи не остаётся повторно отправляемой только из-за сбоя перечитывания.

Исправление общего обработчика не объявляет закрытыми находки локального черновика осмотра. Однако новая регрессия осмотра, вызванная этим изменением, блокирует приёмку пакета.

## 4. B1-02 — жизненный цикл объекта и сроки

Для `acquired` запретить обычные решения, возвращающие объект в активную или отклонённую закупку, и повторное открытие следующей задачи. Проверка обязательна в серверной команде; UI должен отражать те же возможности.

Сохранить отдельную аудируемую корректировку факта покупки. Не вводить неутверждённую отмену покупки, не делать всю карточку неизменяемой и не добавлять новые обязательные юридические условия от имени владельца.

Для существующей проверки разрешить запись результата и завершение с неизменённым исходным сроком в прошлом. Новое назначение или изменение срока проверять отдельно. Не переносить срок автоматически для сокрытия просрочки.

Предварительные точки: `ProcurementWorkspace.cs`, доступные действия read models, `CaseWorkspace.razor`, очередь V2 и targeted tests. Компактный общий helper допустим; универсальный workflow engine не нужен.

Проверки: купленный объект из `analysis` и `negotiation`; отказ всех недопустимых обычных решений и изменения следующего действия через серверные пути; неизменность статуса, задачи и истории при отказе; успешная отдельная коррекция покупки; закрытие просроченной проверки с прежним сроком; конфликт версий и изоляция организаций.

## 5. B1-03 — назначения, Owner и шаблоны

Сопоставить выбор получателя с реальной видимостью объекта после назначения. Различать менеджера объекта, текущего ответственного, исполнителя следующего действия и ответственного за проверку. Для каждого поддерживаемого пути определить ожидаемый доступ получателя.

Не исправлять проблему выдачей всем `Organization` scope. Не менять значения `Own` и `AssignedObjects` незаметно. Использовать утверждённые правила проекта: ограничить недопустимое назначение либо обеспечить предусмотренный адресный доступ. Если выбор не следует из требований, зафиксировать конкретный вопрос до изменения политики прав.

Защиту последнего активного Owner выполнить в общей конкурентно защищённой операции проверки и изменения. Покрыть одновременные отключения, снятие роли и смешанные операции. Предупреждение UI не заменяет серверный инвариант.

**LR-23 — вопрос политики, а не доказанная уязвимость.** Отделить фиксацию текущих прав на общие шаблоны от их изменения. Новая матрица read/use/edit/archive не утверждается автоматически этим планом. При отсутствии решения сохранить текущие права, отметить LR-23 как открытый decision item и не объявлять его закрытым. Это не мешает началу B1-01.

Предварительные точки: `ProcurementVisibility.cs`, `TargetsAsync`, команды назначения, `AccessControl.cs`, `OrganizationWorkspace.cs`, модели разрешений, read models и UI выбора; targeted tests.

Проверки: `Own/AssignedObjects/Team/Department/Organization`; передача руководителю, возврат другому менеджеру, назначение действия и проверки; законный получатель открывает нужный объект без доступа к посторонним; устаревший UI не обходит запрет; конкурентные отключения и снятия роли всегда сохраняют хотя бы одного активного владельца. Данные тестов синтетические.

## 6. B1-04 — передача работы и проверка всего пакета

### 6.1. Проверить накопленный результат до новой реализации

Прочитать план и отчёты B1-01–03. Получить опубликованные коммиты рабочей ветки и зафиксировать проверяемый SHA. Проверить чистоту рабочей копии и наличие чужих изменений; не затирать пользовательские файлы и не менять общую базу самовольно.

Выполнить сборку затронутых проектов и первоначальные targeted checks до четвёртого изменения. Блокирующие ошибки первых трёх задач исправить с отдельной записью в отчёте. Не маскировать регрессии ослаблением assertions или широким отключением тестов.

### 6.2. Реализовать новое поведение

Добавить управляемую передачу незавершённой работы при отключении сотрудника: показать затрагиваемые объекты, задачи, проверки и ожидающие решения; проверить права инициатора и допустимость получателей; сохранить историю ответственности.

Передача не должна переписывать авторов старых событий, роли сотрудников, исходные факты или границы организаций. Предлагаемый сценарий — предварительный просмотр и подтверждённая передача с отключением. Срочный отзыв доступа без готового получателя требует определённого поведения: сотрудник не должен сохранять доступ только из-за незаконченного перераспределения.

Защитить от гонки нового назначения с отключением. После отзыва доступа не должна появиться ещё одна активная работа у отключённого сотрудника. Отдельно проверить получателя ожидающего согласования и запрет собственного одобрения там, где он установлен.

### 6.3. Выполнить итоговые проверки

Запустить относящиеся к пакету существующие и новые тесты на одном итоговом состоянии кода. Для транзакций, конкуренции и ограничений использовать настоящий PostgreSQL, а не SQLite/InMemory.

При наличии миграций проверить полный chain на отдельной чистой БД и отсутствие pending model changes. Применение к общей локальной или production-БД этим планом не разрешается автоматически. С момента появления ценных рабочих данных использовать сохраняющие данные обновления, а не считать рабочую БД одноразовой.

Проверить браузером затронутые формы: результат сохранения, модальные окна, решения после покупки, назначения и передачу работы. Точный browser-scope и порядок запуска сервера должны быть указаны в задании B1-04. Не запускать несогласованные live-сценарии источников и не конфликтовать с общим Server/Worker. Windows-парсер в этом пакете не изменяется.

Исправление обычных регрессий первых трёх задач входит в B1-04. Большой новый бизнес-сценарий вне пакета фиксируется отдельно, а не добавляется незаметно.

## 7. Сквозной сценарий приёмки

Создать двух менеджеров и руководителя с ограниченными областями. Взять предложение в работу; назначить следующий шаг; проверить доступ получателя и отсутствие доступа к постороннему объекту. Сохранить событие с искусственным сбоем последующего чтения и проверить отсутствие дубля. Закрыть просроченную проверку, сохранив срок. Передать объект руководителю и проверить доступ. Подтвердить покупку, проверить запрет обычных переходов и отдельную коррекцию покупки. На другом незавершённом объекте отключить сотрудника через предусмотренный сценарий передачи; проверить нового ответственного, историю и отзыв доступа. Отдельно конкурентным тестом проверить последнего Owner.

Каждая проверка получает статус `Passed/Failed/Not run` и фактическое доказательство. `Not run` не означает `Passed`. В отчёте отличать дефект реализации, недостаток тестового окружения и открытое продуктовое решение.

## 8. Git и передача между сеансами

Рабочая ветка — `codex/release-package-01`. Не менять `main` напрямую. Merge, rebase, force-push, удаление веток и production deploy требуют отдельного разрешения. Не переписывать опубликованную историю.

Перед каждой реализацией сверять актуальный HEAD и изменения после предыдущего отчёта. Не заменять дерево репозитория неполной выборкой файлов. При публикации через Git data API сохранять базовое дерево, родительский commit и использовать обычное fast-forward обновление ref. Подтверждать публикацию повторным чтением удалённой ветки и diff.

Единый журнал пакета при начале B1-01: `docs/03-active/reports/RELEASE_PACKAGE_01_REPORT.md`. Для каждой задачи записывать исходный и итоговый commit, изменённое поведение, точный перечень файлов, миграции, добавленные тесты, фактически выполненные проверки, что не запускалось, открытые решения и следующий шаг. Подготовительный коммит этого плана журнал реализации не имитирует.

Обновление `ACTIVE_TASK.md` выполнять только в согласованной рабочей ветке при активации конкретной задачи, сохраняя исторические записи и чужой scope. Не переписывать всю документацию ради первого пакета.
