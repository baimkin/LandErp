# Catalog object groups — implementation report

Дата: 2026-09-21  
База: `main` `f554c5a3297fadc28812133780f14ccfe30e288f`  
Рабочая ветка: `codex/catalog-object-groups`

## Бизнес-цель

Превратить найденные системой возможные дубли в управляемую связь нескольких объявлений одного физического участка. Менеджер должен быстро сравнить источники, подтвердить или отклонить совпадение, работать с 2–N объявлениями как с одним объектом и при ошибке безопасно разделить их обратно.

## Реализация

- добавлена нейтральная `CatalogObjectGroup`; у группы нет главного Listing;
- `Listing.ObjectGroupId` nullable: одиночные объявления живут без группы;
- подтверждение duplicate candidate создаёт/расширяет/объединяет группу;
- оставшиеся pending-кандидаты не помечаются как «не дубль» автоматически;
- внутренние pending-пары уже объединённой группы закрываются как `Obsolete`;
- ручная команда «связать с объектом» создаёт тот же тип связи и persisted decision;
- generic-классификация `Duplicate` без конкретного объявления запрещена;
- исключение из группы требует причины, пишет Audit, снимает ошибочную подтверждённую source-link к PropertyCase и сохраняет отрицательное решение по парам;
- при одном оставшемся источнике группа удаляется, Listing снова становится самостоятельным;
- `TakeToWork` для любого участника группы связывает все её Listings с одним PropertyCase и не допускает объединение источников, уже принадлежащих разным PropertyCase;
- Incoming показывает группу и её источники, позволяет открыть любой источник, исключить текущий и вручную найти другой Catalog item;
- кандидат можно открыть в широком сравнении бок о бок с фото, ценой, ₽/сот., площадью, локацией, кадастром, продавцом и описанием.

## Database

Forward migration: `20260921143000_CatalogObjectGroups`.

Создаётся `catalog.object_groups` и nullable FK `catalog.listings.object_group_id`. Runtime получает только необходимые DML-права на новую таблицу; DDL по-прежнему недоступен runtime-роли.

## Tests prepared

`CatalogObjectGroupTests` покрывает:

1. четыре источника → одна headless-группа → один PropertyCase с четырьмя source links;
2. отвязку после перевода в работу, снятие только ошибочного source link и отсутствие повторного предложения отвергнутой пары;
3. ручное связывание и запрет несвязанной классификации `Duplicate`.

Существующие migration tests дополнительно проверяют отсутствие pending model changes после применения полного migration chain.
