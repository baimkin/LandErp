# FP-015 — Административный мониторинг сбора

**Версия:** 0.1  
**Статус:** Черновик  
**Владелец:** администратор сбора  
**Модули:** Administration, Collection  
**Зависимости:** FP-002, FP-003, FP-010–FP-014

## 1. Бизнес-результат

Администратор без SQL и удалённого подключения к компьютерам понимает: работают
ли поиски, где очередь задержалась, какой Agent требует внимания, применяются ли
результаты и что можно безопасно сделать. Экран показывает операционное состояние,
а не поток технических логов.

## 2. Основные вопросы экрана

- Какие поиски не запускались по расписанию?
- Есть ли свежие объявления и подробные карточки в обработке?
- Почему результат не применён?
- Какие Agent online, busy, paused, outdated или revoked?
- Есть ли CAPTCHA, auth или изменение разметки?
- Каков возраст старейшей задачи и первоначального наполнения?
- Какие ручные действия ждут администратора?

## 3. Область первой версии

Входят обзор, списки поисков/прогонов/задач/Agent/инцидентов, детализация,
pause/resume, диагностический retry, cancel pending, drain/revoke Agent и аудит.

Не входят редактор DOM-селекторов, удалённый рабочий стол, просмотр секретов,
выполнение произвольного SQL, автоматический обход CAPTCHA и универсальный log
management.

## 4. Информационная архитектура

### 4.1. Обзор

Карточки состояния: active searches, overdue runs, pending/leased/attention,
online/attention agents, open quality incidents, oldest task. Ниже — только
события, требующие действия, и динамика последних прогонов.

### 4.2. Поиски и прогоны

Таблица показывает название, активную ревизию, расписание, последний успешный
прогон, следующий запуск, найдено/new/changed, quality outcome и pause reason.
Деталь прогона связывает страницы, задачи, результаты и инциденты.

### 4.3. Задания

Фильтры по state, type, priority, source, search, Agent, age и error category.
В строке видны attempt, available/lease time и безопасная краткая причина.
Payload показывается как понятные поля, а не необработанный JSON по умолчанию.

### 4.4. Agent

Имя, AgentId, версия, ОС, capabilities, last heartbeat, current task, состояние
источника и backlog outbox. Действия pause, drain, revoke и rotation доступны по
правам и требуют подтверждения влияния.

### 4.5. Качество и инциденты

Список из FP-014 показывает severity, scope, правило, начало, влияние, владельца
и следующий шаг. Evidence открывается отдельно с предупреждением о чувствительных
данных и аудитом.

## 5. Состояния и семантика

`Healthy` означает, что ожидаемые бизнес-прогоны завершаются с применимым
качеством, а не только что процесс отвечает. `Degraded` означает измеримое
отклонение без полной остановки. `AttentionRequired` требует человека. `Paused`
всегда показывает кем, когда и почему остановлено.

Цвет не является единственным носителем статуса; есть текст и иконка. Время
показывается в понятном часовом поясе пользователя, хранится в UTC.

## 6. Read model

Экран читает специализированные проекции и не строит тяжёлые агрегаты при каждом
открытии. Владелец исходных данных остаётся прежним модулем.

```csharp
public sealed record CollectionOverview(
    int ActiveSearches,
    int OverdueRuns,
    int PendingTasks,
    TimeSpan? OldestTaskAge,
    int AgentsOnline,
    int AgentsRequiringAttention,
    int OpenQualityIncidents,
    DateTimeOffset CalculatedAt);
```

Проекция имеет `CalculatedAt`; UI показывает устаревание. Отсутствие свежей
проекции не рисуется как нулевые проблемы.

## 7. Команды администратора

| Команда | Ограничение |
|---|---|
| Run search now | создаёт отдельный аудируемый прогон, соблюдает source limits |
| Pause/Resume search/source | причина обязательна; resume проверяет открытый incident |
| Retry task | создаёт новую попытку/задачу по политике, не переписывает историю |
| Cancel pending task | не отменяет принятый результат |
| Drain Agent | не выдаёт новую задачу, позволяет закончить текущую |
| Revoke Agent | немедленно запрещает новые запросы и отмечает активную аренду |
| Select adapter canary | только разрешённый scope и версия |

Массовое действие сначала показывает число затронутых объектов. Команда
идемпотентна либо защищена operation id. Результат действия отображается явно.

## 8. Права и аудит

- Owner/Admin видит и выполняет административные команды.
- Технический viewer может видеть состояние без evidence и секретных данных.
- Manager видит бизнес-статус своих объектов, но не управляет Agent/адаптером.
- Investor не имеет доступа к разделу.
- Просмотр секретов невозможен для любой роли.

Аудитируются команды, смена конфигурации/порогов, evidence access, revoke,
rotation и опасные повторы. Обычное автообновление dashboard не создаёт аудит.

## 9. Обновление интерфейса

Первая версия использует периодическое обновление с разумным интервалом и кнопку
refresh. SignalR добавляется только если измерена необходимость. Фильтр и выбранная
строка сохраняются при обновлении; новые данные не переставляют строки во время
критичного подтверждения.

## 10. Ошибки и пустые состояния

- «Нет задач» отделено от «данные мониторинга не обновились».
- Недоступный Agent не объявляется revoked автоматически.
- Ошибка команды показывает correlation id и безопасный следующий шаг.
- Частичный сбой одной проекции не скрывает остальные разделы.
- Повтор нажатия не создаёт несколько одинаковых run/retry.
- Удалённый/архивный поиск остаётся доступен в истории по правам.

## 11. Наблюдаемость

Сам мониторинг измеряется: задержка проекций, время открытия, успех команд,
ошибки авторизации, возраст неподтверждённых действий. Алерты направляются по
политике severity; dashboard не является единственным способом узнать об
остановленном сборе.

## 12. Тесты

- правильные агрегаты на смешанных состояниях;
- overdue с учётом расписания/паузы;
- role/permission и отсутствие Investor access;
- mass action preview и обязательная причина;
- идемпотентный retry/run now;
- revoked Agent не может heartbeat/lease;
- устаревшая проекция не выглядит здоровой;
- evidence access аудируется;
- accessibility: клавиатура, focus, status text, таблица;
- E2E: incident → pause → canary → resume.

## 13. Вертикальные этапы

1. Обзор и read model без управляющих команд.
2. Поиски/прогоны и связь с задачами.
3. Agent list/detail, pause/drain.
4. Quality incidents и evidence.
5. Retry/cancel/revoke с аудитом.
6. Canary/resume и операционный E2E.

## 14. Definition of Ready

- состояния FP-010–014 согласованы;
- permission model FP-002 доступна;
- дизайн-компоненты таблицы, статуса и подтверждения определены FP-003;
- классификация ошибок и source limits утверждены.

## 15. Definition of Done

- администратор находит причину остановки без SQL;
- обзор отличает технический health от бизнес-успеха;
- все опасные команды имеют scope, подтверждение и аудит;
- нет доступа к секретам/чужим ролям;
- один E2E-инцидент полностью обрабатывается из UI;
- метрики и алерты содержат ссылку/correlation для диагностики;
- инструкция администратора занимает одну практическую страницу.

## 16. Открытые вопросы
