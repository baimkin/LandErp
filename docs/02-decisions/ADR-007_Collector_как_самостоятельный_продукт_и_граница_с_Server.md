# ADR-007 — Collector как самостоятельный продукт и граница с LandErp Server

**Дата:** 14 сентября 2026 года  
**Статус:** Утверждён  
**Решение:** принято владельцем продукта  
**Связанные документы:** ADR-002, ADR-003, ADR-004, FP-001, FP-004, FP-010–FP-015

## 1. Контекст

В рамках `SPIKE-001` создан и проверен локальный сборщик данных для Avito/Cian с собственным Windows UI, локальной SQLite-базой, очередью, диагностикой и браузерной автоматизацией.

При переходе к ERP важно не превращать этот код в часть веб-сервера и не связывать браузерную автоматизацию напрямую с внутренней БД LandErp.

Collector имеет самостоятельную практическую ценность: его можно запускать, тестировать и развивать локально независимо от ERP. Серверу нужен только согласованный результат сбора и состояние Agent.

## 2. Решение

`LandErp Collector` / `LandErp.Agent` остаётся самостоятельным небольшим приложением и отдельной границей системы.

ERP и Collector могут находиться в одном Git-репозитории LandErp, но имеют независимые runtime-границы, сборку и ответственность.

Collector не становится частью `LandErp.Server`. Связь с сервером реализуется тонким адаптером через версионированный API и контракты.

Базовая схема:

```text
Avito / Cian / future sources
          ↓
  LandErp Collector
  ├─ Browser / source adapters
  ├─ Collector Core
  ├─ Local SQLite
  ├─ Windows UI / diagnostics
  └─ Server Adapter
          ↓ HTTPS/API
  LandErp Server
          ↓
 PostgreSQL / ERP modules
```

## 3. Ответственность Collector

Collector отвечает за:

- работу браузера и source-specific адаптеров;
- получение страниц и классификацию состояний источника;
- извлечение и первичную нормализацию данных;
- локальную очередь выполнения и управление вкладками/браузером;
- локальную SQLite-базу, необходимую для автономного режима и диагностики;
- диагностику ошибок источника, CAPTCHA, rate limit и других состояний;
- формирование `CollectionResult` по согласованному контракту;
- отправку heartbeat/capabilities и результатов серверу в server mode.

Collector не принимает бизнес-решений ERP: не знает workflow закупки, согласования, Due Diligence, инвесторов, финансов, хозблока, маркетинга или продаж.

## 4. Ответственность Server

`LandErp.Server` отвечает за:

- постановку серверных `CollectionJob` и выдачу их Agent;
- lease/reservation и защиту от параллельного выполнения одного задания;
- проверку входящего контракта;
- сохранение серверного каталога и наблюдений;
- историю, дедупликацию, контроль качества и бизнес-события;
- создание очередей менеджеров и дальнейший ERP workflow;
- права, аудит и централизованные настройки.

Сервер не управляет браузером напрямую и не содержит source-specific Playwright-логику.

## 5. Жёсткие границы

Обязательные правила:

1. **Collector никогда не подключается напрямую к PostgreSQL LandErp.**
2. **Server никогда не управляет браузером Collector напрямую.**
3. Обмен выполняется только через API/контракты.
4. Collector не ссылается на внутренние доменные сущности ERP.
5. Server не зависит от внутренних классов browser/source слоя Collector.
6. Ошибка или недоступность ERP не должна делать невозможным локальное тестирование Collector.
7. Ошибка одного Collector не должна повреждать серверные данные или другие Agent.

## 6. Режимы работы

Collector должен поддерживать два режима без дублирования парсинговой логики.

### Local mode

Используется для разработки, тестирования, диагностики и при необходимости самостоятельной работы Collector.

- задания создаются локально;
- результаты сохраняются локально;
- доступен существующий UI и SQLite;
- сервер не требуется.

### Server mode

Используется в рабочем контуре LandErp.

- Agent регистрируется на сервере;
- получает структурированные задания;
- получает lease;
- выполняет сбор тем же Collector Core;
- отправляет нормализованный результат и диагностику;
- сервер подтверждает приём результата.

`Server Adapter` является оболочкой вокруг Collector Core, а не вторым механизмом парсинга.

## 7. Контракты

Контракты Agent ↔ Server выделяются в отдельную стабильную границу, например `LandErp.AgentContracts`.

Минимальные группы контрактов:

- Agent registration / identity;
- heartbeat и capabilities;
- `CollectionJob` + lease;
- acknowledge / complete / fail;
- `CollectionResult`;
- source diagnostics и quality signals;
- совместимая версия протокола.

Контракты версионируются. Добавление нового необязательного поля не должно без необходимости требовать синхронного обновления всех Agent.

Breaking change требует новой версии контракта и явно определённого периода совместимости.

## 8. Данные и владение

Collector может хранить локальные технические и временные данные для своей работы, но сервер является владельцем общей истории рынка и ERP-данных.

Нормализованные данные передаются с явным `Source`, `ExternalId`, временем наблюдения, presence/quality semantics и диагностикой. Отсутствие поля в одном наблюдении не означает автоматического удаления ранее известного значения.

Сырые страницы, screenshots и технические артефакты не являются обязательной частью серверного контракта. Их передача вводится только при подтверждённой потребности, с ограничениями размера, безопасности и retention.

## 9. Развёртывание и жизненный цикл

Collector имеет самостоятельный build/artifact и может обновляться независимо от Server в пределах совместимости контракта.

Несколько Collector (первоначально 3–5 Windows-компьютеров) подключаются к одному Server и идентифицируются как отдельные Agent.

В перспективе Collector может использоваться как самостоятельный небольшой продукт или подключаться к другой системе через иной adapter. Это не является целью первой версии и не должно создавать дополнительную абстракцию заранее.

## 10. Отношение к текущему Spike

Работающий Spike рассматривается как основа будущего Collector, но не переносится в production автоматически целиком.

При production-переходе:

- сохраняется проверенная парсинговая логика и полезный локальный UI;
- выделяются устойчивые `Collector Core`, source adapters и server adapter;
- экспериментальные зависимости и временные решения пересматриваются;
- существующая SQLite остаётся локальным хранилищем Collector и не заменяет PostgreSQL ERP;
- бизнес-логика ERP в Collector не добавляется.

## 11. Что сознательно не строим сейчас

- отдельный репозиторий только ради физического разделения Collector и ERP;
- микросервисную платформу;
- message broker без измеренной необходимости;
- универсальный plugin framework для любых внешних систем;
- сложный remote-browser-control;
- прямую синхронизацию локальной SQLite с PostgreSQL;
- source-specific логику на Server.

## 12. Критерии соблюдения ADR

Решение считается соблюдённым, если:

- Collector можно запустить и протестировать без ERP Server;
- Server можно разрабатывать без запуска Playwright;
- один и тот же Collector Core используется в local и server mode;
- Agent не имеет credentials к PostgreSQL ERP;
- Server получает данные только через версионированный контракт;
- source-specific изменения не требуют изменения ERP-бизнес-модулей;
- ERP-бизнес-процесс не требует изменения browser/parser слоя;
- обновление Agent и Server допускает контролируемую несовпадающую версию в рамках принятой политики совместимости.

## 13. Последствия

Положительные:

- работающий парсер не приходится переписывать под ERP;
- граница отказов и безопасности понятна;
- Collector можно развивать и тестировать отдельно;
- сервер остаётся чистым от browser/source-specific логики;
- проще масштабировать число Agent и добавлять источники;
- уменьшается связанность между сбором данных и бизнес-процессами.

Цена решения:

- нужен стабильный API и versioning contracts;
- появляется отдельный жизненный цикл Agent;
- требуется контролировать совместимость версий Server/Collector.

Эта цена признана оправданной и существенно ниже стоимости жёсткой связки браузерного сборщика с ERP Server.
