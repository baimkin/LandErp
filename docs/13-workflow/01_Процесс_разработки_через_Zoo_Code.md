# Процесс разработки LandErp через Zoo Code

## 1. Модель управления

Zoo Code анализирует, предлагает diff и команды. Владелец проекта отдельно
подтверждает каждую запись и выполнение команды. Отсутствие разрешения означает
остановку, а не поиск обходного пути.

## 2. Цикл одной задачи

1. Выбрать следующий `TP` из реестра.
2. Проверить зависимости и открытые вопросы.
3. Утвердить `TP` либо уточнить его.
4. Открыть новую задачу Zoo Code с одним главным результатом.
5. Попросить сначала прочитать указанные документы и показать план изменения.
6. Проверить список файлов, миграций, пакетов и команд.
7. Отдельно одобрять небольшие группы изменений.
8. После каждого логического шага просматривать diff.
9. Разрешить сборку и релевантные тесты.
10. Провести финальное ревью по чеклисту.
11. Обновить статус `TP` и журнал разработки.
12. Создать логический commit вручную.

## 3. Обязательные контрольные точки

| Момент | Zoo Code обязан показать | Решение владельца |
|---|---|---|
| До записи | цель, файлы, зависимости, риски | одобрить/изменить |
| До установки пакета | назначение, лицензия, альтернатива платформы | одобрить/отклонить |
| До миграции | DDL-эффект, данные, rollback | одобрить/изменить |
| До команды | точную команду и ожидаемый эффект | выполнить/отклонить |
| После реализации | diff, тесты, ограничения | принять/вернуть |
| До commit | состав commit без секретов и чужих правок | создать вручную |

## 4. Размер задачи

Нормальная задача изменяет один пользовательский или системный сценарий и
завершается проверяемым результатом. Если Zoo Code предлагает одновременно
создать БД, авторизацию, UI и парсер, задачу нужно разделить.

Ориентиры остановки:

- более 15–20 существенно изменяемых файлов;
- новая архитектурная зависимость;
- более одной миграции разных бизнес-модулей;
- изменение публичного Agent/API-контракта вместе с несвязанной фичей;
- необходимость «заодно» переработать соседний модуль.

## 5. Запрещённые обходы

- не ослаблять тесты ради зелёной сборки;
- не отключать nullable, analyzers или warnings-as-errors;
- не создавать mock вместо требуемого вертикального результата;
- не менять принятый ADR внутри реализации;
- не делать `git push`, merge, rebase или удаление истории;
- не открывать секреты, cookies и browser profile;
- не устанавливать пакет без отдельного обоснования.
