# 08 — Организация

**Статус:** approved UI reference  
**Экран:** единый административный раздел структуры компании и сотрудников  
**UI reference:** `docs/14-ui-kit/prototypes/landerp_organization_v1_3.html`

## Назначение

Раздел `Организация` заменяет два разрозненных пункта `Сотрудники` и `Оргструктура` одним понятным рабочим пространством.

Внутри три вкладки:

1. `Структура` — отделы → команды → сотрудники;
2. `Сотрудники` — плоский список людей и управление учётными записями/назначениями;
3. `Должности` — справочник должностей.

Права доступа не смешиваются с оргструктурой. Должность, роль и scope — разные понятия.

## Навигация

В левом меню должен остаться один пункт `Организация`.

Старые маршруты `/employees` и текущий `/organization` при переходе на новую страницу не должны ломать сохранённые ссылки: допустим redirect/alias на нужную вкладку.

Рекомендуемый основной route: `/organization`, вкладки могут храниться в query/state (`structure`, `employees`, `positions`).

## 1. Вкладка «Структура»

Главная задача — сразу видеть реальную организацию людей, а не три технические формы создания сущностей.

Иерархия фиксированная и простая:

`Отдел → Команда → Сотрудники`

Команда — **не подотдел**. В Stage 1 вложенные отделы/команды не нужны.

Для отдела показываются:

- название и краткое описание;
- количество сотрудников;
- количество команд;
- руководитель отдела, если назначен;
- состояние `Активен / В архиве`;
- действия `Добавить команду`, `Изменить`, `Архивировать/Восстановить`.

Для команды:

- название и описание;
- количество сотрудников;
- руководитель команды, если используется;
- состояние;
- действия `Изменить`, `Архивировать/Восстановить`.

Под раскрытой командой видны сотрудники: ФИО, должность, непосредственный руководитель и состояние. Сотрудники отдела без Team показываются отдельной группой `Без команды`.

Нужны поиск по отделу/команде/сотруднику, `Развернуть все / Свернуть все` и опция показа архивных элементов.

### CRUD и архив

Постоянные формы создания на странице убрать. Создание и изменение отдела/команды выполняются через небольшие модальные окна.

Физическое удаление рабочих сущностей не использовать. Архив:

- скрывает элемент из обычных списков выбора;
- сохраняет историю и ссылки;
- не должен оставлять активных сотрудников в недействительной структуре;
- при наличии зависимостей сервер либо блокирует архив до переназначения, либо выполняет явный безопасный сценарий, но не делает скрытых каскадных изменений.

Переименование допустимо всегда при соблюдении optimistic concurrency/audit.

## 2. Вкладка «Сотрудники»

Это основной экран ежедневного администрирования людей.

Таблица:

- сотрудник / логин;
- отдел / команда;
- должность;
- руководитель;
- состояние;
- действие `Открыть`.

Фильтры: текстовый поиск, отдел, состояние. При необходимости позже можно добавить фильтр по команде/должности без изменения модели.

Карточка/модальное окно сотрудника используется и для создания, и для редактирования.

### Основной сценарий создания сотрудника

Основной Stage 1 UX — **простое создание учётной записи администратором**, без обязательной email-активации:

1. администратор нажимает `+ Добавить сотрудника`;
2. заполняет ФИО, логин, отдел, команду, должность, руководителя;
3. в закрытом блоке `Дополнительно · доступ` при необходимости меняет роль и область доступа;
4. сервер создаёт Employee + User и генерирует криптографически стойкий временный пароль;
5. UI один раз показывает логин и временный пароль;
6. есть кнопки `Копировать` и `Скопировать логин и пароль`, чтобы передать данные сотруднику, например в Telegram;
7. по умолчанию включён флаг `Потребовать сменить временный пароль при первом входе`.

Логин — отдельное имя пользователя и **не обязан быть email**. Email в будущем может быть необязательным контактным полем.

Автоподсказка логина по ФИО допустима только как UI convenience; сервер всё равно проверяет уникальность и нормализует значение.

### Безопасность временного пароля

Обязательные правила:

- пароль генерируется **на сервере** криптографически стойким RNG, а не JavaScript-кодом прототипа;
- plaintext возвращается только в ответе на успешное создание/сброс и показывается один раз;
- plaintext пароль не хранится в БД, логах, audit payload, telemetry или timeline;
- в Identity хранится только стандартный password hash;
- при закрытии результата пароль нельзя повторно прочитать;
- если пароль потерян, используется `Сбросить пароль`, создающий новый временный пароль;
- reset должен инвалидировать старый пароль и при необходимости активные security sessions через стандартные механизмы ASP.NET Identity;
- если включён `MustChangePassword`, до смены временного пароля пользователь не должен работать с ERP как с обычной активной сессией.

Текущие Identity settings требуют unique/confirmed email. Для утверждённого UX серверную Identity-конфигурацию необходимо адаптировать так, чтобы username/password account мог быть создан и использоваться без обязательного email invitation, не ослабляя password/lockout policy.

### Существующее приглашение

Текущий сценарий `InvitationId + OneTimeToken + /account/activate` не удалять без необходимости. Он может остаться **вторичным** вариантом (`Пригласить по ссылке/email`) для будущего использования, но не должен быть единственным способом добавить сотрудника.

### Редактирование сотрудника

Через `Открыть` доступны:

- изменение отдела;
- команды;
- должности;
- руководителя;
- роли;
- scope;
- `Сбросить пароль`;
- `Отключить` / `Восстановить`.

Сотрудников физически не удалять. Отключённый пользователь не может войти, но история его действий и бизнес-ссылки сохраняются.

Должность не назначает права автоматически. Роль/scope изменяются явно.

## 3. Вкладка «Должности»

Должности — простой справочник организации.

Показывать:

- название;
- число активных сотрудников;
- где используется;
- состояние;
- действия `Изменить`, `Архивировать/Восстановить`.

Создание/изменение — popup. Архивная должность недоступна для новых назначений. Активные назначения перед архивированием должны быть обработаны явно; не делать скрытую замену.

## Руководители

Текущая модель уже содержит `EmployeeAssignment.ManagerEmployeeId` для непосредственного руководителя сотрудника.

Для отображения одного руководителя отдела/команды в самой структуре нужен однозначный server-owned источник истины. Не выводить руководителя из текста должности (`"Руководитель отдела ..."`) и не угадывать его по большинству назначений.

При реализации выбрать минимальный явный вариант:

- `OrgUnit.ManagerEmployeeId?`;
- `Team.ManagerEmployeeId?` — только если реально нужен отдельный руководитель команды.

Если отдельный руководитель команды пока не нужен бизнесу, колонка команды может показывать руководителя сотрудников или `—`, но не должна содержать эвристику.

## Server delta относительно текущего Stage 1

Сейчас `IOrganizationWorkspace` умеет читать данные, создавать Department/Position/Team, приглашать сотрудника и менять assignment. Для утверждённого экрана нужны дополнительные серверные операции.

Минимальный набор:

- rename/update Department;
- archive/restore Department;
- rename/update Team, при необходимости перенос между Department;
- archive/restore Team;
- rename/update Position;
- archive/restore Position;
- direct create Employee/User с username + временным password;
- update employee assignment;
- reset temporary password;
- deactivate/reactivate Employee/User;
- серверные counts/summary для структуры;
- явные manager fields, если утверждены;
- audit для всех административных изменений.

Не добавлять универсальный «CRUD framework» ради этой страницы. Реализовать небольшие команды Organization/Identity поверх существующих сущностей и permission model.

## Permissions

Использовать существующие permissions:

- `users.read` — просмотр сотрудников;
- `users.manage` — создание, назначение, deactivate/reactivate, password reset;
- `organization.manage` — отделы, команды, должности;
- `roles.manage` — изменение роли/scope там, где текущая policy это требует.

UI скрывает/disabled недоступные действия, но сервер всегда проверяет permission самостоятельно.

## Состояния и целостность

Минимальные инварианты:

- Team принадлежит ровно одному Department;
- Employee может быть без Department/Team, но Team нельзя назначить без соответствующего Department;
- Team сотрудника должна принадлежать выбранному Department;
- Manager не может быть самим сотрудником;
- login уникален согласно нормализации Identity;
- archived Department/Team/Position нельзя назначать новым сотрудникам;
- disabled Employee не может авторизоваться;
- optimistic concurrency применяется к редактируемым сущностям;
- все create/update/archive/restore/reset/deactivate действия аудируются, **без секретов**.

## UI reference и граница прототипа

`landerp_organization_v1_3.html` — эталон композиции, иерархии, вкладок и interaction patterns.

JavaScript прототипа демонстрационный. В частности, генерация временного пароля в браузере существует только для визуальной демонстрации и **не является production-логикой**.

Production UI реализуется на текущем Blazor/UI-kit стеке проекта; reference HTML не копируется как production-код.

## DoD

Экран считается законченным, когда можно пройти сквозные сценарии:

- создать отдел → создать в нём команду → увидеть дерево;
- переименовать и безопасно архивировать/восстановить элементы;
- создать сотрудника без email invitation → получить один раз login/password → войти ими;
- при включённом флаге сменить временный пароль при первом входе;
- назначить сотруднику отдел/команду/должность/руководителя и увидеть это одновременно в `Структура` и `Сотрудники`;
- сбросить пароль и убедиться, что старый больше не работает;
- отключить пользователя и убедиться, что вход запрещён;
- восстановить пользователя без потери истории;
- archived элементы не предлагаются для новых назначений;
- permissions и audit подтверждены тестами.

Эта UI-задача не отменяет активный P0 `Catalog → Procurement`: приоритет реализации определяется `docs/03-active/ACTIVE_TASK.md`.
