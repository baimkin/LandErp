# OP-002 — CI/CD и окружения

**Версия:** 0.1  
**Статус:** Черновик  
**Владелец:** технический владелец / эксплуатация  
**Зависимости:** ADR-001, ADR-002, ADR-004, ADR-005, FP-001

## 1. Результат

Каждый commit проверяется одинаково, а Staging и Production получают
воспроизводимые подписанные/идентифицируемые артефакты. Server и Worker одной
версии развёртываются согласованно; миграции выполняются контролируемым шагом;
Agent выпускается отдельно и остаётся совместимым с сервером на время поэтапного
обновления 3–5 компьютеров.

Конкретный CI и облачный провайдер заполняются после выбора. Процесс ниже от них
не зависит.

## 2. Окружения

| Окружение | Данные | Назначение | Доступ |
|---|---|---|---|
| Local | вымышленные | разработка | разработчик |
| Test/CI | одноразовые | автоматические проверки | CI |
| Staging | синтетические/обезличенные | миграции, интеграция, приёмка | команда |
| Production | реальные | работа бизнеса | по ролям |

Production данные не копируются в Staging без отдельной процедуры обезличивания.
Секреты, базы и object storage у окружений разделены.

## 3. Обязательный CI на pull request

1. восстановление закреплённых зависимостей;
2. форматирование/analyzers и сборка с warnings as errors;
3. unit и architecture tests;
4. integration tests на PostgreSQL 18 и файловом контракте;
5. contract tests Server–Agent;
6. parser fixture tests и контроль качества;
7. Blazor component tests и выбранный минимальный E2E smoke;
8. проверка миграций на пустой БД и обновлении предыдущей схемы;
9. поиск секретов и проверка известных уязвимостей зависимостей;
10. создание traceable build metadata.

Нестабильный тест не отключается молча: он получает владельца и срок исправления.

## 4. Артефакты и версии

- Server/Worker собираются из одного commit SHA и получают общий release version.
- Контейнеры имеют immutable tag; `latest` не используется для развёртывания.
- Миграционный артефакт связан с той же версией.
- Agent package имеет собственную версию и диапазон поддерживаемого API contract.
- UI отображает версию сервера; административный экран — версии всех Agent.
- SBOM и перечень лицензий сохраняются вместе с релизом.

## 5. Поставка Server и Worker

Рекомендуемый поток:

1. merge в защищённую ветку создаёт кандидат;
2. автоматическая поставка в Staging;
3. smoke и проверка миграции/rollback-сценария;
4. ручное разрешение Production уполномоченным лицом;
5. pre-deploy backup/проверка готовности по риску изменения;
6. expand-миграция;
7. rolling/restart поставка Server и Worker;
8. post-deploy health и бизнес-smoke;
9. наблюдение установленного окна;
10. фиксация результата релиза.

Автоматический Production deploy без gate не включается в ранней версии.

## 6. Миграции данных

- Отдельный job имеет право DDL; обычный Server по возможности его не имеет.
- Применяется expand–migrate–contract для несовместимых изменений.
- Деструктивный contract выполняется отдельным релизом после проверки, что старый
  код больше не используется.
- Миграция имеет timeout, лог и однозначный exit code.
- Автоматический down migration не считается безопасным rollback для данных.
- Долгая backfill-операция выполняется возобновляемым Worker job.

## 7. Поставка Agent

Agent не обязан обновляться одновременно на всех машинах. Сервер публикует
минимальную и рекомендуемую версии, принимает совместимый предыдущий контракт и
может запретить выдачу новых типов задач старому Agent.

Обновление идёт кольцами: одна тестовая машина, затем остальные. Package hash и
источник проверяются до установки. Самообновление не включается до выбора
подписанного канала и безопасного rollback; на старте допустима контролируемая
ручная установка по OP-010.

## 8. Feature flags и совместимость

Flag имеет владельца, срок удаления и безопасное значение по умолчанию. Он не
заменяет permission. Новая серверная функция сначала развёртывается выключенной,
если требует миграции потока или Agent. Удаление flag входит в Definition of Done
после стабилизации.

## 9. Откат

| Ситуация | Действие |
|---|---|
| Ошибка приложения без изменения данных | вернуть предыдущий immutable artifact |
| Ошибка новой функции | выключить feature flag/kill switch |
| Ошибка парсера | отключить adapter revision и остановить задания источника |
| Ошибка expand-миграции | остановить deploy, исправить forward; восстановление только по runbook |
| Повреждение данных | остановить записи, применить OP-003 и расследование |

Решение об откате фиксируется с версией, временем и ответственным.

## 10. Секреты и права pipeline

- отдельные identities для CI, Staging deploy и Production deploy;
- минимум прав и короткоживущие credentials;
- protected environments и аудит approvals;
- secret values не печатаются и не встраиваются в артефакт;
- pull request из недоверенного контекста не получает Production secrets;
- emergency access отделён и проверяется после использования.

## 11. Наблюдение релиза

Проверяются health, error rate, latency, migration status, очередь, lease expiry,
успех Agent API, parser quality и вход пользователей. Технический health без
успешного lease/result и открытия менеджерской очереди недостаточен.

## 12. Definition of Done

- CI является обязательным gate ветки;
- Staging развёртывается из того же артефакта, что Production;
- миграции и smoke автоматизированы;
- rollback/kill switch проверены;
- версии Server/Worker/Agent видимы;
- инструкция релиза содержит ответственного и журнал;
- выбранный облачный provider и команды подставлены без изменения принципов.

## 13. Требуется решение пользователя

Выбрать облако, CI-платформу и лицо, разрешающее Production. До этого план остаётся
провайдер-независимым и не блокирует проектирование фич.
