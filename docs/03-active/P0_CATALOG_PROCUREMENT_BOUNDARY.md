# P0 — Граница Catalog → Procurement

**Статус:** выполнено; owner correction по database transition утверждён 2026-09-15  
**Приоритет:** P0 — каноническая граница Catalog / Procurement  
**Дата решения:** 2026-09-15  
**Ветка:** `codex/stage-1-procurement-core`  
**Database transition correction:** [`STAGE1_PHASE1_DATABASE_RESET_DECISION.md`](STAGE1_PHASE1_DATABASE_RESET_DECISION.md)

## 1. Почему это P0

Текущая Stage 1 реализация ошибочно делает внешний `Listing` фундаментом закупочного процесса:

- `PropertyCase` содержит обязательный `ListingId`;
- публичные команды Procurement адресуются через `listingId`;
- очередь Procurement строится запросом от `Listings`;
- основные данные карточки PropertyCase фактически читаются из Listing;
- Catalog использует `ListingSource` из Collector Contracts, где сейчас только `Avito` и `Cian`.

Это неверная граница доменов. Объявление или сообщение во внешнем источнике — только источник входящих данных. Реальный объект закупки и весь цикл работы с ним — внутренняя сущность LandErp.

**До исправления этой границы не наращивать Procurement поверх обязательного ListingId.**

## 2. Утверждённая бизнес-модель

Целевая цепочка:

`Avito / Cian / Telegram / ручной ввод / знакомый / агент / другой источник`

→ **Catalog: единый список входящих предложений / объявлений**

→ менеджер выполняет первичный отбор

→ `Взять в работу`

→ создаётся или выбирается **PropertyCase**

→ входящий элемент связывается с PropertyCase как источник

→ `переговоры → проверки → осмотр → DD → решение → куплено`

→ после покупки дальнейший контур относится к `LandAsset / Наши объекты`.

### Главный инвариант

`Catalog item` и `PropertyCase` — разные сущности с разным жизненным циклом.

- Catalog хранит **что пришло извне**.
- PropertyCase хранит **наш внутренний рабочий объект закупки**.
- PropertyCase не принадлежит Avito, Cian, Telegram или любой другой площадке.
- Закрытие, удаление или изменение внешнего объявления не должно ломать PropertyCase.

## 3. Catalog — универсальный входящий поток

Catalog больше не трактуется как хранилище только Avito/Cian.

В единый список входящих могут попадать:

- Avito;
- Cian;
- Telegram и другие каналы/группы;
- ручной ввод сотрудником;
- рекомендация знакомого;
- агент / риелтор;
- прямой контакт собственника;
- будущие интеграции и импорты.

UI может продолжать называться `Входящие объявления`, пока это удобно пользователям. Техническая сущность должна быть нейтральной к конкретной площадке. Рабочее концептуальное имя — `CatalogItem`; немедленное физическое переименование текущей таблицы/класса `Listing` не является самоцелью, если миграция безопаснее в два шага.

### Минимальные данные Catalog item

Элемент входящего каталога должен допускать:

- `Id`, `OrganizationId`;
- server-owned тип/код источника;
- `ExternalId?`;
- `Url?`;
- заголовок / описание;
- цена / валюта;
- площадь;
- локация;
- контакт / продавец, если известен;
- фото / вложения, если есть;
- время получения/обнаружения;
- provenance: кем/чем создано и откуда пришли данные;
- revision/audit по действующим правилам проекта.

Для ручного элемента `ExternalId` и `Url` не обязательны.

### Источник не должен принадлежать Collector Contract

Catalog не должен зависеть от enum `LandErp.Collector.Contracts.V1.ListingSource` как от общей доменной классификации источников.

Collector Contract может по-прежнему описывать способности конкретного парсера (`Avito`, `Cian`). Server при приёме результата маппит их в server-owned source code Catalog.

Добавление в будущем `Telegram`, `Referral`, `Manual`, `Agent`, `Other` не должно требовать изменения бинарного Collector Contract, если соответствующий источник вообще не собирается этим Collector.

### Никаких фиктивных Collector Job для ручных данных

Ручной/Telegram/импортированный Catalog item не должен получать выдуманные `AgentId`, `JobId` или fake observation только ради существующей схемы.

Collector observations остаются историей автоматического сбора. Для других способов поступления используются нормальные provenance/audit данные соответствующего ingestion path.

## 4. Входящие и ручное добавление

На сервере должна быть application-команда создания входящего Catalog item вручную. Web UI должен получить простое действие `+ Добавить объявление / предложение`.

Минимальный сценарий:

- выбрать источник (`Telegram`, `Знакомый`, `Агент`, `Другое` и т.п.);
- название/локация;
- цена при наличии;
- площадь при наличии;
- ссылка при наличии;
- кадастровый номер или другие известные данные при наличии;
- комментарий;
- сохранить во входящие.

После сохранения элемент проходит **тот же первичный отбор**, что и результат парсера: отклонить, наблюдать, связать с существующим объектом или взять в работу.

## 5. PropertyCase — самостоятельная сущность Procurement

`PropertyCase` должен быть самостоятельным aggregate/root закупочного процесса.

Обязательная зависимость `PropertyCase.ListingId` должна быть устранена.

PropertyCase имеет собственный идентификатор и собственные рабочие факты, необходимые для закупки. Минимально он должен уметь существовать и читаться без какого-либо внешнего объявления.

Внутренние подтверждённые/рабочие факты PropertyCase не должны вычисляться каждый раз из текущего Listing. Пример:

- Telegram сообщает `15 соток`;
- Avito сообщает `14,8 соток`;
- Росреестр подтверждает `14,73 сотки`.

В источниках сохраняются исходные значения, а рабочий PropertyCase может содержать подтверждённое значение `14,73`.

Не копировать в PropertyCase все поля источника. Хранить только факты, реально принадлежащие внутреннему процессу объекта.

## 6. Связь входящих элементов с PropertyCase

Один PropertyCase может иметь несколько источников:

`PC-...`

→ Telegram item  
→ Avito item  
→ Cian item

Связь должна храниться отдельно от жизненного цикла PropertyCase. Допустима отдельная сущность/таблица вроде `PropertyCaseCatalogItem` / `PropertyCaseSourceLink` с типом связи и audit/provenance.

Для подтверждённой связи один Catalog item не должен одновременно считаться каноническим источником двух разных PropertyCase. Возможные совпадения могут существовать как отдельные неподтверждённые match records по правилам FP-024.

`PropertyCase` должен уметь существовать с `0..N` связанными Catalog items. Ноль допустим как технический инвариант для импорта/восстановления и самостоятельного создания case, хотя обычный пользовательский поток начинается из входящего каталога.

## 7. Команда `Взять в работу`

`Взять в работу` относится к границе Catalog → Procurement.

Команда должна:

1. работать по `CatalogItemId`/текущему идентификатору входящего элемента;
2. проверить, не связан ли элемент уже с PropertyCase;
3. позволить создать новый PropertyCase либо связать с существующим;
4. создать внутренний BusinessNumber `PC-...` при новом кейсе;
5. инициализировать только допустимые рабочие факты из входящего элемента;
6. записать связь источника с PropertyCase;
7. создать assignment/task по действующим правилам Procurement;
8. записать business timeline + audit;
9. после этого вся дальнейшая работа адресуется **CaseId**, а не ListingId.

Повтор команды должен быть идемпотентно/явно обработан и не создавать второй PropertyCase случайно.

## 8. Очередь закупки должна быть PropertyCase-based

После исправления запрос рабочей очереди начинается с `PropertyCases`, а не с `Listings`.

Фильтрация, права, assignment, next action, stage, переговоры, проверки и история относятся к PropertyCase/Workflow.

Связанные Catalog items используются только для:

- provenance;
- отображения источников;
- исходных цен/описаний/фото;
- истории изменения внешних объявлений;
- сигналов о новых изменениях источника.

Изменение Listing/Catalog item может создать сигнал `источник изменился`, но не должно автоматически перезаписывать подтверждённые рабочие факты PropertyCase.

После создания PropertyCase публичные операции Procurement должны адресоваться по `CaseId`:

- `ReadCase(caseId)`;
- решения/передачи/заметки/переговоры/проверки — `CaseId`;
- Listing/CatalogItemId остаётся только у действий входящего каталога и source-linking.

## 9. Права и область видимости

Procurement после перехода не должен определять доступ к PropertyCase через `Listing.DepartmentId` / `Listing.TeamId`.

Доступ к рабочему объекту закупки определяется через его organization scope, assignment, manager/responsibility и действующую систему permissions.

Правила видимости самого входящего Catalog могут развиваться отдельно. Они не должны становиться скрытой зависимостью жизненного цикла PropertyCase.

## 10. Database transition Phase 1 — clean rebuild

Решением владельца от 2026-09-15 pre-Phase-1 базы LandErp признаны **disposable development/test state**. Их данные не являются production data и не требуют in-place migration.

Канонический Phase 1 transition:

1. существующую dev/test БД удалить;
2. создать чистую БД;
3. применить полный migration chain к пустой БД;
4. проверить `Database.HasPendingModelChanges() == false`;
5. проверить текущие Avito/Cian и manual/Telegram-like сценарии уже на новой модели.

Следствия:

- Phase 1 migration является **schema-only** и не выполняет legacy data backfill;
- не требуется переносить старые `PropertyCase.ListingId` в source links;
- не требуется сохранять pre-Phase-1 BusinessNumber/workflow/timeline/audit/Observation dataset, потому что этот dataset не является сохраняемым production state;
- nullable compatibility field `PropertyCase.ListingId` может физически остаться до Phase 9, но новые business operations от него не зависят;
- ownership источников существует только через `PropertyCaseSourceLink`;
- legacy `/procurement/listings/{ListingId}` резолвит confirmed source link и не использует `PropertyCase.ListingId` как каноническую связь;
- не пытаться «долечивать» старые локальные базы — их следует пересоздать.

Это owner-approved уточнение **supersede-ит** конфликтующие требования legacy backfill/preservation в ранней версии этого P0 и в `STAGE1_COMPLETION_MASTER_PLAN.md` только для Phase 1 pre-production database transition. Правила безопасных production migrations для последующих фаз остаются обязательными.

Если физическое переименование `Listing` → `CatalogItem` создаёт ненужный миграционный риск, его разрешено отложить. **Запрещено** откладывать саму архитектурную независимость PropertyCase от Listing.

## 11. Порядок реализации — обязателен

1. Добавить/скорректировать тесты, фиксирующие целевые инварианты.
2. Исправить domain/data model Catalog ↔ Procurement.
3. Применить schema-only Phase 1 migration на clean database.
4. Перевести application contracts Procurement с `ListingId` на `CaseId` после создания кейса.
5. Перевести `ProcurementWorkspace`/queue/card на PropertyCase-root queries.
6. Добавить server command ручного создания Catalog item.
7. Добавить/обновить source linking.
8. Адаптировать Incoming UI минимально: ручное добавление + `Взять в работу`.
9. Проверить существующий Avito flow и полный manual/Telegram-like flow.
10. Только после green tests продолжать следующие модули.

Не делать параллельно большой редизайн UI, кабинет инвестора или пост-покупочные модули.

## 12. Обязательные acceptance scenarios

Реализация не считается законченной без следующих сценариев:

- вручную создан `Telegram` item без URL и без external id → виден во входящих;
- этот item можно отклонить/наблюдать так же, как Avito item;
- `Взять в работу` создаёт один PropertyCase и source link;
- созданный PropertyCase открывается и проходит workflow без существования Avito/Cian Listing;
- PropertyCase отображается в очереди, потому что очередь строится от PropertyCase;
- позже к тому же PropertyCase привязывается Avito item;
- затем привязывается Cian item;
- исходные значения каждого источника сохраняются отдельно;
- изменение цены на Avito не уничтожает текущую подтверждённую цену/факты PropertyCase;
- manual/Telegram item не создаёт fake Collector Agent/Job;
- clean database поднимается полным migration chain без legacy data/backfill и без pending model changes;
- права Procurement не зависят от наличия Listing;
- concurrency/audit сохраняются;
- legacy ListingId route открывает уже связанный Case и не создаёт Case для несвязанного source.

## 13. Не входит в P0

- внутренний рефактор локального Parser Agent;
- Telegram monitor как отдельная интеграция — сейчас нужен только корректный серверный ingestion boundary;
- LandAsset implementation;
- кабинет инвестора;
- расширенная рыночная аналитика;
- AI matching источников;
- большой визуальный редизайн.

## 14. Документы, которые это решение уточняет

Этот P0 документ является приоритетным уточнением текущей Stage 1 реализации и старых feature plans в части границы Catalog/Procurement.

В частности, любые места, где `PropertyCase` неявно или явно требует `Listing`, читать с учётом этого решения. FP-024 остаётся полезным для сопоставления нескольких внешних источников с одним реальным объектом, но не делает Listing владельцем PropertyCase.

Database-transition semantics дополнительно зафиксированы в [`STAGE1_PHASE1_DATABASE_RESET_DECISION.md`](STAGE1_PHASE1_DATABASE_RESET_DECISION.md). В силу приоритета этого P0 более старые требования master-plan о migration legacy Stage 1 dataset не применяются к Phase 1.
