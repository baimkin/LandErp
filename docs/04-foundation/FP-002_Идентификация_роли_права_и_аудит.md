# FP-002 — Идентификация, роли, права и аудит

**Версия:** 0.1  
**Статус:** Черновик  
**Владелец бизнес-решения:** владелец продукта  
**Технический владелец:** архитектор / специалист по безопасности  
**Зависимости:** генеральный план, ADR-001, FP-001, ADR-004  
**Блокирует:** административные экраны, работу агентов, менеджерский интерфейс и кабинет инвестора

## 1. Решение в одном абзаце

Создать единый контур идентификации для сотрудников, инвесторов и машинных
агентов с разными типами учётных записей. Пользовательские действия защищаются
именованными разрешениями и областями доступа; стартовые роли являются наборами
разрешений, а не жёсткими проверками строк в коде. Инвестор получает доступ только
к назначенным проектам и опубликованным материалам. Критичные изменения
фиксируются в отдельном неизменяемом журнале аудита.

## 2. Почему делаем сейчас

- Все последующие endpoint и экраны должны изначально иметь серверную авторизацию.
- Добавление прав после появления данных обычно оставляет IDOR и скрытые обходы.
- Agent нельзя аутентифицировать пользовательским cookie или давать ему доступ к БД.
- Кабинет инвестора требует project scope ещё до создания внешних экранов.
- Изменения поисков, бюджетов и публикаций должны иметь автора с первого дня.

## 3. Измеримый результат

| Показатель | Цель |
|---|---|
| Защищённые endpoint | 100% непубличных endpoint имеют policy/permission |
| Отрицательные тесты | Для каждого мутирующего Use Case проверен отказ без права и вне scope |
| Инвесторская изоляция | Инвестор не видит чужой проект даже по известному ID |
| Машинная изоляция | Agent token не открывает пользовательский UI и бизнес-API |
| Аудит | Все перечисленные критичные действия имеют запись кто/когда/что/до/после |
| MFA | Обязательно для владельца и администратора до production |
| Отзыв доступа | Пользовательская сессия и агентский credential отзываются независимо |

## 4. Типы субъектов

| Тип | Пример | Способ входа | Основная область |
|---|---|---|---|
| Employee | Владелец, администратор, менеджер, наблюдатель | Интерактивный вход | Организация и назначенные объекты |
| Investor | Внешний инвестор | Приглашение и интерактивный вход | Только назначенные проекты |
| Agent | Локальный компьютер-сборщик | Машинный credential | Только Agent API |
| System | Worker и фоновые процессы | Внутренняя сервисная идентичность | Заранее определённые фоновые Use Case |

Пользовательская и машинная идентичность не объединяются одним типом токена и
не используют общие роли.

## 5. Стартовые роли

| Роль | Назначение | Не означает автоматически |
|---|---|---|
| Owner | Все бизнес-данные и критические решения организации | Доступ к секретам инфраструктуры |
| Administrator | Пользователи, поиски, расписания, агенты, источники и диагностика | Право утверждать бюджет и выплаты без отдельного разрешения |
| Manager | Объявления, объекты, решения, контакты и назначенные проекты | Управление ролями и системными секретами |
| Viewer | Разрешённый внутренний просмотр | Экспорт и просмотр персональных данных |
| Investor | Назначенные проекты и опубликованные материалы | Просмотр чужих участников и внутренних черновиков |

Роль ускоряет назначение прав. Endpoint проверяет конкретное разрешение и scope.

## 7. Области доступа

| Scope | Значение |
|---|---|
| Organization | Все разрешённые данные одной организации |
| AssignedProjects | Только проекты, назначенные сотруднику |
| InvestorProjects | Только проекты, назначенные инвестору |
| OwnTasks | Собственные задачи пользователя |
| PublishedProjectData | Только опубликованные инвестору данные проекта |
| AgentSelf | Только собственное устройство, аренды и результаты агента |

`OrganizationId`, `ProjectId` и другие scope-ID из URL не считаются доказательством
доступа. Сервер сопоставляет их с идентичностью и разрешениями.

## 8. Основные пользовательские сценарии

### 8.1. Создание сотрудника

1. Пользователь с `users.manage` создаёт приглашение.
2. Система привязывает приглашение к организации и выбранным ролям.
3. Получатель завершает регистрацию и подтверждает контакт.
4. Система создаёт активную учётную запись и фиксирует аудит.
5. До выполнения требований MFA критичные административные права не активны.

### 8.2. Изменение ролей

1. Сервер проверяет `roles.manage` и Organization scope.
2. Нельзя удалить последнего активного Owner без безопасной передачи владения.
3. Изменение сохраняется транзакционно.
4. Активные сессии при повышении/понижении прав пересматриваются по политике.
5. Аудит хранит набор прав до и после.

### 8.3. Приглашение инвестора

1. Сотрудник создаёт профиль инвестора и приглашение.
2. Инвестору не назначается проект автоматически.
3. После активации учётной записи сотрудник выдаёт доступ к конкретному проекту.
4. Доступ содержит разрешённые разделы и период действия при необходимости.
5. Инвестор видит только опубликованные данные этого проекта.

### 8.4. Регистрация Agent

1. Администратор создаёт одноразовый registration token.
2. Agent обменивает его на собственную машинную идентичность.
3. Сервер сохраняет fingerprint только в безопасной форме и capabilities.
4. Долгоживущий credential хранится средствами ОС.
5. Администратор может pause, drain или revoke конкретное устройство.

## 9. Отрицательные сценарии

- Пользователь без разрешения получает `403`, а не пустой успешный ответ.
- Неаутентифицированный пользователь получает `401` без сведений о существовании объекта.
- Инвестор с доступом к проекту A запрашивает ID проекта B — `403` или безопасный `404`
  по единой политике против утечки существования.
- Менеджер меняет `OrganizationId` в payload — сервер игнорирует его как источник
  scope и использует доверенный контекст.
- Agent token обращается к `/admin` или пользовательскому API — отказ.
- Отозванный Agent не получает новое задание и не продлевает аренду.
- Истёкшее приглашение нельзя использовать повторно.
- Последнего Owner нельзя деактивировать обычной командой.

## 10. Данные

### 10.1. Основные сущности

| Сущность | Назначение |
|---|---|
| UserAccount | Пользовательская идентичность и состояние |
| OrganizationMembership | Связь пользователя с организацией |
| Role | Именованный набор разрешений |
| Permission | Стабильное системное разрешение |
| RolePermission | Состав роли |
| UserRoleAssignment | Назначение роли в области |
| ProjectAccessGrant | Доступ сотрудника или инвестора к проекту |
| Invitation | Одноразовое приглашение с типом и сроком |
| UserSession | Управляемая активная сессия |
| AgentIdentity | Машинная идентичность и состояние |
| AgentCredential | Версия и отзыв машинного секрета без хранения открытого значения |
| AuditEvent | Неизменяемое критичное бизнес-событие |

Если используется ASP.NET Core Identity, его таблицы остаются частью IdentityAccess,
а доменные project grants и аудит не смешиваются с техническими claims без модели.

### 10.2. Ограничения

- нормализованный login/email уникален в выбранной области;
- invitation token хранится только как криптографический hash;
- credential Agent хранится только как hash/версия и может быть отозван;
- роль не удаляется, если назначена, без явной миграции назначений;
- ProjectAccessGrant уникален по subject + project + типу доступа;
- AuditEvent не обновляется и не удаляется обычным приложением;
- все даты блокировки, истечения и аудита используют `timestamptz`.

## 11. Аутентификация

### 11.1. Пользователи

Предпочтительный первый вариант — ASP.NET Core Identity или совместимый OIDC-
провайдер, выбранный ADR-004. Для браузера используется защищённая cookie-сессия с:

- `HttpOnly`, `Secure` и подходящим `SameSite`;
- защитой от CSRF для мутирующих запросов;
- ограниченным временем жизни и безопасным продлением;
- отзывом сессий;
- MFA минимум для Owner и Administrator;
- rate limit и lockout для попыток входа.

### 11.2. Agent

Agent использует отдельную схему аутентификации, ограниченную маршрутами Agent API.
Предпочтительный механизм выбирается ADR-004 после определения среды: клиентский
сертификат или ротируемый высокоэнтропийный credential с привязкой к устройству.

## 12. Авторизация

Проверка состоит из двух независимых частей:

1. есть ли у субъекта требуемое разрешение;
2. входит ли запрашиваемый объект в разрешённую область.

Обе проверки выполняются внутри Use Case до чтения чувствительных данных и перед
изменением. UI-проверка используется только для удобства.

## 13. Аудит

### 13.1. Что записывать

- actor type и actor ID;
- организация и область проекта;
- UTC-время;
- correlation ID;
- тип действия;
- тип и ID объекта;
- результат;
- безопасные значения до и после для значимых полей;
- причина или комментарий при обязательности;
- источник действия: UI, API, Worker или Agent.

### 13.2. Что не записывать

- пароли;
- registration token;
- cookies;
- access/refresh token;
- полный секрет Agent;
- полный текст конфиденциального документа;
- лишние персональные данные.

### 13.3. Неизменяемость

AuditEvent append-only на уровне приложения. Исправление создаёт новое событие.
Удаление по политике хранения выполняет только отдельный привилегированный
операционный процесс и само фиксируется.

## 15. Эталонные примеры кода

### 15.1. Именованное разрешение

```csharp
public static class Permissions
{
    public const string SearchesRead = "searches.read";
    public const string SearchesManage = "searches.manage";
    public const string AgentsManage = "agents.manage";
    public const string AuditRead = "audit.read";
}
```

### 15.2. Требование разрешения

```csharp
public sealed record PermissionRequirement(string Permission)
    : IAuthorizationRequirement;

public sealed class PermissionAuthorizationHandler(
    IUserPermissionReader permissionReader,
    IHttpContextAccessor httpContextAccessor)
    : AuthorizationHandler<PermissionRequirement>
{
    protected override async Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        PermissionRequirement requirement)
    {
        if (context.User.Identity?.IsAuthenticated != true)
        {
            return;
        }

        CancellationToken cancellationToken =
            httpContextAccessor.HttpContext?.RequestAborted
            ?? CancellationToken.None;

        bool hasPermission = await permissionReader.HasPermissionAsync(
            context.User,
            requirement.Permission,
            cancellationToken);

        if (hasPermission)
        {
            context.Succeed(requirement);
        }
    }
}
```

Fallback `CancellationToken.None` нужен только для редкого вызова policy вне HTTP-
контекста. В HTTP-запросе отмена всегда берётся из `RequestAborted`.

### 15.3. Проверка проектной области внутри Use Case

```csharp
public sealed class GetInvestorProjectHandler(
    ICurrentUser currentUser,
    IProjectAccessReader projectAccessReader,
    IInvestorProjectReader projectReader)
{
    public async Task<InvestorProjectDto?> HandleAsync(
        Guid projectId,
        CancellationToken cancellationToken)
    {
        await projectAccessReader.EnsureInvestorCanReadAsync(
            currentUser.UserId,
            projectId,
            cancellationToken);

        return await projectReader.GetPublishedProjectAsync(
            projectId,
            cancellationToken);
    }
}
```

## 16. UI

### 16.1. Экраны первой очереди

- вход;
- принятие приглашения;
- включение и проверка MFA;
- список пользователей;
- карточка пользователя и роли;
- список Agent identities;
- создание/отзыв Agent registration;
- просмотр аудита с фильтрами;
- управление проектным доступом инвестора позже в соответствующем модуле.

### 16.2. Обязательные состояния

- loading без повторной отправки команды;
- empty с понятным следующим действием;
- validation error у конкретного поля;
- forbidden без раскрытия чужих данных;
- expired invitation;
- locked/disabled account;
- успешное изменение с ясным результатом;
- конфликт изменения роли другим администратором.

Опасные действия — отзыв доступа, сессии или Agent — требуют явного подтверждения
с названием субъекта и последствием.

## 17. Наблюдаемость

### Логи

- успех/ошибка входа без пароля;
- создание и погашение приглашения;
- отказ авторизации с permission code и безопасным scope;
- регистрация/отзыв Agent;
- системная ошибка записи аудита.

### Метрики

- число активных пользователей по типу;
- неуспешные входы и lockout;
- доля MFA у привилегированных пользователей;
- активные/отозванные Agent;
- ошибки authorization handler;
- задержка проверки прав.

Security-метрики не содержат email и финансовые данные.

## 18. Тестирование

| Уровень | Обязательные случаи |
|---|---|
| Unit | Состав ролей, правила последнего Owner, истечение приглашения, scope decision |
| Integration | Уникальность, транзакция назначения, append-only аудит, отзыв credential |
| API | 401, 403, validation, Problem Details, CSRF для cookie-команд |
| Security | IDOR между проектами, инвесторами и организациями; Agent против UI API |
| Architecture | Только IdentityAccess владеет внутренними моделями учётных записей |
| E2E | Приглашение → вход → MFA → разрешённый экран; инвестор → только свой проект |

Не использовать только mock authorization: минимум один набор проходит реальную
аутентификацию и policy pipeline.

## 19. Вертикальные этапы

### Этап 1. Вход одного Owner

Реальный вход, защищённый экран, выход, отзыв сессии, аудит и E2E-test.

### Этап 2. Сотрудники и роли

Приглашение, принятие, назначение роли, серверная policy и отрицательные тесты.

### Этап 3. Машинный Agent

Одноразовая регистрация, отдельная схема аутентификации, heartbeat-заглушка,
отзыв и security tests.

### Этап 4. Project scope инвестора

Профиль инвестора, grant к тестовому проекту, опубликованный read model и запрет
доступа к чужому проекту. Полный кабинет не реализуется.

### Этап 5. Аудит и административный просмотр

Обязательные действия записываются, фильтруются по праву и доступны для разбора.

## 20. Развёртывание и откат

- Первый Owner создаётся безопасной bootstrap-командой, не публичным endpoint.
- Bootstrap отключается после использования либо требует одноразовый секрет среды.
- Миграции совместимы с предыдущей версией Server.
- При ошибке новой policy доступ не ослабляется; фича закрывается безопасно.
- Отзыв credential Agent не откатывается вместе с приложением автоматически.
- Перед production проверяется восстановление доступа Owner.

## 21. Definition of Ready

- выбран механизм аутентификации ADR-004;
- определён первый Owner и способ bootstrap;
- подтверждены типы пользователей;
- подтверждено, будет ли несколько организаций в обозримом будущем;
- согласован стартовый каталог разрешений;
- определена политика MFA и сессий;
- есть тестовая модель Project для проверки scope.

## 22. Definition of Done

- сотрудники, инвесторы и Agent имеют разные безопасные контуры;
- каждый endpoint первой очереди имеет permission и scope test;
- последний Owner защищён от случайного удаления;
- MFA обязательно для привилегированных ролей;
- Agent credential можно независимо отозвать;
- инвестор не видит чужой проект по прямому ID;
- критичные изменения дают неизменяемый AuditEvent;
- секреты и персональные данные не попадают в ответы и логи;
- UI обрабатывает forbidden, expired, locked и conflict;
- E2E и security tests зелёные.

## 23. Открытые вопросы

| Вопрос | Блокирует |
|---|---|
| ASP.NET Core Identity или внешний OIDC | Реальный вход |
| Email, телефон или оба способа приглашения | UX приглашений |
| Нужна ли одна организация или несколько | Полную модель scope |
| Сертификат или ротируемый token для Agent | Машинную аутентификацию |
| Какой срок пользовательской сессии и Agent credential | Политику безопасности |
| Кто может назначать финансовые права | Состав ролей |
| Нужен ли маскированный `404` вместо `403` для чужого объекта | Единое API-поведение |
