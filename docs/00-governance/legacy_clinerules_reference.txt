# ПРАВИЛА РАЗРАБОТКИ LAND ERP
# Версия: 0.3
# Назначение: постоянные инструкции для ИИ и разработчиков

Этот файл задаёт обязательные правила разработки облачной ERP для поиска,
проверки, приобретения, подготовки, раздела и перепродажи земельных участков,
а также для ограниченного взаимодействия с инвесторами.

Правила применяются ко всему репозиторию. Если локальный файл правил в отдельной
папке устанавливает более строгие требования, действуют более строгие требования.


# 1. КОНТЕКСТ ПРОДУКТА

## 1.1. Назначение системы

- Система является единой облачной ERP, а не только парсером объявлений.
- Первый рабочий контур начинается со сбора объявлений и заканчивается очередью
  решений менеджера.
- Дальнейший контур ведёт реальный объект через уточнение, проверки, переговоры,
  покупку, подготовительные работы, раздел, продажу и расчёты с инвесторами.
- Сначала поддерживаются 30–50 вручную подготовленных ссылок поиска.
- Первый источник — Авито. Каждый следующий источник реализуется отдельным
  адаптером и отдельным планом.
- Сбор имеет два независимых уровня: поисковая выдача и подробная карточка.
- Задания выполняют 3–5 локальных браузерных агентов, управляемых сервером.
- Локальный агент не имеет прямого доступа к базе данных ERP.
- Расписания, поисковые ссылки, приоритеты, ограничения и агенты настраиваются
  администратором через веб-интерфейс.
- Кабинет инвестора входит в раннее развитие продукта, но показывает только
  назначенные проекты и опубликованные данные.

## 1.2. Границы первой версии

- Не создавать публичную инвестиционную площадку.
- Не принимать и не выводить деньги через систему.
- Не реализовывать электронное подписание договоров без отдельного решения.
- Не обещать и не рассчитывать гарантированную доходность.
- Не отправлять сообщения продавцам автоматически. Будущая отправка сообщений
  должна быть отдельной фичей с аудитом, лимитами и ручным подтверждением.
- Не считать CAPTCHA, блокировку или ограничение площадки задачей для обхода.
  Агент должен остановиться, сохранить диагностику и запросить внимание человека.
- Не считать данные объявления юридически подтверждёнными фактами.


# 2. ИСТОЧНИКИ ИСТИНЫ И ПОРЯДОК РАБОТЫ

## 2.1. Приоритет источников истины

При конфликте требований использовать следующий порядок:

1. Явное актуальное указание пользователя в текущей задаче.
2. Утверждённое архитектурное решение ADR.
3. Генеральный архитектурно-технический план.
4. Утверждённый план конкретной фичи.
5. Эти правила.
6. Существующий код и тесты как описание фактического поведения.

Если код расходится с утверждённым решением, не исправлять расхождение скрытно.
Зафиксировать его и согласовать область изменения.

## 2.2. Перед началом изменения

- Прочитать генеральный план, план затрагиваемой фичи и применимые ADR.
- Изучить существующий код, тесты, миграции и конфигурацию рядом с изменением.
- Проверить состояние рабочего дерева и не затрагивать чужие незавершённые правки.
- Сформулировать бизнес-результат, границы и критерии приёмки.
- Задать вопрос только тогда, когда неизвестность существенно меняет архитектуру,
  данные, безопасность, пользовательский сценарий или объём работ.
- Не блокировать работу вопросами, на которые можно безопасно ответить из
  утверждённых документов или существующего кода.
- В среде Zoo Code чтение разрешено, но любая запись файла и любая терминальная
  команда выполняются только после отдельного подтверждения владельца.
- До запроса подтверждения показать точный scope, файлы, зависимости, миграции,
  риски и ожидаемый эффект команды.
- Работать по одному `TP` со статусом `Утверждён`; статус `На согласовании` не
  является разрешением реализации.

## 2.3. После изменения

- Кратко перечислить изменённые файлы и бизнес-результат.
- Объяснить, как изменение вписывается в архитектуру.
- Указать выполненные проверки и их результат.
- Явно назвать известные ограничения и оставшиеся решения.
- Не утверждать, что задача завершена, если обязательная проверка не запускалась
  или завершилась ошибкой.


# 3. БАЗОВЫЙ ТЕХНИЧЕСКИЙ СТЕК

## 3.1. Принятая основа нового проекта

- C# 14 и .NET 10 LTS.
- ASP.NET Core и Blazor Web App.
- EF Core 10 и совместимая основная версия Npgsql.
- PostgreSQL 18 на актуальном minor-релизе.
- PostGIS предусматривается архитектурой, но не является обязательной
  зависимостью первого вертикального среза.
- Microsoft.Playwright для локальных браузерных агентов и E2E-тестов.
- TypeScript только для браузерной автоматизации, карт, сложных визуализаций и
  компонентов, где Blazor не даёт достаточного качества или производительности.

## 3.2. Запрет тихой смены версии

- Фактические версии определяются `global.json`, central package management,
  файлами проектов и утверждённым ADR.
- Для нового репозитория LandErp не использовать ранее обсуждавшиеся .NET 9 /
  C# 13 / EF Core 9.
- Запрещено попутно обновлять major-версии SDK, пакетов, PostgreSQL, Playwright или
  формата API в рамках несвязанной фичи.
- Версии взаимосвязанных пакетов EF Core и Npgsql должны быть совместимы по major.
- Все зависимости должны быть централизованно закреплены; плавающие версии
  пакетов запрещены.

## 3.3. Среда выполнения

- Не предполагать конкретную оболочку, букву диска или путь к `psql`, пока они не
  закреплены в документации репозитория.
- Команды должны быть воспроизводимы на заявленной среде разработки.
- Сервер, Worker и агенты должны запускаться независимо.
- Миграции в production не выполняются автоматически при старте приложения.
- Первый поддерживаемый Agent выпускается и тестируется для Windows x64.
- Общую логику Agent не связывать с Windows API; хранилище credential, автозапуск,
  пути и установщик размещать за ОС-специфичными интерфейсами.
- Не заявлять поддержку Linux/macOS до появления сборки, инструкции и тестовой
  матрицы для этих ОС.

## 3.4. Политика зависимостей

- Новая зависимость добавляется только для конкретной измеримой задачи, которую
  неразумно решать средствами платформы или небольшим собственным кодом.
- Для зависимости фиксируются владелец, лицензия, поддержка, версия, влияние на
  deployment и способ замены.
- Предпочитать встроенные возможности .NET/ASP.NET Core и официальные provider.
- Не добавлять MediatR, AutoMapper, FluentValidation, broker, Redis,
  Elasticsearch, UI/component library, map/chart library «на будущее».
- TypeScript и npm toolchain не входят в первый контур без реального JS-сценария.
- Исключения следуют ADR-006 и фиксируются в плане фичи/задачи.


# 4. АРХИТЕКТУРНЫЙ СТИЛЬ

## 4.1. Общий подход

- Архитектура сервера — модульный монолит.
- Организация прикладного кода — Feature-Driven Architecture и Vertical Slices.
- Web/API и серверная бизнес-логика развиваются как единая система с явными
  границами модулей.
- Фоновые задания выполняются отдельным Worker-процессом.
- Локальный браузерный агент является отдельным приложением и общается с сервером
  только через версионированный HTTPS API.
- В первой версии сохраняемая очередь и аренды заданий реализуются в PostgreSQL.
- Микросервисы и внешний брокер сообщений добавляются только после измеренного
  ограничения, подтверждённого ADR.

## 4.2. Доменные модули

Использовать следующие верхнеуровневые границы:

- IdentityAccess — пользователи, роли, разрешения, области доступа и сессии.
- Administration — настройки, расписания, источники, агенты и аварийные выключатели.
- Collection — поиски, задания, запуски, извлечение и наблюдения.
- PropertyCatalog — объявления, реальные объекты, участки, строения, совпадения и
  история сведений.
- ManagerWorkspace — очередь решений, комментарии, задачи, контакты и наблюдение.
- DueDiligence — юридические, кадастровые, градостроительные, технические и
  рыночные проверки с доказательствами.
- ProjectsFinance — покупка, сценарии, работы, бюджеты, лоты, продажи и движения
  капитала.
- InvestorPortal — участие, доступы, публикации, отчёты и обращения инвесторов.
- Reporting — управленческие показатели и утверждённые представления данных.

Новый модуль нельзя добавлять только ради удобного размещения файлов. Для него
должны существовать отдельный бизнес-смысл, данные, права и жизненный цикл.

## 4.3. Вертикальный срез

- Каждый Use Case размещается в отдельной папке внутри своего бизнес-модуля.
- Срез содержит входной контракт, валидацию, авторизацию, обработчик, выходной
  DTO, endpoint/UI-точку и тесты, относящиеся к этому сценарию.
- Не создавать технические папки `Controllers`, `Repositories`, `Models`,
  `Helpers` внутри бизнес-модуля.
- Не создавать `Common`, `Shared` или `Utils` как склад несвязанного кода.
- Небольшое осознанное дублирование между срезами допустимо и предпочтительнее
  скрытой связи между модулями.
- Вынос общего сервиса разрешён после появления минимум трёх реальных потребителей
  или когда сервис является инфраструктурной границей.

## 4.4. Границы зависимостей

- Один Use Case не вызывает endpoint или handler другого Use Case напрямую.
- Один модуль не обращается напрямую к внутренним типам и таблицам другого модуля.
- Межмодульное взаимодействие выполняется через публичный прикладной контракт,
  доменное событие или явно утверждённый read model.
- Общая база данных не означает общую модель данных без владельца.
- Каждая таблица, команда и событие должны иметь модуль-владелец.
- Циклические зависимости между модулями запрещены.
- Архитектурные ограничения должны проверяться автоматическими тестами.

## 4.5. Структура решения

Ориентир для нового репозитория:

- `src/LandErp.Server` — Blazor Web App, HTTP API и композиция приложения.
- `src/LandErp.Application` — модули, вертикальные срезы и прикладные контракты.
- `src/LandErp.Infrastructure` — EF Core, файлы, внешние источники и технические
  реализации интерфейсов.
- `src/LandErp.Worker` — планировщик, очереди и фоновые обработчики.
- `src/LandErp.Agent` — локальное приложение браузерного сбора.
- `src/LandErp.AgentContracts` — минимальные версионированные контракты сервер–агент.
- `tests` — модульные, интеграционные, архитектурные, контрактные и E2E-тесты.
- `docs` — генеральный план, ADR, планы фич, операционные инструкции и журнал решений.

Структура является архитектурным ориентиром. После создания репозитория её точный
вариант закрепляется ADR и архитектурными тестами.


# 5. ПРАВИЛА ИЗМЕНЕНИЯ КОДА

## 5.1. Отсутствие регрессий

- Не удалять существующую функциональность, обработчики, проверки, комментарии
  или документацию без явного основания задачи.
- Не переписывать большой файл ради локального изменения.
- Не подменять исправление упрощённой заглушкой.
- Не использовать многоточия и фразы «остальной код без изменений» внутри
  создаваемого или изменяемого файла.
- `TODO` допустим только как осознанный технический долг с идентификатором задачи;
  он не заменяет обязательную реализацию текущей задачи.
- Перед рефакторингом зафиксировать существующее поведение тестом, если оно не
  покрыто и должно сохраниться.

## 5.2. Механические изменения

- Не использовать ad-hoc PowerShell, Bash, `sed`, `awk` или регулярные выражения
  для массового изменения исходного кода без предварительной проверки области.
- Разрешены штатные форматтеры, миграции, генераторы клиентов и другие
  воспроизводимые инструменты проекта.
- После механического изменения обязательно проверить diff и убедиться, что не
  затронуты несвязанные файлы.
- Не переформатировать весь репозиторий в рамках небольшой фичи.

## 5.3. Читаемость C#

- Приоритет — явный и читаемый код, а не минимальное число строк.
- Использовать фигурные скобки для управляющих конструкций.
- Не использовать `#region` для сокрытия чрезмерного размера класса.
- Не создавать вложенные тернарные выражения.
- LINQ-запрос должен оставаться читаемым и предсказуемо транслироваться в SQL.
- Имена отражают бизнес-смысл, а не техническую операцию.
- Порядок членов класса: константы, поля, свойства, конструктор, публичные методы,
  приватные методы.
- Современные возможности языка применять только тогда, когда они улучшают
  ясность и соответствуют закреплённой версии C#.

## 5.4. Документация кода

- Публичные контракты, интерфейсы, модели интеграции и нетривиальные публичные
  методы должны иметь XML-документацию.
- Документация объясняет бизнес-смысл и ограничения, а не повторяет имя свойства.
- Финансовые формулы, правила доступа, алгоритмы сопоставления и переходы статусов
  должны иметь ссылку на план фичи или ADR.
- Комментарий объясняет причину решения; очевидные действия кода не комментировать.


# 6. API И ПРИКЛАДНЫЕ КОНТРАКТЫ

- Endpoint не обращается к `DbContext` напрямую; он вызывает конкретный Use Case.
- Каждый входной контракт валидируется на сервере.
- Авторизация проверяется на сервере для каждого запроса, независимо от UI.
- EF Core entities нельзя возвращать через API или напрямую привязывать к UI.
- Использовать специализированные DTO; не создавать один универсальный DTO для
  чтения, редактирования, списка и экспорта.
- Асинхронные endpoint, handlers и сервисы принимают `CancellationToken` и
  передают его во все поддерживающие отмену операции.
- Ошибки API возвращаются в едином формате Problem Details без утечки stack trace,
  SQL, секретов или внутренних путей.
- Мутирующие и повторяемые интеграционные команды должны поддерживать
  идемпотентность.
- Контракты сервер–агент версионируются явно и сохраняют обратную совместимость в
  течение утверждённого окна обновления агентов.
- Разрушающее изменение контракта требует отдельного ADR и плана развёртывания.


# 7. ДАННЫЕ И POSTGRESQL

## 7.1. Общие правила

- Для бизнес-идентификаторов использовать UUIDv7, если нет обоснованного исключения.
- Для времени использовать `DateTimeOffset` в C# и `timestamptz` в PostgreSQL.
- Запрещён `DateTime.Now`; текущее время получать через внедряемый `TimeProvider`.
- Деньги хранить и считать только как `decimal` / `numeric` с явно выбранной
  точностью и отдельным кодом валюты.
- Площадь, расстояние и другие измерения имеют единицу измерения в контракте.
- Не использовать `double` для финансовых расчётов.
- Не использовать строку как замену статусу, валюте, единице или типу события,
  если множество значений контролируется системой.
- Все таблицы и значимые столбцы должны иметь русские SQL-комментарии.
- Для частых фильтров, внешних ключей, уникальности и очередей создавать
  обоснованные индексы; индексы подтверждаются реальными запросами.

## 7.2. История и происхождение сведений

- Объявление, реальный объект и проект являются разными сущностями.
- Одно объявление может встречаться в нескольких поисках, но хранится один раз
  по `Source + ExternalId`.
- Каждое чтение источника создаёт неизменяемое наблюдение со временем, уровнем
  сбора, версией парсера и перечнем реально полученных полей.
- Новое наблюдение не стирает историю цены и доступности.
- Отсутствующее поле в выдаче не очищает значение, ранее полученное из карточки.
- Сведения источника, вывод системы и подтверждение специалиста хранятся раздельно.
- Ручное подтверждение пользователя не перезаписывается новым рекламным текстом.
- Противоречие создаёт признак качества данных или задачу уточнения, а не
  произвольный выбор одного значения.
- Сохранять происхождение критичных полей: источник, наблюдение, время, способ
  получения и, при наличии, подтверждающий документ.

## 7.3. JSON и исходные материалы

- Канонические поля, по которым выполняются поиск, сортировка, права и отчётность,
  хранятся типизированно, а не только в JSON.
- JSONB разрешён для версионированного снимка специфичных полей источника и
  диагностических метаданных.
- Исходный HTML, скриншоты и трассы имеют политику хранения, размерные лимиты и
  ограниченный доступ.
- Недоверенный HTML никогда не отображается как исполняемая разметка ERP.

## 7.4. Миграции

- Каждое изменение схемы сопровождается миграцией и проверкой на чистой БД.
- Миграция должна быть безопасна для существующих данных и отката приложения.
- Для рискованных изменений использовать подход expand–migrate–contract.
- Перед production-миграцией создать резервную копию и проверить восстановление
  согласно операционной инструкции.
- Production-миграции выполняются отдельным контролируемым шагом развёртывания.

## 7.5. PostGIS

- Первый сбор не зависит от PostGIS.
- При добавлении геометрии явно выбирать тип и SRID; для GPS-координат исходным
  стандартом считать WGS 84 / SRID 4326, если ADR не установил иное.
- Геометрические операции должны выполняться в PostgreSQL, а не после загрузки
  полного набора в память.
- Для геометрических столбцов создавать подходящие GiST/SP-GiST индексы.
- Пространственные методы EF/Npgsql использовать только при подтверждённой
  серверной трансляции.


# 8. ПАРСИНГ И ЛОКАЛЬНЫЕ АГЕНТЫ

## 8.1. Адаптеры источников

- Логика конкретной площадки изолируется в отдельном адаптере.
- Домен ERP не зависит от CSS-селекторов, текста кнопок или структуры URL площадки.
- Выдача и карточка являются разными типами заданий и разными парсерами.
- Селекторы и извлечение покрываются контрактными тестами на сохранённых HTML-
  фикстурах разных состояний страницы.
- Парсер возвращает значение вместе с признаком наличия и качеством извлечения.
- Изменение разметки не должно массово помечать объявления снятыми.
- При резком падении полноты обязательных полей источник автоматически
  приостанавливается и требует внимания администратора.

## 8.2. Оркестрация заданий

- Сервер является единственным владельцем расписаний и приоритетов.
- Задание выдаётся агенту с ограниченной арендой и heartbeat.
- Повторная доставка допустима; обработка результата на сервере идемпотентна.
- Одну ревизию поиска нельзя выполнять параллельно без явного разрешения.
- Приоритеты: ручные проверки, новые объявления, наблюдаемые объекты и сигналы
  цены не блокируются первичным массовым наполнением.
- Агент сохраняет результат в локальный SQLite outbox до подтверждения сервера.
- После потери агента аренда истекает, а задание может получить другой совместимый
  агент без потери уже подтверждённых данных.

## 8.3. Безопасность агента

- Агент использует отдельную машинную учётную запись с минимальными правами.
- Токен агента нельзя использовать для входа в пользовательский интерфейс.
- Агент не получает connection string и не подключается к PostgreSQL.
- Секреты и браузерные профили не попадают в Git, обычные логи или payload задачи.
- Возможности агента объявляются серверу; несовместимое задание не выдаётся.
- Должны существовать pause, drain, revoke и аварийная остановка источника.
- CAPTCHA, запрос повторной авторизации, блокировка и нетипичная страница создают
  состояние `AttentionRequired`; запрещён скрытый обход ограничений.

## 8.4. Качество сбора

- Счётчик результатов площадки не равен количеству реально прочитанных карточек.
- Сортировка «по дате» не считается строго хронологической без проверки.
- Первичный прогон не останавливается только на первом известном ID; используется
  перекрытие страниц и контрольная сверка.
- Объявления из рекомендаций и других городов не смешиваются с основной выдачей.
- Заголовок, параметры и описание могут противоречить друг другу; исходные
  значения сохраняются отдельно.
- Дата площадки и дата первого обнаружения системой являются разными фактами.


# 9. СТАТУСЫ И БИЗНЕС-ЛОГИКА

- Запрещено описывать весь жизненный цикл одним полем `Status`.
- Раздельно хранить как минимум:
  - доступность объявления у источника;
  - результат и качество последнего сбора;
  - интерес бизнеса к объекту;
  - стадию проверки;
  - стадию реального проекта;
  - статус публикации для инвестора.
- Неизвестное значение не равно отрицательному.
- «Юридически чист» не является автоматически вычисляемым флагом.
- Результат проверки содержит предмет, источник, автора, время, вывод и
  нерешённые вопросы.
- Решаемая проблема и критическое ограничение являются выводами проверки, а не
  ключевыми словами объявления.
- Переходы между состояниями выполняются командами и журналируются.


# 10. ФИНАНСЫ И ИНВЕСТОРЫ

## 10.1. Финансовая целостность

- Исходные данные, допущение, прогноз, согласованное значение и факт хранятся
  раздельно и визуально различаются.
- Цена объявления, цена продавца в переговорах, предложение компании и
  утверждённый лимит покупки — разные значения.
- Прибыль проекта не равна доходности конкретного инвестора.
- Бюджет имеет версии; утверждённая версия не изменяется скрытно.
- Движения капитала и выплаты журналируются как отдельные события.
- Исправление подтверждённого финансового события выполняется корректирующим
  событием, а не удалением истории.
- Любая формула должна иметь название, версию, единицы, правила округления и тесты.

## 10.2. Доступ инвестора

- Инвестор видит только назначенные ему проекты.
- Данные других инвесторов скрыты; агрегаты доступны только по отдельному праву.
- Инвестор видит только опубликованные документы, отчёты и значения.
- Черновики внутренних расчётов не публикуются автоматически.
- Каждая публикация имеет автора, время, версию и аудит.
- Изменение участия, доступов, условий, выплат и документов обязательно
  журналируется.
- Проверка доступа выполняется сервером на каждом запросе и скачивании файла.


# 11. БЕЗОПАСНОСТЬ И АУДИТ

- Авторизация строится на именованных разрешениях и областях доступа, а не только
  на строковых названиях ролей.
- Начальные роли: владелец, администратор, менеджер, наблюдатель и инвестор.
- Области доступа: организация, назначенные проекты, собственные задачи и
  специально опубликованные материалы.
- Защита от IDOR обязательна: идентификатор объекта из запроса не доказывает право
  пользователя на этот объект.
- Минимум для владельца и администратора — многофакторная аутентификация.
- Пользовательские и машинные учётные записи разделяются.
- Секреты запрещено хранить в исходном коде, конфигурации репозитория и логах.
- Журнал аудита отделён от технических логов и не содержит секретов.
- Аудировать: роли, права, расписания, поисковые ссылки, подтверждённые факты,
  бюджет, публикации инвесторам, выплаты, экспорт и будущую отправку сообщений.
- Персональные и контактные данные маскируются в логах и ограничиваются правами.
- Все внешние входные данные, HTML и имена файлов считаются недоверенными.


# 12. BLAZOR И TYPESCRIPT

- UI использует единый набор дизайн-токенов и переиспользуемых компонентов.
- Базовый CSS — локальный Bootstrap из шаблона Blazor, без CDN, NuGet и отдельной
  npm-сборки; Bootstrap не считать частью runtime Blazor.
- Поверх Bootstrap создавать собственные Blazor-компоненты Land ERP; не добавлять
  готовую component library в первом контуре.
- Bootstrap JavaScript по умолчанию не подключать: интерактивность реализовать
  Blazor и нативным HTML, а JS добавлять только для доказанного сценария.
- Использовать системный стек шрифтов без внешнего web-font.
- Новая фича не вводит собственные цвета, отступы, статусы и формы без плана UI.
- Бизнес-правила не реализуются только на клиенте.
- Кнопки и экраны скрываются по правам для удобства, но безопасность обеспечивает
  серверная проверка.
- Компонент Blazor, подписанный на события или JS-ресурсы, реализует корректный
  `IDisposable` или `IAsyncDisposable`.
- JS/TS-модуль должен иметь явный lifecycle и освобождать обработчики, таймеры и
  внешние ресурсы.
- Перед обращением к DOM проверять наличие элемента.
- Ошибка JS interop не должна разрушать весь экран; она обрабатывается и
  диагностируется с контекстом операции.
- Контракты C# ↔ TypeScript типизированы и имеют явную политику сериализации.
- Сложная карта и геовизуализация добавляются отдельным планом; библиотека карты
  выбирается после определения сценариев, объёма геометрии и требований UX.


# 13. ТЕСТИРОВАНИЕ

## 13.1. Тесты по умолчанию

- Бизнес-логика не реализуется без одновременного создания или обновления тестов.
- План каждой фичи содержит стратегию тестирования до начала написания кода.
- Фича не завершена, если тесты не подтверждают её критерии приёмки.
- Исправление дефекта начинается с воспроизводящего теста, если это технически
  возможно.

## 13.2. Виды тестов

- Unit-тесты — чистые правила, расчёты, переходы состояний и валидаторы.
- Интеграционные тесты — EF Core и реальные особенности PostgreSQL через
  изолированный PostgreSQL/Testcontainers; EF InMemory не использовать для
  подтверждения SQL-поведения.
- Контрактные тесты источников — HTML-фикстуры выдачи и карточки, включая
  противоречивые, пустые, заблокированные и изменённые страницы.
- Тесты API — авторизация, идемпотентность, валидация и совместимость контрактов.
- E2E-тесты — критические пользовательские маршруты в Blazor через Playwright.
- Архитектурные тесты — границы модулей, запрет циклов, запрет утечки entities и
  расположение вертикальных срезов.
- Тесты безопасности — отрицательные сценарии доступа и изоляция инвесторов.
- Тесты устойчивости — повторная доставка, истечение аренды, сбой сети, перезапуск
  агента и запоздавшие результаты.

## 13.3. Стиль тестов

- Основной стек: xUnit и FluentAssertions либо утверждённый эквивалент.
- Тесты строятся по AAA с визуально разделёнными Arrange, Act, Assert.
- Имя теста описывает действие, ожидаемое поведение и условие.
- Временные сценарии используют внедряемый `TimeProvider` и фиксированное время.
- Финансовые тесты покрывают ноль, отрицательные значения, границы, округление,
  валюту и версии исходных данных.
- Геопространственные тесты выполняются на том же типе БД и расширении, что и
  production.

## 13.4. Минимальная проверка изменения

- Сборка решения без ошибок и неожиданных предупреждений.
- Архитектурные тесты.
- Тесты затронутого вертикального среза.
- Интеграционные тесты при изменении БД, EF-запросов, очередей или авторизации.
- Контрактные тесты при изменении адаптера источника.
- E2E-тест критического пути при изменении пользовательского сценария.
- Проверка форматирования и статического анализа.


# 14. НАБЛЮДАЕМОСТЬ И ЭКСПЛУАТАЦИЯ

- Все запросы, задания и результаты имеют correlation/trace identifier.
- Структурированные логи содержат событие, модуль, идентификаторы объектов и
  результат, но не секреты и не лишние персональные данные.
- Метрики отделены от аудита.
- Минимальные метрики сбора: длительность, успех, тип ошибки, полнота полей,
  количество новых и изменённых объявлений, возраст очереди и состояние агентов.
- Минимальные метрики менеджера: размер очереди, возраст решения, причины возврата
  и переходы по воронке.
- Health checks должны различать готовность и жизнеспособность процесса.
- Для production обязательны резервные копии, проверяемое восстановление,
  мониторинг свободного места и срок хранения журналов.
- Изменение критичной настройки должно иметь безопасное значение по умолчанию,
  аудит и возможность аварийного отключения.


# 15. GIT И РЕВЬЮ

- Не выполнять commit, push, merge, rebase или создание pull request без явного
  запроса пользователя.
- Предлагать логический коммит после завершения целого вертикального изменения,
  а не после каждого технического слоя.
- Один коммит не должен смешивать независимые фичи и массовое форматирование.
- Использовать Conventional Commits: `<type>(<scope>): описание на русском>`.
- Сообщение объясняет бизнес-результат, а не просто перечисляет технологию.
- Перед предложением коммита проверить diff, тесты и отсутствие секретов.
- Архитектурные тесты нельзя удалять, отключать или ослаблять ради прохождения CI.
- Исправление архитектурного теста выполняется в коде либо через отдельное
  утверждённое ADR с объяснением изменения правила.


# 16. ПЛАНЫ И АРХИТЕКТУРНЫЕ РЕШЕНИЯ

- Генеральный план описывает устойчивую архитектуру, границы и порядок развития;
  в нём нет примеров реализации конкретного кода.
- Каждая крупная фича перед разработкой получает отдельный план.
- План фичи содержит бизнес-цель, сценарии, границы, данные, API, UI, права,
  наблюдаемость, миграции, тесты, этапы и примеры эталонного кода.
- Примеры кода в плане фичи должны соответствовать фактическому стеку и проходить
  компиляционную проверку после переноса в репозиторий.
- Значимое и трудно обратимое архитектурное решение оформляется ADR.
- План задачи не дублирует план фичи, а ссылается на него и описывает конкретный
  проверяемый объём работы.
- После реализации обновлять статус плана и журнал решений; завершённый план не
  переписывать так, будто первоначальных допущений не существовало.


# 17. DEFINITION OF DONE

Задача считается завершённой, только если одновременно выполнено следующее:

- Реализован согласованный бизнес-сценарий без скрытого расширения объёма.
- Соблюдены границы модулей и вертикального среза.
- Входные данные валидируются, права проверяются на сервере.
- Изменения данных и миграции безопасны и документированы.
- Добавлены или обновлены необходимые тесты; обязательные проверки зелёные.
- Добавлены необходимые логи, метрики и аудит.
- UI использует единые компоненты и корректно обрабатывает loading, empty, error,
  forbidden и success состояния.
- Документация и план фичи отражают фактическое решение.
- Diff не содержит чужих изменений, секретов, временных файлов и отладочных
  обходов.
- Итог пользователю содержит перечень изменений, цель, принцип работы, проверки и
  известные ограничения.
