# Инструкции ИИ-агентам LandErp

Эти правила действуют для всего репозитория. Более локальный `AGENTS.md` может
уточнить их, но не отменяет ограничение активной задачи и ручного подтверждения.

## 1. Обязательный маршрут старта

Перед любым анализом или изменением прочитай строго по порядку:

1. `README.md`;
2. `docs/START_HERE.md`;
3. `docs/03-active/ACTIVE_TASK.md`;
4. только документы, перечисленные в `Required reading` активной задачи;
5. только после этого — затрагиваемый код.

Не выполняй рекурсивное чтение `docs/`, не открывай весь реестр планов и не
изучай документы будущих волн «для полноты». Контекст является ограниченным
ресурсом.

## 2. Единственная единица разрешённой работы

- Одновременно активен только один Gate или TP.
- Документ `docs/03-active/ACTIVE_TASK.md` является единственным указателем
  текущей работы.
- План верхнего уровня, ADR, FP или SPIKE не является разрешением реализовать всё
  его содержимое.
- Если пользователь не утвердил текущий Gate в своём запросе, сначала представь
  план и перечень файлов; запись не начинай.
- Не переходи к следующему Gate после завершения текущего.

## 3. Ограничение текущего этапа

По запросу владельца 2026-09-14 выполнен документационный переход `ERP-00`.
`SPIKE-001` закрыт как исследовательская фаза; его прежний общий запрет на
Server/PostgreSQL/EF Core/Blazor снят. Это не подтверждает production-готовность
Collector и не разрешает реализацию следующего Gate без отдельного запроса.

- Единственный следующий Gate — `ERP-01`: техническое основание и БД.
  Он подготовлен, но в рамках ERP-00 не реализуется; production migrations не создаются.
- Server/Application/Infrastructure/Worker, PostgreSQL и EF Core допустимы только
  в утверждённом scope ERP-01; Worker — host skeleton, без серверной очереди и jobs.
- Identity, Workflow, Blazor UI, кабинет инвестора, бизнес-модули и Collector
  integration в ERP-01 не входят. Снятие запрета Blazor не активирует UI.
- Collector остаётся самостоятельным приложением по ADR-007. Browser/Playwright,
  source adapters, WPF и локальная SQLite не переносятся в Server; Collector
  не получает прямого доступа к PostgreSQL и внутренним ERP entities.
- Работающий Collector не переписывается; его отдельные доработки,
  server adapter, установщик/обновление/tray и новые источники требуют своего Gate.
- Сообщения продавцам и раскрытие телефонов не разрешены текущими задачами.
- Обход CAPTCHA, fingerprint masking, proxy rotation и другие механизмы
  противодействия защите источника остаются запрещены.
- Перед генерацией первой production migration завершить review data conventions
  из ERP-01 и бизнес-карты. Применение к production — отдельное разрешение;
  startup не меняет production schema, applied migrations не переписываются.

## 4. Git и безопасность изменений

- Работай в ветке, указанной активной задачей.
- Не изменяй `main` напрямую, если пользователь явно не попросил обратное.
- Не выполняй merge, rebase, force-push, reset, удаление веток или релиз без
  отдельного разрешения.
- Не переписывай уже опубликованную историю.
- Перед записью перечисли планируемые файлы и проверки.
- Не удаляй пользовательские файлы. Временные файлы удаляй только если они
  созданы текущей задачей и точный путь проверен.

## 5. Технологическая база

- C# 14 и .NET 10 LTS.
- Windows x64 — первая целевая платформа исследовательского Agent.
- Microsoft.Playwright — единственная внешняя зависимость браузерного слоя Spike,
  если активный Gate не говорит иначе.
- Central Package Management и фиксированные версии без wildcard.
- Nullable reference types и warnings as errors для собственного кода.
- Никаких новых пакетов без обоснования, проверки лицензии/поддержки и одобрения.

## 6. Правила парсинга

- Сначала классифицируй страницу, затем извлекай бизнес-поля.
- `Captcha`, `AuthenticationRequired`, `RateLimited`, `SourceError` и `Unknown`
  не являются пустой успешной выдачей.
- Не создавай synthetic external ID.
- Не смешивай основной результат с рекламой, рекомендациями и другими регионами.
- Сохраняй различие `Raw`, `Parsed` и `Presence`.
- Отсутствие поля в одном наблюдении не очищает автоматически старое значение.
- Никакого автоматического обхода защитных механизмов.
- Cookies, токены, пароли, auth headers и содержимое личных сообщений не должны
  попадать в Git, логи, fixtures и отчёты.

## 7. Качество и завершение

- Тесты являются частью Gate, а не последующим улучшением.
- Не объявляй работу завершённой без фактического запуска обязательных проверок.
- Если проверка недоступна в среде, явно назови её и не заменяй предположением.
- В конце создай отчёт по шаблону активного Gate: изменённые файлы, решения,
  команды, результаты, ограничения и следующий рекомендуемый шаг.
- Найденная проблема вне scope фиксируется, но не исправляется самовольно.

## 8. Дополнительные правила

После обязательного чтения использовать актуальный Gate и отчёт; не перечитывать
неизменившиеся документы на каждой правке. После смены контекста восстановить
scope по ACTIVE_TASK, Gate и отчёту. Открытый для предметной работы код пояснять
рядом с важными границами и инвариантами; отдельный обход ради комментариев не делать.

Правила Zoo Code находятся в `.roo/`. При расхождении приоритет имеют:

1. прямой запрос пользователя;
2. ближайший `AGENTS.md`;
3. `docs/03-active/ACTIVE_TASK.md` и активный Gate;
4. утверждённые ADR;
5. общие правила `.roo/`;
6. планы будущих функций.

Для production-задач ERP, затрагивающих оргструктуру, workflow, справочники,
финансы, согласования, задачи/SLA, документы, историю, уведомления, интеграции или
управленческие метрики, активная задача должна включать
`docs/04-foundation/FP-004_Сквозное_ERP-ядро_и_общие_бизнес-механизмы.md` в
`Required reading`. Сам по себе FP-004 не разрешает реализовывать весь его объём.
