# FP-013 — Каталог объявлений, наблюдения и дедупликация

**Версия:** 0.1  
**Статус:** Черновик  
**Владелец:** владелец продукта / аналитик данных  
**Модуль-владелец:** PropertyCatalog  
**Зависимости:** FP-001, FP-002, FP-010, FP-011, FP-012  
**Блокирует:** FP-014 и рабочее место менеджера FP-020–FP-024

## 1. Решение

Создать каталог, в котором Listing представляет одно объявление конкретного
источника, а каждое чтение создаёт неизменяемое ListingObservation. Точное
устранение дублей выполняется по `SourceCode + ExternalId`; появление одного
Listing в нескольких поисках хранится отдельными SearchMatch. Актуальная карточка
является вычисленным представлением истории и не стирает detail-данные снимком
выдачи. Связывание разных объявлений с одним реальным PropertyCase выполняется
отдельно и не подменяется агрессивной автоматической дедупликацией.

## 2. Ценность

- одно объявление не размножается из-за пересекающихся поисков;
- цена и доступность сохраняются во времени;
- повторная доставка Agent не создаёт второе наблюдение;
- можно объяснить происхождение каждого значения;
- неполный новый снимок не уничтожает ранее известные детали;
- менеджер видит новые и действительно изменившиеся предложения;
- в будущем несколько объявлений можно связать с одним объектом безопасно.

## 3. Границы

### Входит

- Source и Listing;
- неизменяемый ListingObservation;
- SearchRun/SearchMatch references;
- идемпотентный приём результата Agent;
- exact deduplication по Source + ExternalId;
- нормализованные основные поля и исходные значения;
- current projection;
- история цены, площади, локации и доступности;
- обнаружение значимых изменений;
- признаки противоречий и качества;
- связь Listing → PropertyCase как отдельное решение;
- API списка, карточки и истории;
- события для ManagerWorkspace.

### Не входит

- автоматическое объединение разных external ID по фото/телефону;
- окончательная модель Parcel и Building;
- юридические проверки;
- рыночная оценка;
- полнофункциональная очередь менеджера;
- загрузка всех фотографий;
- удаление истории после снятия объявления;
- универсальный EAV-каталог всех полей площадки.

## 4. Термины

| Термин | Значение |
|---|---|
| Source | Площадка/канал происхождения объявления |
| Listing | Стабильная сущность объявления `Source + ExternalId` |
| ListingObservation | Один неизменяемый результат чтения |
| SearchMatch | Факт появления Listing в конкретном SearchRun/позиции |
| CurrentListingView | Быстрое вычисленное актуальное представление |
| SignificantChange | Доменное событие о полезном изменении |
| PropertyCase | Реальный объект-кандидат, отличный от объявления |
| ListingPropertyLink | Явная связь Listing и PropertyCase с автором/основанием |

## 5. Уникальность и уровни дедупликации

### Уровень 1 — транспортный

Повтор результата с тем же `AgentId + ResultId` возвращает прежнее подтверждение.
Новая Observation не создаётся.

### Уровень 2 — объявление

`SourceCode + ExternalId` уникальны. URL, заголовок и цена не являются primary key.

### Уровень 3 — одинаковый снимок

Если один и тот же content hash для того же Listing/level/observed window пришёл
повторно из-за технической доставки, создаётся один Observation. Если это реально
новый плановый проход, допустимо сохранить отдельный факт проверки доступности с
тем же содержанием; правило различает delivery duplicate и repeated observation.

### Уровень 4 — реальный объект

Разные Listing не объединяются автоматически в один PropertyCase только из-за
похожего адреса, цены или фото. Система может предложить кандидатов на связь, но
решение имеет основание, автора, время и возможность отмены с историей.

## 6. Основной поток сохранения

1. Collection передаёт принятую extraction result в публичный контракт каталога.
2. Каталог проверяет idempotency и Source/ExternalId.
3. Listing создаётся или находится.
4. Создаётся Observation с raw/parsed/presence и provenance.
5. SearchMatch связывается с SearchRun без дублирования.
6. Current projection обновляется по правилам уровня и времени.
7. Вычисляются изменения относительно предыдущего сопоставимого состояния.
8. Публикуются события `ListingDiscovered`, `ListingPriceChanged`,
   `ListingAvailabilityChanged`, `ListingDataConflictDetected`.
9. ManagerWorkspace решает, создавать ли действие в очереди.

Сохранение Observation и outbox событий выполняется транзакционно.

## 8. Правила current projection

### 8.1. Приоритет уровня

- Detail Observation может заполнять поля, которых нет в SearchResult.
- Новый SearchResult обновляет цену, краткий заголовок и доступность, если поле
  действительно присутствовало.
- Новый SearchResult не очищает description, coordinates, attributes и photos,
  потому что они были `NotInspected`.
- Detail с ParseFailed не перезаписывает прежнее корректное значение без явного
  события качества.

### 8.2. Порядок времени

- Для факта источника учитывается ObservedAt.
- ReceivedAt используется для технического порядка и диагностики.
- Запоздавшая Observation сохраняется, но не становится current, если существует
  более новое сопоставимое качественное наблюдение.
- При одинаковом ObservedAt применяется детерминированный tie-breaker и audit.

### 8.3. Ручные подтверждения

Подтверждённые менеджером/специалистом значения хранятся как FieldAssertion и не
перезаписываются рекламным текстом. Current source view и confirmed property view
не смешиваются.

## 9. Значимые изменения

### Первая версия

- первое обнаружение Listing;
- изменение публичной цены;
- изменение площади при подтверждённом присутствии поля;
- изменение canonical URL без ExternalId;
- явное снятие/возврат объявления;
- изменение заголовка/назначения, создающее противоречие;
- появление подробной карточки после summary;
- существенное изменение продавца/типа профиля;
- новый кадастровый номер как заявление источника;
- резкое падение качества извлечения не является бизнес-изменением Listing, а
  инцидентом Collection.

### Цена

- Цена хранится amount + currency + raw text.
- Null/Absent/ParseFailed не равны нулю.
- Цена за сотку площадки и вычисленная цена хранятся раздельно.
- Снижение цены считается сопоставимым только если площадь и состав предложения
  не изменились либо менеджер подтвердил сопоставимость.
- Правило significance имеет версию и настраиваемый абсолютный/процентный порог.

## 10. Доступность

- Один неуспешный SearchRun не снимает Listing.
- Отсутствие в одной пересекающейся выдаче не доказывает снятие.
- Явная unavailable detail page создаёт observation соответствующего типа.
- Снятие может требовать повторного подтверждения по политике.
- Возврат объявления создаёт отдельное событие.
- Source outage и parser failure не меняют availability Listing.

## 15. Индексы и производительность

Минимальные индексы:

- unique OrganizationId + SourceCode + ExternalId;
- Listing LastObservedAt;
- Listing current availability;
- Observation ListingId + ObservedAt desc;
- SearchMatch SearchRunId + position;
- SearchMatch ListingId + MatchedAt;
- Change ListingId + DetectedAt;
- ResultId uniqueness.

JSONB index создаётся только для подтверждённого запроса. История пагинируется по
стабильному cursor, а не большим OFFSET на растущей таблице.

## 16. Хранение и удаление

- Listing не удаляется после снятия.
- Observation имеет долгосрочную ценность для истории рынка; срок утверждается
  отдельной data-retention policy.
- Большие raw artifacts хранятся отдельно и могут иметь короткий срок.
- Удаление персональных данных выполняется отдельно от обезличенной истории цены,
  если это допускает политика и закон.
- Архивирование PropertyCase не удаляет Listing.

## 17. Безопасность и аудит

- Ingest доступен только внутреннему доверенному серверному пути, не напрямую Agent
  к доменному модулю.
- Пользовательские reads фильтруются Organization/project scope.
- Link/unlink аудируются с основанием.
- Ручное подтверждение поля аудируется как отдельное действие.
- Raw description и seller data не попадают в обычные логи.
- Diagnostic artifact защищён отдельным разрешением.

## 18. Наблюдаемость

- listings created/updated;
- observations accepted/duplicate/late;
- price/availability changes;
- projection update failures;
- contradiction count;
- observation completeness;
- event outbox lag;
- DB query duration и размер истории;
- suspected duplicate PropertyCase suggestions отдельно от подтверждённых связей.

## 19. Тестирование

| Уровень | Обязательные случаи |
|---|---|
| Unit | current projection precedence, late observation, price significance, presence semantics |
| Integration | unique Source+ExternalId, ResultId idempotency, transaction observation+outbox, cursor history |
| Contract | payload FP-012 всех fixtures |
| Concurrency | два Agent создают один Listing; одновременные observations |
| Security | чужая Organization, raw diagnostic permission, link outside scope |
| E2E | ingest → list → history → price change → link PropertyCase |

Контрольный тест обязан доказать: новый SearchResult с `description = NotInspected`
не очищает description из прежней Detail Observation.

## 20. Вертикальные этапы

1. Первый accepted result создаёт Listing и Observation.
2. Повтор ResultId возвращает тот же outcome без дубля.
3. Пересекающиеся SearchRun создают SearchMatch к одному Listing.
4. Detail дополняет current projection, summary не стирает detail.
5. Цена меняется и создаёт историю/событие.
6. Availability отличает source incident от явного unavailable.
7. Карточка и история доступны пользователю с правом.
8. Добавляется ручная связь Listing → PropertyCase с аудитом.

## 21. Развёртывание и миграции

- Сначала разворачиваются таблицы и ingest без менеджерских событий.
- Затем включается projection и сравнение в shadow mode на контрольных данных.
- После проверки включаются события ManagerWorkspace.
- Изменение significance rules версионируется и не переписывает историю скрытно.
- Rebuild projection выполняется из observations и имеет контрольный hash/count.
- Откат приложения не удаляет новые observations.

## 22. Definition of Ready

- утверждён payload FP-012;
- определены обязательные typed fields;
- согласована уникальность с OrganizationId;
- определены правила late observation;
- согласован первый порог изменения цены;
- выбрана политика availability confirmation;
- согласована data-retention policy хотя бы для пилота;
- создан минимальный PropertyCase stub/contract для связи.

## 23. Definition of Done

- Source + ExternalId создают один Listing;
- повтор ResultId не создаёт Observation;
- реальный новый проход может сохранить одинаковое наблюдение по политике;
- SearchMatch сохраняет все поиски и позиции;
- summary не стирает detail;
- late result не откатывает current view;
- цена и availability имеют историю;
- source incident не снимает объявления;
- разные external ID не объединяются автоматически в PropertyCase;
- provenance доступен в карточке;
- outbox событий транзакционен;
- integration/concurrency/security/E2E tests зелёные.
