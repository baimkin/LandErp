# ADR-003 — Сохраняемая очередь в PostgreSQL

**Статус:** Принято  
**Дата:** 6 сентября 2026 года  
**Владелец решения:** технический владелец  
**Затрагивает:** Collection, Worker, Agent API, эксплуатацию и мониторинг

## 1. Решение

Для первой версии хранить задания сбора в PostgreSQL. Worker создаёт задания,
Agent получает их через серверный HTTPS API, а сервер атомарно выдаёт аренду
одной задаче. Выбор конкурентными Worker выполняется транзакционно с
`FOR UPDATE SKIP LOCKED` или эквивалентным корректным запросом EF/SQL.

Внешний брокер сообщений в первый контур не добавлять. Плановые триггеры и
бизнес-очередь остаются разными понятиями: расписание определяет, когда создать
задание, таблица очереди хранит его жизненный цикл.

## 2. Почему это соответствует масштабу

Исходный объём — 30–50 поисковых ссылок и 3–5 локальных компьютеров. Для него
PostgreSQL обеспечивает требуемую сохранность, транзакции и прозрачную
диагностику без отдельного кластера и второго механизма восстановления.

## 3. Минимальная модель

`CollectionTask` содержит:

- `Id`, `TaskType`, `SourceCode`, `PayloadVersion`, `Payload`;
- `Priority`, `State`, `AvailableAt`, `CreatedAt`;
- `DeduplicationKey` и область его уникальности;
- `AttemptCount`, `MaxAttempts`, `LastErrorCategory`;
- активные `LeaseId`, `AgentId`, `LeaseExpiresAt`, `HeartbeatAt`;
- `CompletedAt`, `CancelledAt`, `CorrelationId`;
- concurrency token.

Результат имеет созданный агентом `ResultId`; уникальность `(AgentId, ResultId)`
делает повторную отправку безопасной. Сырые большие материалы хранятся отдельно,
в очереди находятся только ссылки и метаданные.

## 4. Атомарная выдача

В одной короткой транзакции сервер:

1. выбирает доступную задачу с учётом capability, источника и приоритета;
2. блокирует только выбранную строку;
3. меняет состояние на `Leased`;
4. создаёт новый `LeaseId` и срок аренды;
5. фиксирует аудит выдачи;
6. возвращает контракт после commit.

Браузерная работа никогда не выполняется внутри транзакции БД. Heartbeat только
продлевает действующую аренду в установленном пределах. Истёкшую аренду reaper
возвращает в очередь, если результат не был принят.

Упрощённый эталон SQL для обсуждения:

```sql
WITH candidate AS (
    SELECT id
    FROM collection.tasks
    WHERE state = 'Pending' AND available_at <= now()
    ORDER BY priority, available_at, id
    FOR UPDATE SKIP LOCKED
    LIMIT 1
)
UPDATE collection.tasks AS task
SET state = 'Leased', lease_id = @lease_id,
    agent_id = @agent_id, lease_expires_at = @lease_expires_at
FROM candidate
WHERE task.id = candidate.id
RETURNING task.*;
```

Точная схема и синтаксис утверждаются миграцией и интеграционным тестом на
PostgreSQL 18; пример нельзя копировать без условий capability/source limits.

## 5. Приоритет и справедливость

Используются P0–P4 из FP-011. Порядок внутри приоритета детерминирован. Worker
резервирует долю мощности для фонового P4, чтобы первоначальный сбор завершался,
но свежие объявления и наблюдаемые объекты имели преимущество.

Глобальные и поисковые ограничения скорости задаются отдельно от приоритета.
Наличие свободного Agent не даёт права превысить лимит источника.

## 6. Повторы и завершение

- Бесконечных повторов нет.
- Категория ошибки определяет backoff и допустимость повтора.
- CAPTCHA, неизвестная разметка и потеря авторизации требуют человека.
- `DeadLetter` сохраняет задачу и диагностику; запись не удаляется автоматически.
- Completion принимается идемпотентно.
- Запоздавший результат может пополнить историю, но не обязан стать актуальным.
- Отмена аренды не удаляет уже подтверждённый факт.

## 7. Очистка и эксплуатация

Активные задания не архивируются. Завершённые записи сохраняются на срок,
достаточный для аудита прогона, после чего могут переноситься в архивную таблицу
или удаляться по утверждённой политике. Конкретный срок задаётся OP-003.

Обязательные метрики: глубина по типу/приоритету, возраст старейшей задачи,
скорость создания/завершения, истечения аренд, retry/dead-letter, длительность
lease и доля повторной доставки.

## 8. Рассмотренные варианты

| Вариант | Решение |
|---|---|
| PostgreSQL queue | Рекомендуется для первого масштаба и одной операционной БД |
| Hangfire/Quartz как бизнес-очередь | Не использовать как скрытую доменную модель; допустимы позже как механизм расписаний после ADR |
| RabbitMQ/Kafka/облачная очередь | Отложить до измеримой потребности в независимом масштабировании или доставке между сервисами |
| In-memory очередь | Запрещена для бизнес-заданий: теряет состояние при перезапуске |

## 9. Критерии перехода к брокеру

Отдельный ADR рассматривается, если подтверждены хотя бы два фактора:

- очередь стала узким местом по измерениям;
- появились независимо развёртываемые производители/потребители;
- требования к задержке или объёму не покрываются PostgreSQL;
- нужна географически распределённая доставка;
- эксплуатационная команда готова обслуживать второй stateful-компонент.

## 10. Проверки реализации

- конкурентный тест нескольких lease-запросов без двойной выдачи;
- crash/restart Worker и Agent;
- истечение и продление аренды;
- повтор completion с тем же ResultId;
- поздний результат после новой аренды;
- starvation и лимиты источника;
- explain plan и индексы на реалистичном объёме.

## 11. Зафиксированное решение

6 сентября 2026 года PostgreSQL-очередь принята как стартовое решение. Точные
lease/retry/retention значения задаются настройками и операционными планами, а
не закрепляются навсегда в ADR.
